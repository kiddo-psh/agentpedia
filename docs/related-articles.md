# 관련 기사 그래프

> 상태: 1단계(태그 기반) 구현 · 2026-11-13

기사 끝에 가까운 기사를 최대 4개까지 작은 그래프와 목록으로 보여 줍니다. 이 문서는 지금 방식과, 기사가 늘어났을 때 쓸 두 가지 확장 방식을 기록합니다.

## 참고한 사례

Anthropic 블로그의 기사 페이지(예: `anthropic.com/research/redesigning-source-control`)는 "Related articles" 영역에 280×105 SVG를 둡니다. 노드 5개, 선 4개이고, 노드는 썸네일을 원으로 자른 모양입니다. SVG는 서버가 렌더링한 HTML에 이미 들어 있어서 브라우저에서 그래프 라이브러리가 돌지 않습니다. 관련 기사를 고르는 방식은 공개되어 있지 않습니다. 기사마다 Topics 태그가 붙어 있어서 태그 기반이거나 편집자가 직접 지정한다고 추정합니다.

## 1단계: 공유 신호 점수 (현재)

코드는 `src/content/related.ts`, 화면은 `src/components/RelatedArticles.tsx`에 있습니다.

| 공유하는 것 | 가중치 |
|---|---|
| 인물 (`people`) | 3 |
| 태그 (`tags`) | 2 |
| 용어집 용어 (본문의 `<Term>`) | 1 |
| 같은 카테고리 | 1 |

- 점수가 2 이상인 기사만 관련 기사로 칩니다. 태그나 인물 하나를 공유하면 충분하고, 카테고리나 용어 하나만 같으면 부족합니다.
- 점수가 같으면 최신 기사가 먼저 옵니다.
- 관련 기사끼리도 점수가 2 이상이면 점선으로 잇습니다.
- 관련 기사가 없으면 섹션을 숨깁니다.
- 계산은 렌더링할 때 메모리에서 합니다. 기사 n개에 대해 O(n²)이고, 기사가 수백 개가 되어도 빌드 시간에 영향이 없습니다.

### 현재 콘텐츠에서 드러난 점

기사 8개 중 `harrison-chase-agent-harness`와 `karpathy-software-3`은 다른 기사와 겹치는 태그가 없어 관련 기사가 0개입니다. 알고리즘보다 태그 어휘가 결과를 더 크게 좌우합니다. 예를 들어 `agent-ready`와 `agent-ready-docs`, `claude-md`와 `context-files`는 같은 주제를 다른 이름으로 부릅니다. 다음 둘 중 하나가 먼저 필요합니다.

- 태그 목록을 `content/tags.yaml` 같은 레지스트리로 고정하고, `validate:content`가 목록에 없는 태그를 거부하게 합니다. 인물과 용어집이 이미 이 방식입니다.
- 아래 2단계로 태그에 의존하지 않는 유사도를 더합니다.

## 2단계 후보 A: 임베딩 유사도

기사 본문의 의미가 가까운 기사를 찾습니다. 태그가 겹치지 않아도 같은 주제를 다룬 기사를 잇습니다.

1. **임베딩할 텍스트.** 본문 전체보다 `title + summary + keyIdeas`가 낫습니다. 짧고, 기사의 주장을 담고, 인용이나 사례 서술의 잡음이 적습니다.
2. **생성 시점.** 빌드 중에 API를 부르지 않습니다. `scripts/embed-articles.ts`가 기사별 벡터를 `content/articles/<slug>/embedding.json`에 쓰고, 이 파일을 커밋합니다. 파일에 입력 텍스트의 해시를 같이 저장해 두고, 해시가 같으면 다시 계산하지 않습니다. `validate:content`는 해시가 낡은 파일을 경고합니다.
3. **점수 합치기.** 코사인 유사도를 0~1로 두고 `score = 공유 신호 점수 + k × cosine`으로 더합니다. `k`는 기사 20개쯤 모였을 때 사람이 고른 "좋은 관련 기사" 쌍 몇 개를 기준으로 맞춥니다.
4. **저장소.** 기사가 수천 개 아래라면 JSON 파일과 메모리 계산으로 충분합니다. 그 이상이면 이미 쓰고 있는 Postgres(Neon)에 `pgvector`를 켜서 옮깁니다.

주의할 점입니다.

- 임베딩 모델을 바꾸면 모든 벡터를 다시 만들어야 합니다. 파일에 모델 이름을 같이 저장합니다.
- 한국어 본문이므로 다국어 임베딩 모델을 써야 합니다.
- 유사도가 높다고 독자에게 유용한 것은 아닙니다. 같은 사건을 다룬 두 기사는 유사도가 높지만, 독자는 다른 관점의 기사를 원할 수 있습니다.

## 2단계 후보 B: LLM이 `related` 후보 제안

LLM이 관련 기사를 제안하고 사람이 검수해 frontmatter에 확정합니다. 관련 이유를 문장으로 받을 수 있다는 점이 임베딩과 다릅니다.

1. **스키마.** frontmatter에 `related: [{ slug, reason }]`를 추가합니다. `reason`은 "같은 공급망 공격을 방어 쪽에서 다룸"처럼 한 문장입니다. `validate:content`는 slug가 실제 기사인지 확인합니다.
2. **제안 시점.** `write-article` 스킬의 수정 단계 뒤에 넣습니다. 새 기사의 `title`, `summary`, `keyIdeas`와 기존 기사 전체의 같은 필드를 LLM에 주고, 후보 3~5개와 이유를 받습니다. 기존 기사가 많아지면 먼저 1단계 점수나 임베딩으로 후보를 20개쯤 추린 뒤 LLM에 넘깁니다.
3. **양방향.** 새 기사가 기존 기사를 가리키면, 기존 기사 쪽에도 역방향 후보를 제안합니다. 사람이 승인한 쪽만 커밋합니다.
4. **화면에 합치기.** `related`에 있는 기사가 먼저 오고, 남은 자리를 1단계 점수로 채웁니다. 목록의 "공통: …" 자리에 `reason`을 보여 줍니다.

주의할 점입니다.

- LLM이 없는 slug를 지어낼 수 있으므로 검증이 꼭 필요합니다.
- 제안 결과를 그대로 커밋하지 않습니다. 기사 검수와 같은 기준으로 사람이 확인합니다.

## 어느 쪽을 먼저 할지

태그 레지스트리가 비용이 가장 적고 효과가 바로 보입니다. 그다음은 B입니다. 이미 기사 작성 파이프라인에 LLM이 있고, 이유 문장이 독자에게 가장 큰 차이를 만듭니다. A는 기사가 50개를 넘어 사람이 기존 기사를 다 기억하기 어려워질 때 도입합니다.
