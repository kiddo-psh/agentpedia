# 기사 작성 가이드

Agentpedia 기사를 쓰는 사람(사람이든 에이전트든)이 따르는 기준입니다.
**기계로 검사할 수 있는 규칙은 `npm run validate:content`가 강제**하고, 판단이 필요한 기준은 [리뷰 기준표](review-rubric.md)로 평가합니다.

---

## 1. 기사의 약속

독자는 기사를 다 읽었을 때 세 가지를 얻어야 합니다.

1. **누가, 언제, 무슨 맥락에서** 한 말인지 안다.
2. 그 생각이 **왜 중요한지** 이야기로 이해한다.
3. 키트를 실행하면 **내 레포에서 무엇이 바뀌는지** 정확히 안다.

## 2. 세 겹 구조

독자마다 원하는 깊이가 다릅니다. 같은 기사를 세 겹으로 씁니다.

| 겹 | 독자 | 위치 | 쓰는 법 |
|---|---|---|---|
| ① 30초 요약 | 훑어보는 사람 | frontmatter `brief` + `keyIdeas` | 사실만. 한 항목에 한 문장 |
| ② 본문 | 이해하고 납득하려는 사람 | MDX 본문 | 이야기(아래 3, 4장). 용어는 `<Term>` |
| ③ 원문과 적용 | 검증하고 실행하려는 사람 | `sources`, 키트 | 원문 링크·타임스탬프, 적용 키트 |

**`brief`** (새 기사는 필수). 각 140자 이하, 한 문장.

| 필드 | 쓸 내용 | 예 |
|---|---|---|
| `what` | 무슨 일이, 언제, 누구에게 | "2026년 10월, Postman 데스크톱이 사용자 동의 없이 Codex와 Claude Code에 플러그인을 설치했습니다." |
| `why` | 에이전트를 쓰는 개발자에게 왜 중요한가 | "에이전트 설정 폴더가 다른 앱이 몰래 고칠 수 있는 공격면이 됐습니다." |
| `action` | 지금 할 수 있는 일 (보통 키트가 하는 일) | "키트로 내 에이전트에 붙은 플러그인·훅·MCP를 점검합니다." |

원문 전체나 번역 전문은 싣지 않습니다(저작권). 원문은 링크로 보내고, 직접 인용은 아래 5장의 한도를 지킵니다.

## 3. 본문 구조

| 순서 | 내용 | 비고 |
|---|---|---|
| 도입 (장면) | 인물과 상황으로 시작. "2025년 6월, 샌프란시스코의 YC 행사장에서…" | 2~4문장. 핵심 주장을 미리 말하지 않는다 |
| 문제 | 독자가 겪는 문제나 통념을 꺼낸다 | "대부분의 개발자는 …라고 생각합니다" |
| 전환 | 인물이 다르게 보는 관점 | `<KeyIdea>` 1개 |
| 전개 | 근거와 예시를 2~4개 섹션으로 | 섹션마다 `##` 제목은 질문이나 주장으로 |
| 비교 | 이전 방식과 새 방식 | `<Compare>` |
| 적용 | 내 프로젝트에서 해볼 것 | `<Steps>`, `<TryIt>` |
| 맺음 | 한계와 반론, 언제 맞지 않는지 | 과장하지 않는다 |

## 4. 스토리텔링 규칙

- **장면으로 시작합니다.** 정의나 요약으로 시작하지 않습니다.
- **인물을 사람으로 보여줍니다.** 이름만 쓰지 말고, 어떤 일을 해 온 사람인지 한 문장으로 소개합니다.
- **긴장을 만듭니다.** "기존에는 이랬는데, 이 사람은 이렇게 본다"는 대비가 기사 전체에 흘러야 합니다.
- **한 섹션에 한 주장.** 섹션 제목만 읽어도 흐름이 이어져야 합니다.
- **문장은 짧게.** 한 문장에 한 생각. 존댓말(합니다체)로 씁니다.
- **과장하지 않습니다.** "혁명", "완전히 바꾼다" 같은 표현 대신 구체적인 변화를 씁니다.

문장 규칙은 ASD-STE100(간결 기술 영어)에서 한국어에 맞는 것만 빌려 옵니다. 이야기는 유지하고 모호함만 줄입니다.

- **한 문장에 한 생각.** 한 문장이 60자를 넘으면 나눌 수 있는지 봅니다.
- **한 개념에 한 용어.** "에이전트 도구", "코딩 에이전트", "하네스"를 섞어 쓰지 않습니다. 고른 용어는 끝까지 같게 씁니다.
- **능동태와 주어.** "~되어졌다", "~에 의해" 대신 누가 무엇을 했는지 씁니다.
- **지시문은 동사로 시작.** 키트와 `<Steps>`에서는 "확인합니다", "삭제하지 않습니다"처럼 명령을 분명히 합니다.

## 5. 출처와 시점

- 모든 사실은 frontmatter `sources`에 있는 출처로 뒷받침합니다. 출처 없는 주장은 쓰지 않습니다.
- 출처의 `publishedAt`은 **원문에서 직접 확인한 날짜**만 씁니다. 원문에서 직접 읽지 못했다면 `dateNote`에 어떻게 확인했는지 적습니다. 날짜가 없는 페이지(소개 페이지, 전사본)는 `publishedAt` 대신 `accessedAt`(열람일)을 쓰고, 열람일은 출처 시점에 넣지 않습니다.
- 본문에서 시점을 밝힙니다. "2026년 1월 스레드에서", "이 강연 당시(2025년 6월)에는"처럼 씁니다.
  AI 업계는 빠르게 바뀌므로, 독자가 **언제 기준의 이야기인지** 항상 알 수 있어야 합니다.
- 직접 인용은 `<Quote>`로만 합니다. 영상·팟캐스트·강연은 타임스탬프(`at`)가 필수입니다.
  원문 문장을 직접 확인하지 못했다면 인용하지 말고 의역합니다.
- 인용은 기사당 5개 이하, 하나에 2~3문장까지입니다.
- 2차 출처(요약 기사)만 확인했다면 그 사실을 본문이나 출처 목록에서 밝힙니다.

## 6. 인물과 사진

- 인물은 `content/people.yaml`에 한 번 등록하고, 기사에서는 `people: [id]`로 참조합니다.
- 사진은 **재사용 라이선스가 명확한 이미지만** 씁니다.
  - 허용: Wikimedia Commons의 CC BY / CC BY-SA / CC0 / 퍼블릭 도메인, 본인이 공개 사용을 허락한 프로필 이미지
  - 금지: 뉴스 사진, 출처 불명 이미지, 라이선스를 확인하지 못한 이미지
- 사진에는 `credit`, `license`, `sourceUrl`이 반드시 있어야 하며 페이지에 표시됩니다.
- 조건을 만족하는 사진이 없으면 사진을 비워 둡니다. 이니셜 아바타가 대신 나옵니다.

## 7. 용어집

- 용어는 `content/glossary.yaml`에 사이트 전체로 한 번 등록합니다. 같은 용어는 모든 기사에서 같은 뜻입니다.
- 항목: `id`, `term`(한국어 표기), `en`(영어 원어, 다를 때만), `definition`(200자 이하, 한두 문장, 처음 보는 개발자 기준).
- 본문에서 독자가 모를 수 있는 용어가 **처음 나올 때** `<Term id="mcp">MCP</Term>`로 감쌉니다. 두 번째부터는 감싸지 않습니다.
- 기사당 3~8개가 적당합니다. "API", "레포"처럼 대상 독자가 다 아는 말은 넣지 않습니다.
- 독자가 표시된 용어를 누르면 그 자리에 정의가 작은 창으로 뜹니다(모바일은 화면 아래). 용어는 본문 뒤 목록에도 모이고, MCP 응답에도 포함됩니다.

## 8. 적용 키트

키트는 독자의 레포를 바꿉니다. 그래서 **무엇을 하는지 실행 전에 알 수 있어야** 합니다.
frontmatter `apply`에 아래를 반드시 씁니다. 기사 페이지와 MCP `apply_article` 프롬프트에 그대로 표시됩니다.

| 필드 | 내용 | 예 |
|---|---|---|
| `goal` | 한 문장 목표 | "에이전트가 스스로 결과를 검증할 수 있는 명령을 갖추게 합니다" |
| `changes` | 바뀔 수 있는 파일과 내용 (2~5개) | "`CLAUDE.md`에 테스트 명령 추가" |
| `doesNotDo` | 하지 않는 일 (1~3개) | "기존 코드 로직은 수정하지 않습니다" |
| `fitsWhen` | 이런 프로젝트에 맞음 | "테스트나 빌드 명령이 있는 프로젝트" |
| `time` | 예상 소요 시간 | "15~30분" |

`kit/prompt.md`와 `kit/checklist.md`는 위 내용과 어긋나면 안 됩니다. `prompt.md`에는 다음을 꼭 포함합니다.

- 먼저 레포를 읽고 맞는지 판단하고, 맞지 않으면 멈추라는 지시
- 변경 전에 계획을 보여주고 승인을 받으라는 지시
- 추측한 명령을 쓰지 말고 실제로 실행해 확인하라는 지시

## 9. 형식 체크리스트 (자동 검사)

- [ ] frontmatter 스키마 통과 (`summary` 200자 이하, `keyIdeas` 1~7개, `brief` 각 140자 이하 등)
- [ ] `<Quote>`의 `source`가 `sources`에 있고, 시간 기반 출처에는 `at`이 있음
- [ ] 허용된 컴포넌트만 사용 (`KeyIdea`, `Quote`, `TryIt`, `Compare`, `Steps`, `Term`)
- [ ] `<Term id>`가 `content/glossary.yaml`에 있음
- [ ] `people`의 id가 `content/people.yaml`에 있음
- [ ] 사진이 있다면 `credit`, `license`, `sourceUrl`이 있음
- [ ] `apply` 필드가 모두 채워져 있고 `kit/prompt.md`가 있음
- [ ] 사람 검수 전까지 `draft: true`

## 10. 에이전트 워크플로로 쓰기

[`.claude/workflows/write-article.js`](../.claude/workflows/write-article.js)가 이 가이드를 여러 에이전트로 실행합니다.

1. **조사** (기사마다 1명): 1차 출처, 원문에서 확인한 날짜, 원문 그대로의 인용, 인물 정보와 라이선스가 확인된 사진
2. **인물 등록** (1명): `content/people.yaml`은 공유 파일이라 한 에이전트만 수정
3. **작성** (기사마다 1명): 조사 결과에 있는 사실만으로 이야기 구성, 키트 작성, 자동 검사 통과
4. **리뷰** (기사마다 3명, 서로 다른 관점): 팩트체커, 편집자, 키트 리뷰어가 [기준표](review-rubric.md)로 채점
5. **수정**: 4점 미만이나 반려 사유가 있으면 고치고 다시 리뷰 (최대 2회)

결과물은 모두 `draft: true`로 남고, 커밋과 초안 해제는 사람이 검수한 뒤에 합니다.
Claude Code에서 "write-article 워크플로를 실행해줘"라고 요청하고, 기사 목록을 넘기면 됩니다.

```json
[
  { "slug": "karpathy-software-3", "topic": "카파시의 Software 3.0 강연", "category": "people", "mode": "revise" },
  { "slug": "new-article-slug", "topic": "다룰 주제", "category": "trends", "sources": ["https://..."] }
]
```
