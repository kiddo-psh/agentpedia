# 기사 작성 가이드

Agentpedia 기사를 쓰는 사람(사람이든 에이전트든)이 따르는 기준입니다.
**기계로 검사할 수 있는 규칙은 `npm run validate:content`가 강제**하고, 판단이 필요한 기준은 [리뷰 기준표](review-rubric.md)로 평가합니다.

---

## 1. 기사의 약속

독자는 기사를 다 읽었을 때 세 가지를 얻어야 합니다.

1. **누가, 언제, 무슨 맥락에서** 한 말인지 안다.
2. 그 생각이 **왜 중요한지** 이야기로 이해한다.
3. 키트를 실행하면 **내 레포에서 무엇이 바뀌는지** 정확히 안다.

## 2. 구조

| 순서 | 내용 | 비고 |
|---|---|---|
| 도입 (장면) | 인물과 상황으로 시작. "2025년 6월, 샌프란시스코의 YC 행사장에서…" | 2~4문장. 핵심 주장을 미리 말하지 않는다 |
| 문제 | 독자가 겪는 문제나 통념을 꺼낸다 | "대부분의 개발자는 …라고 생각합니다" |
| 전환 | 인물이 다르게 보는 관점 | `<KeyIdea>` 1개 |
| 전개 | 근거와 예시를 2~4개 섹션으로 | 섹션마다 `##` 제목은 질문이나 주장으로 |
| 비교 | 이전 방식과 새 방식 | `<Compare>` |
| 적용 | 내 프로젝트에서 해볼 것 | `<Steps>`, `<TryIt>` |
| 맺음 | 한계와 반론, 언제 맞지 않는지 | 과장하지 않는다 |

## 3. 스토리텔링 규칙

- **장면으로 시작합니다.** 정의나 요약으로 시작하지 않습니다.
- **인물을 사람으로 보여줍니다.** 이름만 쓰지 말고, 어떤 일을 해 온 사람인지 한 문장으로 소개합니다.
- **긴장을 만듭니다.** "기존에는 이랬는데, 이 사람은 이렇게 본다"는 대비가 기사 전체에 흘러야 합니다.
- **한 섹션에 한 주장.** 섹션 제목만 읽어도 흐름이 이어져야 합니다.
- **문장은 짧게.** 한 문장에 한 생각. 존댓말(합니다체)로 씁니다.
- **과장하지 않습니다.** "혁명", "완전히 바꾼다" 같은 표현 대신 구체적인 변화를 씁니다.

## 4. 출처와 시점

- 모든 사실은 frontmatter `sources`에 있는 출처로 뒷받침합니다. 출처 없는 주장은 쓰지 않습니다.
- 출처의 `publishedAt`은 **원문에서 직접 확인한 날짜**만 씁니다. 추정했다면 `dateNote`에 근거를 적습니다.
- 본문에서 시점을 밝힙니다. "2026년 1월 스레드에서", "이 강연 당시(2025년 6월)에는"처럼 씁니다.
  AI 업계는 빠르게 바뀌므로, 독자가 **언제 기준의 이야기인지** 항상 알 수 있어야 합니다.
- 직접 인용은 `<Quote>`로만 합니다. 영상·팟캐스트·강연은 타임스탬프(`at`)가 필수입니다.
  원문 문장을 직접 확인하지 못했다면 인용하지 말고 의역합니다.
- 인용은 기사당 5개 이하, 하나에 2~3문장까지입니다.
- 2차 출처(요약 기사)만 확인했다면 그 사실을 본문이나 출처 목록에서 밝힙니다.

## 5. 인물과 사진

- 인물은 `content/people.yaml`에 한 번 등록하고, 기사에서는 `people: [id]`로 참조합니다.
- 사진은 **재사용 라이선스가 명확한 이미지만** 씁니다.
  - 허용: Wikimedia Commons의 CC BY / CC BY-SA / CC0 / 퍼블릭 도메인, 본인이 공개 사용을 허락한 프로필 이미지
  - 금지: 뉴스 사진, 출처 불명 이미지, 라이선스를 확인하지 못한 이미지
- 사진에는 `credit`, `license`, `sourceUrl`이 반드시 있어야 하며 페이지에 표시됩니다.
- 조건을 만족하는 사진이 없으면 사진을 비워 둡니다. 이니셜 아바타가 대신 나옵니다.

## 6. 적용 키트

키트는 독자의 레포를 바꿉니다. 그래서 **무엇을 하는지 실행 전에 알 수 있어야** 합니다.
frontmatter `apply`에 아래를 반드시 씁니다. 기사 페이지와 MCP `apply_article` 프롬프트에 그대로 표시됩니다.

| 필드 | 내용 | 예 |
|---|---|---|
| `goal` | 한 문장 목표 | "에이전트가 스스로 결과를 검증할 수 있는 명령을 갖추게 합니다" |
| `changes` | 바뀔 수 있는 파일과 내용 (2~5개) | "`CLAUDE.md`에 테스트 명령 추가" |
| `doesNotDo` | 하지 않는 일 (1~3개) | "기존 코드 로직은 수정하지 않습니다" |
| `fitsWhen` | 이런 프로젝트에 맞음 | "테스트나 빌드 명령이 있는 프로젝트" |
| `time` | 예상 소요 시간 | "15~30분" |

`kit/prompt.md`와 `kit/checklist.md`는 위 내용과 어긋나면 안 됩니다. `prompt.md`에는 다음을 꼭 포함합니다.

- 먼저 레포를 읽고 맞는지 판단하고, 맞지 않으면 멈추라는 지시
- 변경 전에 계획을 보여주고 승인을 받으라는 지시
- 추측한 명령을 쓰지 말고 실제로 실행해 확인하라는 지시

## 7. 형식 체크리스트 (자동 검사)

- [ ] frontmatter 스키마 통과 (`summary` 200자 이하, `keyIdeas` 1~7개 등)
- [ ] `<Quote>`의 `source`가 `sources`에 있고, 시간 기반 출처에는 `at`이 있음
- [ ] 허용된 컴포넌트만 사용 (`KeyIdea`, `Quote`, `TryIt`, `Compare`, `Steps`)
- [ ] `people`의 id가 `content/people.yaml`에 있음
- [ ] 사진이 있다면 `credit`, `license`, `sourceUrl`이 있음
- [ ] `apply` 필드가 모두 채워져 있고 `kit/prompt.md`가 있음
- [ ] 사람 검수 전까지 `draft: true`
