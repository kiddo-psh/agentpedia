2026년 9월 23일 Cursor 블로그에서 Jediah Katz, Connor O'Keefe, Calvin Yee는 장시간 에이전트 실행의 토큰 비용을 줄이려면, 프롬프트를 더 자세히 쓰기보다 <Term id="agent-harness">하네스</Term>가 매 턴 싣는 컨텍스트를 줄여야 한다고 썼습니다. 에이전트가 더 긴 일을 맡으면서 단계마다 컨텍스트가 이어지고, 그래서 요청을 어떻게 조립하느냐가 비용의 중심이 됐다는 이야기입니다. 이들은 하네스의 여러 층을 손본 뒤, 에이전트 품질을 유지한 채 사용자 토큰 비용이 7% 줄었다고 보고했습니다.

## 성능을 위해 지침과 도구를 더 싣는 습관과 반대다

에이전트가 자주 헛발질하면, 시스템 지침에 금지 문구를 더하고 도구 설명을 길게 늘리기 쉽습니다. 모델이 약할 때는 Cursor도 도구 사용·작업 관리·코드 변경 절차를 자세히 적었고, 긴 해시 덤프나 바이너리 출력, 이모지 같은 이상한 행동을 막는 문장도 많이 넣었다고 합니다. 그런데 모델이 나아지자, 도구가 무엇을 하는지만 짧게 적어도 대체로 따른다고 봤습니다. 모델 계열을 가로질러 같은 방향이었고, 시스템 프롬프트도 그에 맞춰 줄였다고 적습니다.

<Quote source="cursor-token-efficiency">
This was true across model families, allowing us to trim roughly 66% of our system prompt.
</Quote>

모델 계열을 가리지 않고 시스템 프롬프트를 약 66% 줄였다고 합니다. 금지·강제 문장을 길게 나열하던 때와 달리, 도구 동작만 정의해도 모델이 대체로 따랐다는 맥락입니다. 평가는 어려운 문제 위주의 eval만으로는 부족하고, 실제 사용자 트래픽에서 A/B로 하네스를 다듬는 일이 중요하다고도 적습니다.

<KeyIdea title="상시 컨텍스트가 비용의 중심입니다">
매 턴 다시 실리는 시스템 지침과 도구 정의는 하네스가 직접 통제하는 큰 지출입니다. 장시간 실행에서는 그 앞부분을 줄이고, 덜 쓰는 정의는 필요할 때만 붙이는 쪽이 비용과 맞닿습니다.
</KeyIdea>

## 저빈도 도구는 정의만 동적 컨텍스트로 옮긴다

시스템 프롬프트만이 아닙니다. 도구 정의도 매 턴 <Term id="static-context">고정 컨텍스트</Term>에 들어가며, 기능을 늘리는 동안 백그라운드 셸 감시·클라우드 서브에이전트·웹 접근처럼 정의가 크게 커졌다고 합니다. 중요한 도구라도, 각각이 필요한 대화는 전체의 20%가 되지 않았다고 적습니다. 예전에 <Term id="mcp">MCP</Term> 도구를 <Term id="dynamic-context">동적 컨텍스트</Term>로 옮겨 필요할 때만 로드했을 때, MCP를 호출한 세션에서는 총 토큰이 46.9% 줄었다고 합니다. 같은 기법을 내장 도구에도 적용했습니다.

어떤 도구를 고정에 남길지는 사용 빈도와, 처음부터 보여야 하는지로 A/B 했다고 합니다. 추적한 지표는 토큰·비용·지연·도구 호출 오류·전체 에이전트 사용량이었습니다. 읽기·검색·편집·셸처럼 고빈도 도구는 고정에 남겼습니다. 일부 모델이 호출을 지어내던 `ask_question`, Plan Mode의 `create_plan`처럼 제품 흐름에 꼭 필요한 것도 남겼습니다. 나머지는 필요할 때 로드합니다. 그 결과 고정 컨텍스트에 들어 있던 도구 설명 토큰이 60% 줄었다고 적습니다.

## 캐시가 먹히려면 앞부분이 안정적이어야 한다

요청 앞을 줄인 뒤에는, 남은 앞부분을 턴마다 재사용하는 <Term id="prompt-caching">프롬프트 캐싱</Term>을 손봤습니다. 매 턴 도구·시스템 지침·설정·대화가 다시 보내지고, 앞은 비슷하고 뒤 대화만 길어집니다. GPT-5.6 이전에는 캐시 경계가 최신 요청 기준으로 자동 정해져, 거의 안 바뀌는 도구·지침도 따로 재사용 표시하기 어려웠다고 합니다. GPT-5.6부터는 명시적 캐시 중단점을 둘 수 있어, 안정적인 층 뒤·늘어나는 대화 앞에 경계를 두었다고 적습니다.

경계만으로는 부족합니다. 접두 자체가 흔들리면 캐시가 빗나갑니다. 그래서 거의 안 바뀌는 내용만 도구·시스템 지침에 남기고, 스킬·서브에이전트·환경 정보처럼 요청마다 달라지는 설정은 캐시 경계 뒤 phantom user message(요청마다 달라지는 내용을 담는 가상 사용자 메시지)로 옮겼습니다. 이 변경으로 cold cache miss 비율이 20% 줄었다고 합니다.

파일 읽기 쪽도 손댔습니다. `Read` 도구가 줄마다 번호를 붙이면 줄당 약 3~5토큰이지만, 세션에서 수만 줄을 읽으면 합이 커집니다. 열 줄마다만 번호를 남겨도 인용은 충분했고, cache-read 토큰이 1.6% 줄었으며 품질 하락은 없었다고 적습니다.

## 서브에이전트는 쓰되 부추기지 않는다

긴 실행에서는 <Term id="subagent">서브에이전트</Term>에 일을 넘기면, 부모 대화 전체를 들고 가지 않아 토큰을 줄일 수 있습니다. 다만 컨텍스트를 공유하지 않으면 일을 겹치거나 이미 필요 없어진 작업을 이어 가는 조정 비용이 생깁니다. Cursor는 코드베이스 탐색에 서브에이전트를 강하게 쓰라는 지침을 없앴습니다. 학습 데이터와 사후 학습에 패턴이 충분히 들어와, 지침을 빼니 사용이 더 균형 잡혔다고 합니다. 서브에이전트 모델도 사용자나 하네스가 시킬 때만 다르게 고르도록 도구 인자를 조였습니다.

## 수치는 Cursor 자체 보고이며 로컬 복제에는 한계가 있다

위에 나온 비율은 모두 Cursor가 생산 트래픽과 A/B로 보고한 수치입니다. 원문에 독립 검증은 없습니다. 로컬 레포에서 같은 비율을 재현할 수는 없습니다. 프로바이더별 캐시 API, phantom user message, 내장 도구 동적 로딩은 제품 하네스 안에 있기 때문입니다. 그래도 옮길 수 있는 질문은 분명합니다. 매 턴 필수인 지침·도구 정의는 무엇인지, 드물게만 쓰는 MCP를 상시에 붙여 두었는지, 자주 바뀌는 환경 정보가 캐시될 접두를 흔드는지입니다. 같은 글은 별도 제품인 Grok Bot 하네스에도 이 배움을 옮기고 있다고만 짧게 덧붙입니다.
