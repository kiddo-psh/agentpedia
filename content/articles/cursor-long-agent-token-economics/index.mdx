에이전트를 오래 돌릴 때 토큰 비용을 줄이려면, 프롬프트를 더 자세히 쓰기보다 <Term id="agent-harness">하네스</Term>가 매 턴 싣는 컨텍스트를 줄여야 합니다. Cursor의 Jediah Katz, Connor O'Keefe, Calvin Yee가 2026년 9월 23일 Cursor 블로그에 쓴 결론입니다. 에이전트가 맡는 일이 길어지면서 컨텍스트가 단계마다 이어집니다. 그래서 요청을 어떻게 조립하느냐가 비용의 중심이 됐습니다. 세 사람은 하네스의 여러 층을 손본 뒤, 에이전트 품질은 유지하면서 사용자 토큰 비용을 7% 줄였다고 보고합니다.

## 성능을 위해 지침과 도구를 더 싣는 습관과 반대다

에이전트가 자주 헛발질하면 시스템 지침에 금지 문구를 더하고 도구 설명을 늘리기 쉽습니다. Cursor도 모델이 약할 때는 도구 사용, 작업 관리, 코드 변경 절차를 자세히 적었습니다. 긴 해시 덤프, 바이너리 출력, 이모지 같은 이상한 행동을 막는 문장도 많이 넣었습니다. 그런데 모델이 나아지자 도구가 하는 일만 짧게 적어도 대체로 따랐습니다. 모델 계열을 가리지 않고 같은 결과였습니다.

<Quote source="cursor-token-efficiency">
This was true across model families, allowing us to trim roughly 66% of our system prompt.
</Quote>

그 덕에 시스템 프롬프트를 약 66% 덜어 냈습니다. 평가는 어려운 문제 위주의 eval만으로는 부족합니다. 실제 사용자 트래픽에서 A/B 시험으로 하네스를 다듬는 일이 중요합니다.

<KeyIdea title="상시 컨텍스트가 비용의 중심입니다">
매 턴 다시 실리는 시스템 지침과 도구 정의는 하네스가 직접 통제하는 큰 지출입니다. 장시간 실행에서는 이 앞부분을 줄이고, 잘 안 쓰는 정의는 필요할 때만 붙여야 비용이 줄어듭니다.
</KeyIdea>

## 잘 안 쓰는 도구는 정의를 동적 컨텍스트로 옮긴다

시스템 프롬프트만 문제가 아닙니다. 도구 정의도 매 턴 <Term id="static-context">고정 컨텍스트</Term>에 들어갑니다. 기능을 늘리면서 백그라운드 셸 감시, 클라우드 서브에이전트, 웹 접근 같은 정의가 크게 불었습니다. 중요한 도구라도 그 도구가 필요한 대화는 전체의 20%가 안 됐습니다. Cursor는 예전에 <Term id="mcp">MCP</Term> 도구를 <Term id="dynamic-context">동적 컨텍스트</Term>로 옮겨 필요할 때만 불러온 적이 있습니다. 그때 MCP를 호출한 세션에서 총 토큰이 46.9% 줄었습니다. 이번에는 같은 기법을 내장 도구에 적용했습니다.

어떤 도구를 고정 컨텍스트에 남길지는 A/B 시험으로 정했습니다. 기준은 사용 빈도와, 처음부터 보여야 하는 도구인지였습니다. 추적한 지표는 토큰, 비용, 지연, 도구 호출 오류, 전체 에이전트 사용량입니다. 읽기·검색·편집·셸처럼 자주 쓰는 도구는 고정에 남겼습니다. 제품 흐름에 꼭 필요한 도구도 남겼습니다. 일부 모델이 호출을 지어내던 `ask_question`, Plan Mode의 `create_plan`이 그렇습니다. 나머지는 필요할 때 불러옵니다. 그 결과 고정 컨텍스트에 있던 도구 설명 토큰이 60% 줄었습니다.

## 캐시를 살리려면 앞부분이 바뀌지 않아야 한다

요청 앞부분을 줄인 뒤에는 <Term id="prompt-caching">프롬프트 캐싱</Term>을 손봤습니다. 남은 앞부분을 턴마다 재사용하는 기능입니다. 하네스는 매 턴 도구, 시스템 지침, 설정, 대화를 다시 보냅니다. 앞부분은 비슷하고 뒤의 대화만 길어집니다. GPT-5.6 이전에는 캐시 경계가 최신 요청을 기준으로 자동으로 정해졌습니다. 그래서 거의 바뀌지 않는 도구와 지침도 따로 재사용 표시를 하기 어려웠습니다. GPT-5.6부터는 캐시 중단점을 직접 지정할 수 있어, 안정된 층 뒤와 늘어나는 대화 앞 사이에 경계를 두었습니다.

경계만으로는 부족합니다. 앞부분이 흔들리면 캐시가 빗나갑니다. 그래서 거의 바뀌지 않는 내용만 도구와 시스템 지침에 남겼습니다. 스킬, 서브에이전트, 환경 정보처럼 요청마다 달라지는 설정은 캐시 경계 뒤의 phantom user message로 옮겼습니다. 요청마다 바뀌는 내용을 담는 가상 사용자 메시지입니다. 이 변경으로 cold cache miss 비율이 20% 줄었습니다.

파일 읽기도 손봤습니다. `Read` 도구가 줄마다 번호를 붙이면 줄당 약 3~5토큰이 듭니다. 한 세션에서 수만 줄을 읽으면 합이 커집니다. 열 줄마다만 번호를 남겨도 인용에는 충분했습니다. cache-read 토큰은 1.6% 줄었고, 품질은 떨어지지 않았습니다.

## 서브에이전트는 쓰되 부추기지 않는다

긴 실행에서는 <Term id="subagent">서브에이전트</Term>에 일을 넘기면 토큰을 줄일 수 있습니다. 부모 대화 전체를 들고 가지 않기 때문입니다. 다만 컨텍스트를 공유하지 않아 조정 비용이 생깁니다. 일이 겹치거나, 이미 필요 없어진 작업을 이어 가기도 합니다. Cursor는 코드베이스를 탐색할 때 서브에이전트를 적극 쓰라는 지침을 없앴습니다. 학습 데이터와 사후 학습에 이 패턴이 충분히 들어 있어서, 지침을 빼자 사용이 더 균형 잡혔습니다. 서브에이전트 모델도 사용자나 하네스가 시킬 때만 다르게 고르도록 도구 인자를 좁혔습니다.

## 수치는 Cursor 자체 보고이고, 로컬 재현에는 한계가 있다

위 비율은 모두 Cursor가 실제 사용자 트래픽과 A/B 시험으로 보고한 값입니다. 독립 검증은 없습니다. 로컬 저장소에서는 같은 비율을 재현할 수 없습니다. 프로바이더별 캐시 API, phantom user message, 내장 도구 동적 로딩이 모두 제품 하네스 안에 있기 때문입니다. 그래도 옮겨 올 질문은 분명합니다.

- 매 턴 꼭 필요한 지침과 도구 정의는 무엇인가?
- 드물게 쓰는 MCP를 늘 붙여 두고 있지 않은가?
- 자주 바뀌는 환경 정보가 캐시될 앞부분을 흔들고 있지 않은가?

Cursor는 별도 제품인 Grok Bot 하네스에도 이 배움을 옮기고 있다고 짧게 덧붙입니다.
