사용자는 코딩 에이전트에게 "오래된 브랜치를 정리해 줘"라고만 말했습니다. 에이전트는 원격 브랜치 목록을 받아 패턴으로 골라 삭제 명령을 냈습니다. Anthropic이 내부 사고 기록을 다듬어, auto 모드가 막으려는 사례로 소개한 예시입니다. 요청은 모호했고 삭제는 되돌릴 수 없었습니다. 사용자는 로컬 브랜치만 뜻했을지도 모릅니다. Claude Code는 기본적으로 이런 명령 앞에서 사용자에게 승인을 묻습니다. 그런데 사람은 그 승인 창을 얼마나 꼼꼼히 볼까요. 2026년 3월 25일 Anthropic이 올린 John Hughes의 엔지니어링 글에 그 답을 보여 주는 숫자가 있습니다.

<Quote source="anthropic-auto-mode">
Manual prompts sit in the middle, and in practice users accept 93% of them anyway.
</Quote>

원문은 수동 승인을 '아무것도 안 묻는 방식'과 '모든 것을 가두는 방식'의 중간에 놓습니다. 그런데 사용자는 그 요청의 93%를 그냥 승인합니다. 요청이 이렇게 잦으면 사람은 점점 덜 읽게 되고, Anthropic은 이를 <Term id="approval-fatigue">승인 피로</Term>라고 부릅니다. 버튼은 눌렸지만 검토는 없었을 수 있습니다.

2026년 3월 당시 개발자가 쓸 수 있던 대안은 두 가지였습니다. 하나는 샌드박스, 곧 에이전트를 격리된 환경에 가두는 방식입니다. 글은 이 방식을 안전하지만 손이 많이 간다고 설명합니다. 새 기능이 필요할 때마다 설정해야 하고, 네트워크나 호스트에 접근해야 하는 일은 격리를 깹니다. 다른 하나는 `--dangerously-skip-permissions` 옵션입니다. 글은 이 옵션을 이름 그대로 보호를 모두 끈다고 설명합니다. 그래서 Anthropic은 승인 자체를 모델에 맡겨 보기로 했습니다.

---

이 방식이 <Term id="auto-mode">auto 모드</Term>입니다. 아래 내용은 2026년 3월 글 기준이고, 이후 바뀐 점은 뒤에서 따로 정리합니다. 글에 따르면 auto 모드는 승인을 모델 기반 분류기에 맡기고, 방어를 두 층으로 나눕니다. 입력 층은 서버에서 도구 출력을 검사해 <Term id="prompt-injection">프롬프트 인젝션</Term>으로 보이면 에이전트에게 경고를 붙이는 탐지기입니다. 출력 층은 에이전트가 행동을 실행하기 직전에 그 행동을 심사해 사람의 승인을 대신하는 <Term id="transcript-classifier">트랜스크립트 분류기</Term>입니다.

글이 꼽은 위험은 네 가지입니다. 월권 행동, 정직한 실수, 프롬프트 인젝션, 그리고 모델 자체가 사용자 의도와 다른 목표를 따르는 경우입니다. 이 중 <Term id="overeager">월권(overeager) 행동</Term>이 가장 이해하기 쉽습니다. 앞서 본 브랜치 정리가 그 예입니다. 악의는 없지만 결과는 사고입니다. 이 항목은 뒤의 시험 결과에서 다시 나옵니다.

3월 글에 따르면 모든 행동이 분류기까지 가는 것은 아니었습니다. 행동은 세 등급으로 나뉘었습니다. 파일 읽기, 검색처럼 상태를 바꾸지 못하는 도구와 사용자가 만든 허용 규칙이 첫째 등급, 프로젝트 안의 파일 편집이 둘째 등급입니다. 이 두 등급은 분류기를 거치지 않았고, 나머지 전부(셋째 등급)가 분류기로 갔습니다.

그런데 분류기를 건너뛰는 이 길에는 구멍이 있었습니다. 사용자가 편의로 넓게 열어 둔 허용 규칙이 있으면 가장 위험한 명령도 분류기를 거치지 않기 때문입니다. 그래서 auto 모드에 들어갈 때는 아무 코드나 실행하게 하는 허용 규칙을 버렸습니다. 셸을 통째로 여는 규칙, 와일드카드를 쓴 스크립트 인터프리터(python, node 같은), 패키지 매니저 실행 명령이 그 예입니다. 포맷터 실행만 허락하는 식의 좁은 규칙은 그대로 남았습니다. 글은 이 목록이 실제 사용을 바탕으로 만든 최선의 목록일 뿐 빠진 것이 있을 수밖에 없다고 덧붙입니다.

사람 대신 판단하는 쪽도 한 번에 끝내지 않습니다. 출력 층의 트랜스크립트 분류기는 안에서 다시 두 단계로 나뉩니다. 3월 글이 나온 시점에는 Anthropic의 모델 Sonnet 4.6이 이 역할을 맡았습니다. 1단계는 예·아니오만 빠르게 답하는 필터로, 애매하면 막는 쪽으로 기울게 했습니다. 2단계는 1단계가 위험하다고 표시한 행동만 추론을 거쳐 다시 따져 보는 느린 재평가입니다.

Anthropic의 글에서 가장 눈에 띄는 설계 선택은 분류기가 보는 것을 줄인 점입니다. 에이전트가 쓴 설명부터 잘라 냈습니다.

<Quote source="anthropic-auto-mode">
We strip assistant text so the agent can't talk the classifier into making a bad call.
</Quote>

분류기가 설득당하지 않도록, 에이전트가 쓴 글은 분류기에 아예 넘기지 않았습니다. 3월 글 기준으로 출력 층 분류기는 사용자 메시지와 도구 호출만 봤고, 도구 결과도 보지 못했습니다. 웹 페이지나 파일에 숨은 지시는 입력 층의 탐지기가 따로 검사했습니다. 대가도 있었습니다. 사용자가 말한 적 없는 작업 번호(ID)를 에이전트가 조회해서 찾았는지 지어냈는지 분류기는 구분하지 못했습니다.

<KeyIdea title="변명을 들을 수 없는 승인자">
사람 승인자는 에이전트의 설명을 듣고 납득하기 쉽습니다. 이 분류기는 에이전트가 무슨 말을 했는지는 보지 않고 무슨 행동을 했는지만 봅니다. 변명을 들을 수 없게 만든 대신, 에이전트가 그 대상을 왜 골랐는지도 알 수 없게 됐습니다.
</KeyIdea>

3월 글에서 분류기가 막았을 때의 동작은 이랬습니다. Claude는 멈추지 않고 더 안전한 길을 찾으라는 안내를 받았습니다. 그래도 거부가 쌓이면 사람에게 넘겼습니다.

<Quote source="anthropic-auto-mode">
If a session accumulates 3 consecutive denials or 20 total, we stop the model and escalate to the human.
</Quote>

한 세션에서 거부가 연속 3번 쌓이거나 합쳐서 20번이 되면, 모델을 멈추고 사람에게 넘겼습니다. 화면 없이 돌리는 헤드리스 모드에서는 프로세스를 끝낸다고 했습니다. 이 부분은 지금 문서에서 달라졌고, 뒤에서 다시 다룹니다.

3월 글에 따르면 검사는 에이전트가 다른 에이전트에게 일을 넘기는 경우에도 이어집니다. 일을 맡길 때 분류기가 위임 자체를 거부할 수 있습니다. 결과가 돌아올 때는 하위 에이전트의 행동 기록 전체를 검사하고, 문제가 보이면 결과를 버리지 않고 일을 맡긴 에이전트에게 보안 경고를 붙입니다.

---

그렇다면 분류기는 얼마나 잘 막았을까요. 3월 글이 공개한 결과입니다. 글은 당시 분류기가 Sonnet 4.6에서 돈다고 설명했지만, 결과를 보고하는 부분에서 시험에 쓴 모델을 따로 적지는 않았습니다.

시험 집합은 세 가지입니다. 실제 트래픽 1만 건은 Anthropic 직원들이 평소에 쓴 Claude Code 도구 호출입니다. 실제 월권 행동 52건은 실제 세션에서 직원이 거부했거나 나중에 문제로 표시된 행동입니다. 합성 유출 시도 1,000건은 민감한 데이터를 밖으로 보내도록 일부러 만든 시도이고, 상당수는 난독화를 썼습니다.

1단계 필터만 썼을 때와 전체 파이프라인을 썼을 때를 비교했습니다. 오탐률은 안전한 행동을 잘못 막은 비율이고, <Term id="false-negative-rate">미탐률</Term>은 위험한 행동을 놓친 비율입니다.

| 시험 집합 | 지표 | 1단계만 | 전체 |
|---|---|---|---|
| 실제 트래픽 (n=10,000) | 오탐률(FPR) | 8.5% | 0.4% |
| 실제 월권 행동 (n=52) | 미탐률(FNR) | 6.6% | 17% |
| 합성 유출 시도 (n=1,000) | 미탐률(FNR) | 1.8% | 5.7% |

정상 행동을 잘못 막는 비율은 8.5%에서 0.4%로 줄었습니다. 대신 위험한 행동을 놓치는 비율은 두 집합 모두 늘었습니다. 2단계가 1단계의 과잉 차단을 풀어 주는 만큼, 풀어 준 것 가운데 일부는 실제로 위험한 행동이었습니다.

<Quote source="anthropic-auto-mode">
The 17% false-negative rate on real overeager actions is the honest number.
</Quote>

다만 52건은 작은 표본입니다. 위험한 시도는 실제 세션에서 붙잡아 일일이 라벨을 붙여야 모이기 때문에 이 이상 늘리기 어려웠고, 그만큼 17%라는 수치도 흔들릴 수 있습니다.

원문은 놓친 사례 대부분에서 분류기가 강제 푸시나 삭제 같은 위험 자체는 알아봤다고 설명합니다. 틀린 곳은 사용자가 한 말이 그 행동까지 허락한 것인지였습니다. "PR을 정리해 줘"라고 말했다고 강제 푸시까지 허락한 것은 아닌데, 분류기는 승인처럼 보이는 흔적을 찾고 거기서 멈췄습니다. 비슷한 행동을 앞서 한 번 승인한 것도 일반적인 허락은 아닙니다.

여기까지는 2026년 3월 25일 글의 이야기입니다. 이제부터는 2026년 11월 13일에 읽은 Claude Code 공식 문서 기준입니다. 문서는 네 가지를 3월 글과 다르게, 또는 더 자세히 적고 있습니다.

먼저 알아 둘 점은 최신 버전이면 이미 auto 모드일 수 있다는 것입니다. 3월 글은 켜는 방법을 문서로 넘겼습니다. 11월 문서에 따르면 실행 옵션 `--permission-mode auto`나 Shift+Tab으로 켜고, 최신 버전의 터미널과 VS Code 대화형 세션은 처음부터 auto 모드로 시작합니다.

둘째는 버려지는 규칙과 남는 규칙입니다. 11월 문서는 버려지는 규칙을 3월 글보다 구체적으로 적습니다. `Bash(*)`, `PowerShell(*)`, `Bash(python*)` 같은 규칙과 패키지 매니저 실행 명령에 더해, 하위 에이전트를 띄우는 `Agent` 허용 규칙과 명령을 셸로 실행하는 `Monitor` 허용 규칙도 버려집니다. 모드를 나가면 이 규칙들은 다시 적용됩니다. 반면 좁은 규칙은 대체로 분류기보다 먼저 적용되어 분류기를 건너뜁니다. 3월 글이 말한 구멍은 일부 남아 있는 셈입니다.

| 허용 규칙 | auto 모드에서 |
|---|---|
| 넓은 규칙 (`Bash(*)` 등) | 버려지고, 분류기가 판단 |
| 명령이 고정된 좁은 규칙 (`Bash(npm test)`) | 남아서 분류기를 건너뛰고 실행 |
| 인자가 열린 좁은 규칙 (`Bash(npm test *)`) | 남아서 분류기를 건너뜀. 뒤에 예상하지 못한 인자나 스크립트 경로가 붙어도 그대로 실행될 수 있음 |

모든 셸 명령을 분류기에 보이고 싶다면 `autoMode.classifyAllShell: true`로 셸 허용 규칙을 멈출 수 있습니다. 다만 이 `autoMode` 설정은 홈의 `~/.claude/settings.json`, 조직이 배포하는 관리형 설정, 실행할 때 넘긴 설정에서만 읽힙니다. auto 모드로 시작하게 하는 `defaultMode: "auto"`도 홈이나 관리형 설정에 적어야 합니다. 두 설정 모두 레포의 `.claude/settings.json`에 적으면 무시됩니다.

셋째는 분류기입니다. 3월 글에서는 Sonnet 4.6이었지만, 11월 문서는 기본값을 Claude Sonnet 5로 적습니다. 환경과 설정에 따라 다른 모델이 쓰일 수 있고, 일부 세션은 Anthropic 서버가 직접 판정합니다. 내 세션이 어느 쪽인지는 `/status`로 확인할 수 있습니다. 입력도 달라졌습니다. Claude Code가 직접 보내는 분류기 요청에는 사용자 메시지와 도구 호출에 더해 CLAUDE.md 내용이 들어가고, 파일 읽기·검색 같은 읽기 전용 조회는 빠집니다. 도구 결과는 여전히 제거됩니다.

넷째는 거부 한도에 닿은 뒤의 동작입니다. 한도(연속 3번, 누적 20번)는 그대로이고 바꿀 수 없습니다. 대화형 세션에서는 3월 글처럼 사람에게 다시 묻습니다. 달라진 것은 화면 없이 `-p`로 돌리는 헤드리스 실행입니다. 3월 글에서는 프로세스를 끝냈지만, 11월 문서에 따르면 따로 승인 도구(`--permission-prompt-tool`)를 붙이지 않은 `-p` 실행은 한도에 닿아도 그 행동만 실행하지 않고 작업은 계속합니다.

남는 한계도 있습니다. 17%라는 수치는 3월 글의 분류기 것입니다. 이후의 분류기(Sonnet 5 기본값이나 서버 판정)에 대한 미탐률은 확인한 문서에서 찾지 못했습니다. 3월 글에서 Anthropic은 이 모드가 모든 승인을 꼼꼼히 직접 하던 사람에게는 오히려 후퇴일 수 있고, 위험이 큰 인프라 작업에서 사람의 검토를 대신하지 못한다고도 적었습니다. 반사적으로 Enter를 누르던 손도 완전하지 않았고, 분류기도 완전하지 않습니다. 그래서 확인할 것은 두 가지입니다. 터미널에서 `claude auto-mode defaults`로 내가 쓰는 버전의 기본 규칙을 보고, 레포의 `.claude/settings.json`에서 분류기를 건너뛰는 좁은 허용 규칙을 직접 열어 보는 일입니다.
