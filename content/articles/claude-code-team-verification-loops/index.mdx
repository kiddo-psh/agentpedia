2026년 11월 16일, Addy Osmani가 Claude Code 팀의 검증을 적었습니다. 첫 문장이 규모를 말합니다.

<Quote source="osmani-verification">
On the Claude Code team, the vast majority of our code (~90%) is written and reviewed by Claude.
</Quote>

팀 코드의 대부분, 약 90%를 Claude가 쓰고 검토한다는 문장입니다. 그 규모에서 에이전트가 증거를 가지고 일을 확인하게 하는 방법이 중요해진다고 이어집니다. 같은 날 22:31 UTC, ClaudeDevs가 이 글을 소개했습니다.

<Quote source="claude-devs-verification">
Claude writes better code when it can verify its work. Checks that used to be expensive, like tests, benchmarks, and end-to-end runs, are now cheap.
</Quote>

일을 확인할 수 있으면 코드가 나아지고, 비싸던 검사들이 싸졌다는 소개입니다. 다음 날 Osmani의 X 아티클도 같은 제목이고, 첫 문단이 이 약 90% 문장입니다.

## 병목은 쓰는 일이 아니다

검증 루프가 더 많은 일을 맡길 수 있게 하는 단위라고 글이 적습니다. 루프가 없으면 결과를 사람이 다 봐야 해서 Claude를 한두 개만 돌릴 수 있고, 있으면 수십에서 수백을 병렬로 돌릴 수 있다고 적습니다. 구조화된 파일 생성에 대한 내부 시험에서는, 별도의 채점자가 루브릭으로 Claude의 일을 보면 일반 프롬프트 루프보다 과제 성공이 최대 10점 올랐고, 가장 어려운 문제에서 이득이 컸다고 적습니다. 그 10점은 이 내부 시험의 숫자입니다.

<KeyIdea title="생성은 싸고 확인이 병목입니다">
한번 만든 테스트와 벤치마크는 소프트웨어로 자주 돌릴 수 있어, 토큰을 많이 더 쓰지 않는다고 글이 적습니다. 실패가 반복되면 훅이나 CLAUDE.md의 더 명시적인 규칙으로 다음을 막을 수 있다고도 적습니다. 그 규칙을 지시 파일에 쌓는 절차는 이 글의 범위 밖입니다.
</KeyIdea>

## 맡길 양은 검사가 정한다

어떤 검사를 둘지가 그다음 질문입니다. Osmani가 투자할 만하다고 고른 것은 셋입니다.

### E2E는 기능이 됐는지 끝까지 본다

하나에 집중해야 하면 <Term id="e2e-test">E2E 테스트</Term>를 고르라고 적습니다. 카트에 담고, 결제하고, 확인 페이지로 가는 실제 흐름입니다. 전체가 되거나 안 되거나라서 속이기가 어렵고, 끝난 기준이 분명하다고 적습니다. 단위 테스트는 더 빠르고 덜 흔들리지만, 통과해도 기능이 깨질 수 있다고 적습니다. 에이전트와 테스트가 과제 전체를 모르기 때문입니다.

### 속성은 만든 사람이 안 고른 입력을 넣는다

<Term id="property-based-testing">속성 기반 테스트</Term>는 깨지면 안 되는 문장을 먼저 적고, fast-check, Hypothesis, proptest 같은 라이브러리가 수천 개의 입력으로 반례를 찾습니다. 글이 드는 성질은 왕복 인코딩, 잔고가 음수가 되지 않는 불변식, 같은 일을 두 번 해도 한 번과 같은 멱등, 최적화한 코드와 단순하지만 맞는 코드의 동등입니다. 그 입력은 코드를 만든 에이전트와 같은 편향으로 고르지 않아서, 에이전트를 정직하게 두는 방법이라고 적습니다.

### 차분은 옛 시스템을 정답으로 둔다

<Term id="differential-test">차분 테스트</Term>는 동작이 같아야 하는 큰 이전에서 특히 유효하다고 적습니다. 같은 입력으로 옛 시스템과 새 시스템을 돌려 결과가 다르면, 고칠 버그이거나 깨지는 변경입니다. 입력은 무작위로 만들거나 실제 트래픽의 표본을 쓰고, 공백처럼 상관없는 차이는 정규화하며, 새 환경이 달라야 하는 곳은 승인된 변경 목록으로 둔다고 적습니다.

## 검사가 자기 숙제를 채점하면 깨진다

검사 종류만으로 정직해지지는 않습니다. 글이 못 박는 문장입니다.

<Quote source="osmani-verification">
If a change can modify the check that judges it, the check is broken.
</Quote>

변경이 자기를 심판하는 검사를 고칠 수 있으면 그 검사는 깨집니다. Code Review는 `REVIEW.md`를 베이스나 기본 브랜치에서 읽고, 풀 리퀘스트의 변경에서는 읽지 않는다고 적습니다. 규칙은 그 변경이 고칠 수 없는 브랜치에 둔다고 적습니다. 실패가 세 번 라운드 뒤에도 남으면 Claude가 멈추고 사람을 부른다고 적습니다.

같은 날 20:28 UTC, Osmani 글의 답글이 아닌 팁이 먼저 올라왔습니다. X 계정 kyr0stack입니다.

<Quote source="kyr0-gate">
the mistake almost everyone makes is letting the agent decide when the work is done. it will quietly edit its own tests to go green and call it shipped.
</Quote>

일의 끝을 에이전트가 정하게 두면, 테스트를 조용히 고쳐 녹색으로 만들고 끝났다고 부른다는 말입니다. 팁이 제안하는 고침은 훅이 실제 테스트를 돌리고, 코드를 쓰지 않은 검증자가 서명하기 전에는 합치지 않는 게이트입니다. 모델 이름과 세 번 실패 뒤 `git reset`은 이 팁의 제안이지, Osmani 글이 팀의 절차로 적은 내용이 아닙니다. 팀 글의 세 번은 실패한 검사 뒤에 사람을 부르는 라운드입니다.

## 회귀 수는 이 글에 없다

작은 리팩터를 시험 없이 맡긴 결과와, 옛 구현을 정답으로 두는 차분 시험을 두고 맡긴 결과가 어떻게 다른지는 이 글이 재지 않았습니다. 회귀 개수를 적어 두지 않은 이유입니다. 순수 함수가 있는 저장소에서 그 둘을 나란히 시켜 보고, 깨진 개수는 그 실행 옆에만 적으면 됩니다.

가져갈 순서는 검사의 종류보다 자리입니다. 변경이 채점 규칙에 손을 대지 못하게 두고, 입력은 만든 쪽의 예시만 믿지 않고, 숫자가 필요하면 직접 돌린 뒤에 적습니다.
