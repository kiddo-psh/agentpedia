코드를 거의 읽지 않고도 개발합니다. Peter Steinberger가 2025년 12월 28일 블로그에 쓴 방식입니다. Steinberger는 PSPDFKit 창업자입니다. 글을 쓰는 동안 프로젝트 네 곳에서 codex가 리팩터링을 돌렸습니다. 하나당 1~2시간이 걸렸습니다. 그동안 Steinberger는 코드 대신 글을 썼습니다.

## 은퇴했던 창업자가 AI 때문에 다시 개발을 시작했다

Steinberger는 PSPDFKit를 창업했습니다. 지금은 Nutrient입니다. 외부 투자 없이 키우고 매각했습니다. 그 뒤 은퇴했습니다. AI 때문에 다시 개발을 시작했습니다. 소개 페이지에 적은 내용입니다. 이 글에서는 보통 혼자 일한다고 밝힙니다. OpenAI 합류는 이 글보다 뒤입니다. 2026년 2월입니다.

## 구현을 맡겨도 개발 감각은 사라지지 않는다

코드를 직접 써야 나쁜 아키텍처를 알아챈다고 믿는 개발자가 많습니다. 구현을 에이전트에 맡기면 그 감각을 잃는다는 걱정도 있습니다. Steinberger는 글을 쓰기 몇 주 전에 이 주장을 봤습니다. 강하게 반대합니다.

근거는 경험입니다. 에이전트와 오래 일하면 작업 시간이 감으로 옵니다. codex가 한 번에 해결하지 못하면 곧 이상하다고 느낍니다. 감각은 그대로입니다. 쓰이는 곳만 달라졌습니다. Steinberger가 보기에 바뀐 것은 병목의 위치입니다.

## 만들 수 있는 양은 추론 시간과 고민이 정한다

<KeyIdea title="병목이 추론 시간으로 옮겨 갔습니다">
2025년 5월에는 한 번에 동작하는 코드가 놀라웠습니다. 12월에는 당연해졌습니다. 속도는 다음 시간에 달려 있습니다.

- 모델이 생각하는 시간
- 사람이 고민하는 시간
</KeyIdea>

<Quote source="post">
The amount of software I can create is now mostly limited by inference time and hard thinking.
</Quote>


모든 소프트웨어에 깊은 고민이 필요하지는 않습니다. 대부분의 앱이 하는 일은 다음입니다.

- 데이터를 다른 형태로 바꿉니다.
- 저장합니다.
- 보여 줍니다.

이 변화를 확실히 느낀 건 GPT 5부터입니다. 소프트웨어를 공장처럼 빨리 만들기 시작한 계기입니다. GPT 5 이후 Steinberger는 코드를 거의 읽지 않습니다. 에이전트가 일하는 과정을 지켜봅니다. 가끔 중요한 부분만 엽니다.

## 한 줄은 에이전트가 맡고 구조는 사람이 맡는다

손에서 놓지 않는 것이 있습니다. 어떤 컴포넌트가 어디 있는지 압니다. 구조도 압니다. 전체 시스템 설계도 압니다. 한 줄 한 줄은 에이전트가 맡습니다. 전체 구조는 사람이 책임집니다.

사람이 직접 정하는 일도 따로 있습니다.

<Quote source="post">
The important decisions these days are language/ecosystem and dependencies.
</Quote>


2025년 12월 Steinberger는 웹에 TypeScript를 씁니다. <Term id="cli">CLI</Term>에는 Go를 씁니다. macOS 기능이 필요하면 Swift를 씁니다. UI가 있어도 Swift를 씁니다. Go는 몇 달 전만 해도 고려하지 않던 언어입니다. 고른 이유는 다음입니다.

- 에이전트가 Go를 잘 씁니다.
- 타입 시스템이 단순합니다.
- 린트가 빠릅니다.

Mac과 iOS 개발에서 Xcode는 크게 필요 없습니다. xcodeproj 파일도 쓰지 않습니다. codex가 iOS 앱을 실행합니다. 시뮬레이터도 다룹니다.

어려운 일이 없어진 것은 아닙니다. Steinberger가 여전히 어렵다고 보는 일은 둘입니다.

- 의존성과 프레임워크를 고릅니다. 관리가 잘 되는지 봅니다. 피어 의존성도 봅니다. 에이전트가 알 만큼 널리 쓰이는지도 봅니다.
- 시스템 설계를 정합니다. 웹소켓을 쓸지 정합니다. 서버와 클라이언트를 어떻게 나눌지 정합니다. 데이터가 어떻게 흐를지 정합니다.

## CLI로 시작하면 에이전트가 결과를 확인한다

언어와 의존성을 정한 뒤 결과를 직접 확인할 방법을 만듭니다.

<Quote source="post">
The simplest form is text, so by default, whatever I wanna build, it starts as CLI. Agents can call it directly and verify output - closing the loop.
</Quote>


closing the loop는 사람 없이 끝내는 과정입니다. 에이전트가 다음을 합니다.

- 만듭니다.
- 실행합니다.
- 결과를 확인합니다.

예는 YouTube 영상을 요약하는 크롬 확장입니다. 먼저 summarize라는 CLI로 핵심을 완성했습니다. 그다음 확장 전체를 하루 만에 만들었습니다. 글의 다른 곳에서도 모델과 CLI부터 시작하라고 권합니다.

## 느려도 한 번에 끝내는 codex를 기본으로 쓴다

추론 시간이 병목이면 빠른 모델이 나아 보입니다. Steinberger의 경험은 반대였습니다. codex는 코드를 쓰기 전에 10~15분 동안 파일을 읽기도 합니다. Opus는 더 서두릅니다. 작은 수정에는 좋습니다. 큰 기능에는 덜 맞습니다. 리팩터링에도 덜 맞습니다. 같은 작업에 codex가 4배 오래 걸려도 다시 고칠 일이 없습니다. 그래서 결국 더 빠릅니다.

모드를 고르는 데 시간을 쓰지 않습니다. 기본 모델은 gpt-5.2-codex입니다. 거의 모든 작업을 high로 돌립니다. <Term id="reasoning-effort">추론 수준</Term>입니다. xhigh는 훨씬 느리기만 합니다. 나은 점이 거의 없습니다. GPT 5.2와 codex는 충분히 비슷합니다. 모델을 바꿀 이유도 없습니다. Opus는 컴퓨터 자동화에 씁니다. 개인 AI 비서에도 씁니다. 글 끝에 `~/.codex/config.toml`도 공개했습니다.

Steinberger는 VibeTunnel 멀티플렉서의 핵심을 옮겨 보려 한 적이 있습니다. TypeScript에서 다음 언어로입니다.

- Rust
- Go
- zig

그때 모델들은 번번이 실패했습니다. 이번에는 포워딩 시스템 전체를 zig로 바꾸라고 했습니다. 프롬프트는 두 문장이었습니다. codex에 줬습니다. codex는 5시간 넘게 일했습니다. <Term id="compaction">컴팩션</Term>을 여러 번 거쳤습니다. 한 번에 동작하는 결과를 내놓았습니다.

모델이 좋아지자 더 강한 모델을 따로 부를 일도 줄었습니다. 글을 쓰기 한 달쯤 전 oracle을 만들었습니다. 에이전트가 GPT 5 Pro를 호출하게 해 주는 CLI입니다. 처음에는 하루에 여러 번 썼습니다. GPT 5.2 뒤에는 일주일에 몇 번으로 줄었습니다. GPT 5.2의 <Term id="knowledge-cutoff">지식 컷오프</Term>입니다. Opus보다 5개월쯤 늦습니다.

## 계획은 별도 모드 없이 대화로 세운다

작업 절차도 단순해졌습니다. Steinberger는 별도의 <Term id="plan-mode">계획 모드</Term>를 쓰지 않습니다. 모델에 질문합니다. 검색과 코드 탐색을 시키며 대화로 계획을 세웁니다. 계획이 마음에 들면 다음 중 하나를 씁니다.

- "build"
- "write plan to docs/*.md and build this" 계획 모드는 예전 모델의 임시방편이었습니다. 프롬프트를 잘 따르지 못하던 때입니다.

## 프로젝트 여러 개를 동시에 돌린다

Steinberger는 보통 프로젝트 3~8개를 동시에 진행합니다. 큰 프로젝트 하나에 작은 프로젝트가 몇 개 딸립니다. 글을 쓸 당시 가장 공들인 프로젝트는 Clawdis였습니다. AI 비서입니다. 접근하는 대상은 다음입니다.

- 컴퓨터
- 메시지
- 이메일
- 홈 오토메이션

오케스트레이션은 별로 필요 없습니다. 에이전트 여러 개를 지휘하는 일을 말합니다. 대개 병목은 Steinberger 자신입니다.

프로젝트끼리는 서로 참고가 됩니다. 이미 푼 문제가 있으면 다른 프로젝트를 보게 합니다. 예는 "../vibetunnel을 보고 Sparkle 체인지로그에도 똑같이 해"라는 지시입니다. 새 프로젝트의 기본 골격도 이렇게 만듭니다.

지난 세션을 기억하는 별도 시스템은 쓰지 않습니다. 대신 프로젝트마다 `docs` 폴더를 둡니다. 하위 시스템 문서를 둡니다. 기능 문서도 둡니다. 전역 AGENTS 파일의 지시로 관련 문서를 읽게 합니다. 스크립트로도 읽게 합니다.

<Quote source="post">
After all, I don’t design codebases to be easy to navigate for me, I engineer them so agents can work in it efficiently.
</Quote>


코드베이스는 에이전트가 효율적으로 일하게 설계합니다.

## 혼자 일하는 방식이라 큰 팀에는 맞지 않는다

되돌리기와 체크포인트는 거의 쓰지 않습니다. 문제가 생기면 모델에 수정을 맡깁니다. main 브랜치에 바로 커밋합니다. 워크트리는 가끔만 씁니다. 바로 여기서 조건을 붙입니다.

<Quote source="post">
Caveat: I usually work alone, if you work in a bigger team that workflow obv won’t fly.
</Quote>


보통 혼자 일하는 방식입니다. 큰 팀에서는 통하지 않는다고 Steinberger가 단서를 붙였습니다. 리뷰와 브랜치 규칙이 있는 팀은 그대로 따르기 어렵습니다. 팀 규칙과 부딪히지 않는 부분만 골라 씁니다. CLI로 결과를 확인하게 하는 습관이 그런 부분입니다.

## 한계

이 글은 2025년 12월의 기록입니다. OpenAI에 들어가기 전입니다. 기본 모델은 gpt-5.2-codex였습니다. 다음 비교는 당시 모델을 쓴 한 사람의 경험입니다.

- codex와 Opus
- oracle 사용 빈도
- 지식 컷오프 차이

모델이 바뀌면 이 비교도 쉽게 달라질 수 있습니다. 비교는 금방 낡아도 남는 일이 있습니다. 병목이 타이핑에서 생각으로 옮겨 갔다면 사람의 일은 둘입니다.

- 언어와 의존성을 고릅니다.
- 에이전트가 결과를 확인할 수 있게 해 둡니다.
