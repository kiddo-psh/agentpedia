# 목표: 글로만 있는 규칙을 피라미드의 린트 층으로 하나 옮기기

2026년 11월 Lauren Tan은 에이전트 실수를 고칠 때마다 AGENTS.md에 한 줄을 더하는 대신, 그 교정을 결정적 검사로 바꾸거나 API·구조로 문제 자리를 없앤다고 말했다. 거꾸로 선 피라미드는 위에서부터 **코드 자체 → 린트·타입·컴파일러·테스트 → 검증 → 얇은 글 층**이다. 글 규칙을 없애자는 말이 아니라, 검사로 옮길 수 없는 판단에만 글을 쓰라는 순서다.
이 키트는 컨텍스트 파일(얇은 글 층)의 금지·강제 규칙을 피라미드로 분류해 보고서로 남기고, 승인받으면 **기존 린터로 표현 가능한 규칙 하나만** 린트 층으로 옮긴다. 코드·API 재설계는 하지 않고 보고서에 후보만 적는다. 기본은 **읽기 전용 점검**이다.

## 절대 지킬 것

- 승인받기 전에는 파일을 만들거나 고치지 않는다.
- `npm run lint`나 `make lint` 같은 래퍼 스크립트는 실행하지 않는다. 스크립트에 `--fix`, 포맷, 캐시 쓰기가 들어 있을 수 있으므로 내용만 읽고, 린터 실행 파일(`node_modules/.bin/eslint`, `ruff` 등)을 직접 호출한다. 로컬에 설치돼 있지 않으면 `npx` 등으로 내려받지 말고 설정 읽기와 grep 확인으로 대신한 뒤 그 사실을 보고한다.
- 실행하는 도구는 린터 하나뿐이다. 테스트와 타입 검사는 캐시나 스냅샷 파일을 만들 수 있으므로 실행하지 않고, 이미 강제되는지는 설정 파일을 읽어 판단한다.
- 린터는 파일을 바꾸지 않는 모드로만 실행한다. ESLint는 `node_modules/.bin/eslint <경로>`처럼 `--fix`와 `--cache` 없이 실행한다. `eslint.config.*`는 실행되는 JavaScript이므로, 실행 전에 내용을 읽고 파일 쓰기나 네트워크 호출 코드가 있으면 린터를 실행하지 말고 그 사실을 보고한다. 먼저 설정에 자동 수정 옵션(Ruff의 `fix = true` 등)이 켜져 있는지 읽고, Ruff는 `ruff check --no-fix --no-cache`로 실행한다(Ruff는 기본으로 `.ruff_cache`를 쓴다). 캐시가 기본으로 켜진 다른 린터도 끄는 플래그를 붙이고, 캐시를 켜는 옵션, `--fix`, 포맷, 설치, 빌드, 스냅샷 갱신은 실행하지 않는다. 빌드 산출물을 만들어야 하는 린터(`cargo clippy` 등)는 실행하지 말고 설정 읽기와 grep 확인으로 대신한 뒤 그 사실을 보고한다.
- 기존 코드의 위반을 고치지 않는다. 위반은 개수와 위치만 보고한다.
- 컨텍스트 파일의 문장을 지우거나 바꾸지 않는다. (글 층에서 지우는 키트가 아니다. 린트로 **이중 강제**를 추가하는 키트다.)
- 애플리케이션 코드, API, 디렉터리 구조를 바꾸지 않는다. "코드 자체" 층 후보는 보고서에만 적는다.
- 새 린터나 의존성을 설치하지 않는다. 이미 쓰는 린터의 기능만 쓴다.
- `git commit` 등 git 기록을 바꾸는 명령은 실행하지 않는다.
- API 키, 토큰의 값을 읽어서 출력하지 않는다.

## 0. 맞는지 먼저 판단하기

아래를 확인한다. 하나라도 해당하지 않으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알린다.

- `CLAUDE.md`, `AGENTS.md`, `.cursor/rules/`, `.github/copilot-instructions.md` 같은 컨텍스트 파일이 하나 이상 있고, 금지하거나 강제하는 규칙이 들어 있다.
- 레포가 린터를 이미 쓴다. 설정 파일(`eslint.config.*`(구형 `.eslintrc*`도 있을 수 있음), `ruff.toml`, `.ruff.toml`, `pyproject.toml`의 `[tool.ruff]`, `.golangci.yml`(`.yaml`, `.toml`, `.json`도 가능), `clippy.toml`, `Cargo.toml`의 `[lints]`, `biome.json` 등)과 린트 명령을 확인한다. 목록에 없는 린터는 레포 문서와 `package.json`, `Makefile`의 린트 명령으로 찾는다.

## 1. 규칙 모으기 (읽기 전용)

- 컨텍스트 파일을 읽고 "하지 마라", "항상 ~해라", "~만 써라"처럼 금지하거나 강제하는 규칙을 한 줄씩 모은다.
- 각 규칙에 파일 이름과 줄 번호를 붙인다.
- 에이전트가 주석·문서로 땜질을 정당화하지 말라는 식의 규칙도 모은다(Tan의 "주석 탈출구" 사례). 다만 주석 금지 자체를 린트로 옮길지는 2단계에서 판정한다.

## 2. 피라미드로 분류하기

각 규칙을 실제 설정을 읽어 분류한다. 추측하지 말고 설정 파일로 확인한다. 표에 **현재 층**(대부분 얇은 글 층)과 **목표 층**을 함께 적는다.

- **이미 강제됨 (린트·타입·테스트·디렉터리)**: 결정적 층이 이미 막고 있다. 어느 설정이 막는지 적는다. 글 층에 남아 있어도 이 키트는 글을 지우지 않는다.
- **린트로 옮길 후보**: 글로만 있지만 기존 린터 내장 기능만으로 "나쁜 길을 막거나" 강제할 수 있고 새 파일이 필요 없다.
  - **우선**: 금지 import/API, 경로·패키지 경계(Tan의 useEffect 금지·main/renderer 경계와 같은 형태).
  - 예: ESLint `no-restricted-imports`(`paths`/`patterns`의 `message`), Ruff `[lint.flake8-tidy-imports.banned-api]`(pyproject면 `[tool.ruff.lint.flake8-tidy-imports.banned-api]`) + `lint.extend-select`에 `TID251` (`select`가 없으면 `select`를 새로 쓰지 않는다. 이미 `TID251`이 있으면 그대로 둔다).
  - 플러그인·사용자 정의 규칙이 필요하면 후보가 아니다. 린터별 이름은 공식 문서로 확인한 것만 쓴다. 확인 못하면 **글로 남김**.
- **코드 자체 후보 (이 키트에서 구현하지 않음)**: API·디렉터리 구조·타입으로 문제 자리를 없애야 하는 규칙. 보고서에만 "코드 층 후보"로 적고 옮기지 않는다.
- **검증 층 후보 (구현하지 않음)**: 런타임·형식 검증이 맞지만 린트로 안 되는 것. 보고서에만 적는다.
- **글로 남김 (얇은 글 층)**: 판단·뉘앙스가 필요해 검사로 옮기기 어렵다. 이유를 적는다. **얇은 글 층은 남겨 두는 것이 피라미드에 맞다.**

옮길 후보가 없으면 파일을 만들지 말고 분류 표만 알린 뒤 멈춘다.

## 3. 계획을 보여주고 승인받기

다음을 보여주고 **사용자의 승인을 받은 뒤에만** 4단계를 진행한다.

- 1~2단계 결과 표 (규칙, 위치, 분류, 목표 층, 근거)
- 만들 보고서 `docs/correction-audit.md` (이미 있으면 날짜를 붙인 다른 이름)
- 옮길 후보 중 **하나**만 고른 규칙과 이유. 금지 API·경로 경계처럼 "나쁜 길을 막는" 후보를 스타일 규칙보다 우선한다. 사용자가 다른 규칙을 고를 수 있다.
- 같은 규칙이 설정에 있으면 기존 목록에 덧붙이는 형태만 제안하고, 전후 설정을 나란히 보여 기존 항목이 사라지지 않음을 증명한다. 같은 규칙을 두 번 선언해 덮어쓰지 않는다.
- 추가할 린터 설정의 정확한 내용과 오류 메시지(무엇이 잘못됐는지 + 고치는 방법). 설정 키·규칙 이름은 공식 문서 URL(또는 설치된 린터 규칙 설명·패키지 문서)로 확인한 뒤 쓰고 출처를 승인 요청에 적는다. 확인 못하면 후보에서 빼고 글로 남김으로 옮긴다.
- 현재 코드에서 이 규칙을 어기는 곳의 개수(파일을 바꾸지 않는 검색, 예: grep). 위반이 있으면 위반 없는 경로에만 적용할지·보류할지 묻는다. 린터가 규칙별 경고 수준을 지원한다고 공식 문서로 확인했을 때만(ESLint `"warn"` 등) 선택지에 더한다. Ruff처럼 없으면 주지 않는다.

## 4. 승인된 범위만 적용하기

- `docs/correction-audit.md`를 만든다. 점검 날짜, 피라미드 한 줄 요약, 규칙 분류 표(목표 층 포함), 선택한 규칙과 이유, 기존 위반 목록, 글로 남긴 규칙과 이유, 코드 자체·검증 층 후보(구현하지 않음)를 담는다.
- 승인한 경우에만 기존 린터 설정에 규칙 하나를 추가한다. 사용자가 고른 방식(경로 제한, 경고 수준, 보류)대로만 적용하고, 다른 설정은 건드리지 않는다. 컨텍스트 파일은 수정하지 않는다.

## 5. 실행해서 확인하기

- 수정한 설정이 올바른지 린터를 파일을 바꾸지 않는 모드로 실행해 확인한다. 명령은 추측하지 말고 실제로 실행한다.
- 린터 출력의 해당 규칙 위반 수를 3단계 개수와 비교한다. 다르면 이유(경로 제한, 무시 설정)를 보고한다. 적용 범위를 제한했다면 같은 범위로 다시 센다. 범위 안에 위반이 없으면 표준 입력으로 위반 예시를 넣어 규칙이 걸리는지 확인한다. 예: `echo "import cgi" | ruff check --no-fix --no-cache --stdin-filename <적용 경로>/check.py -`, `echo "import x from 'banned'" | node_modules/.bin/eslint --stdin --stdin-filename <적용 경로>/check.ts`. 걸리지 않으면 추가한 규칙만 되돌리고 보고한다.
- 설정이 오류를 내면 추가한 규칙만 되돌리고 원인을 보고한다. 캐시를 켜는 옵션은 쓰지 않는다.
- 오류 메시지가 에이전트가 따를 수 있을 만큼 고치는 방법을 말하는지 확인한다(Tan: 린트 메시지가 뿌리 원인을 가리킨다).
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고한다.
