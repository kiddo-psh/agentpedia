# 목표: 글로만 있는 규칙을 찾아 보고하고, 승인받으면 하나를 린트 규칙으로 옮기기

2026년 11월 로렌 탄은 에이전트를 고칠 때마다 규칙 문서에 한 줄을 더하는 대신, 그 교정을 린트 규칙 같은 결정적 검사로 바꾼다고 말했다.
이 키트는 이 레포의 컨텍스트 파일에서 글로만 있는 규칙을 찾아 보고서로 남기고, 승인받으면 규칙 하나를 이미 쓰는 린터로 옮긴다. 기본은 **읽기 전용 점검**이다.

## 절대 지킬 것

- 승인받기 전에는 파일을 만들거나 고치지 않는다.
- `npm run lint`나 `make lint` 같은 래퍼 스크립트는 실행하지 않는다. 스크립트에 `--fix`, 포맷, 캐시 쓰기가 들어 있을 수 있으므로 내용만 읽고, 린터 실행 파일(`node_modules/.bin/eslint`, `ruff` 등)을 직접 호출한다. 로컬에 설치돼 있지 않으면 `npx` 등으로 내려받지 말고 설정 읽기와 grep 확인으로 대신한 뒤 그 사실을 보고한다.
- 린터, 테스트, 타입 검사는 파일을 바꾸지 않는 모드로만 실행한다. 먼저 설정에 자동 수정 옵션(Ruff의 `fix = true` 등)이 켜져 있는지 읽고, Ruff는 `ruff check --no-fix --no-cache`로 실행한다(Ruff는 기본으로 `.ruff_cache`를 쓴다). 캐시가 기본으로 켜진 다른 린터도 끄는 플래그를 붙이고, 캐시를 켜는 옵션, `--fix`, 포맷, 설치, 빌드, 스냅샷 갱신은 실행하지 않는다. 빌드 산출물을 만들어야 하는 린터(`cargo clippy` 등)는 실행하지 말고 설정 읽기와 grep 확인으로 대신한 뒤 그 사실을 보고한다.
- 기존 코드의 위반을 고치지 않는다. 위반은 개수와 위치만 보고한다.
- 컨텍스트 파일의 문장을 지우거나 바꾸지 않는다.
- 새 린터나 의존성을 설치하지 않는다. 이미 쓰는 린터의 기능만 쓴다.
- `git commit` 등 git 기록을 바꾸는 명령은 실행하지 않는다.
- API 키, 토큰의 값을 읽어서 출력하지 않는다.

## 0. 맞는지 먼저 판단하기

아래를 확인한다. 하나라도 해당하지 않으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알린다.

- `CLAUDE.md`, `AGENTS.md`, `.cursor/rules/`, `.github/copilot-instructions.md` 같은 컨텍스트 파일이 하나 이상 있고, 금지하거나 강제하는 규칙이 들어 있다.
- 레포가 린터를 이미 쓴다. 설정 파일(`eslint.config.*`(구형 `.eslintrc*`도 있을 수 있음), `ruff.toml`, `.ruff.toml`, `pyproject.toml`의 `[tool.ruff]`, `.golangci.yml`(`.yaml`, `.toml`, `.json`도 가능), `clippy.toml`, `Cargo.toml`의 `[lints]`, `biome.json` 등)과 린트 명령을 확인한다. 목록에 없는 린터는 레포 문서와 `package.json`, `Makefile`의 린트 명령으로 찾는다.

## 1. 규칙 모으기 (읽기 전용)

- 컨텍스트 파일을 읽고 "하지 마라", "항상 ~해라", "~만 써라"처럼 금지하거나 강제하는 규칙을 한 줄씩 모은다.
- 각 규칙에 파일 이름과 줄 번호를 붙인다.

## 2. 규칙 분류하기

각 규칙을 실제 설정을 읽어 다음 중 하나로 분류한다. 추측하지 말고 설정 파일과 린트 명령의 출력으로 확인한다.

- **이미 강제됨**: 린트, 타입 검사, 테스트, 디렉터리 구조가 이미 막고 있다. 어느 설정이 막는지 적는다.
- **옮길 후보**: 글로만 있지만 기존 린터의 내장 기능만으로 표현할 수 있고 새 파일이 필요 없다(금지 import, 금지 구문, 경로별 규칙 등. 예: ESLint `no-restricted-imports`(`paths`/`patterns`의 `message`), Ruff는 `[lint.flake8-tidy-imports.banned-api]`(pyproject.toml에서는 `[tool.ruff.lint.flake8-tidy-imports.banned-api]`)에 금지 대상을 적고 `lint.select`에 `TID251`을 포함한다. 메시지 키 이름은 설치된 버전의 공식 문서로 확인한 것만 쓴다). 플러그인이나 사용자 정의 규칙이 필요한 것은 후보가 아니다. 지금 꺼져 있어도 린터에 내장된 규칙이면 후보다(설정에 켜는 키 하나를 더하는 것까지가 이 키트의 변경 범위다). 린터별 금지 규칙 이름은 공식 문서로 확인한 것만 쓰고, 확인하지 못한 린터의 규칙은 글로 남김으로 분류한다. 사용할 린터 기능 이름을 적는다.
- **글로 남김**: 판단이 필요해 검사로 옮기기 어렵다. 이유를 적는다. 얇은 글 층은 남겨 두는 것이 이 접근에도 맞다.

옮길 후보가 없으면 아무것도 바꾸지 말고 보고서 내용만 알린 뒤 멈춘다.

## 3. 계획을 보여주고 승인받기

다음을 보여주고 **사용자의 승인을 받은 뒤에만** 4단계를 진행한다.

- 1~2단계 결과 표 (규칙, 위치, 분류, 근거)
- 만들 보고서 파일 `docs/correction-audit.md` (이미 있으면 날짜를 붙인 다른 이름을 제안)
- 옮길 후보 중 이 키트가 하나만 고른 규칙과 이유. 사용자가 다른 규칙을 고르게 할 수 있다.
- 추가할 린터 설정의 정확한 내용(규칙을 켜는 키, 예를 들어 `select`가 이미 있는지도 보여 준다)과 오류 메시지 문구. 메시지에는 무엇이 잘못됐는지와 고치는 방법을 적는다. 설정 키와 규칙 이름은 기억에 의존하지 말고 해당 린터의 공식 문서나 설치된 버전의 `--help`로 확인한 뒤 쓰고, 확인한 문서 URL을 승인 요청에 적는다.
- 현재 코드에서 이 규칙을 어기는 곳의 개수 (파일을 바꾸지 않는 검색, 예를 들어 grep으로 위반 위치를 세고 그 명령을 함께 보여 준다). 위반이 있으면 규칙을 경고 수준으로 넣을지, 위반이 없는 경로에만 적용할지, 설정 추가를 보류할지 사용자에게 묻는다.

## 4. 승인된 범위만 적용하기

- `docs/correction-audit.md`를 만든다. 점검 날짜, 규칙 분류 표, 선택한 규칙과 이유, 기존 위반 목록(경로와 줄), 글로 남긴 규칙과 이유를 담는다.
- 승인한 경우에만 기존 린터 설정에 규칙 하나를 추가한다. 다른 설정은 건드리지 않는다.

## 5. 실행해서 확인하기

- 수정한 설정 파일이 올바른 형식인지 린터를 파일을 바꾸지 않는 모드로 실행해 확인한다. 명령은 추측하지 말고 실제로 실행해 결과를 보고한다.
- 린터 출력의 해당 규칙 위반 수를 3단계 개수와 비교한다. 다르면 이유(경로 제한, 무시 설정)를 보고한다. 적용 범위를 제한했다면 같은 범위로 다시 센 개수와 비교한다. 이것으로 규칙이 실제 과거 위반을 잡는다는 것을 증명한다. 위반이 없었다면 그 사실을 보고하고, 규칙이 작동한다는 증거가 없다고 밝힌다.
- 설정이 오류를 내면 추가한 규칙만 되돌리고(다른 설정은 건드리지 않는다) 원인과 함께 보고한다. 캐시를 켜는 옵션은 쓰지 않는다.
- 오류 메시지가 에이전트가 따를 수 있을 만큼 고치는 방법을 말하는지 확인한다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고한다.
