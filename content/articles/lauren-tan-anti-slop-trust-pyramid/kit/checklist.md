# 점검 체크리스트

## 규칙 목록
- [ ] 컨텍스트 파일이나 린터가 없거나 옮길 후보가 없으면 아무 파일도 바꾸지 않고 멈춘 뒤 이유를 알렸다.
- [ ] 컨텍스트 파일의 금지·강제 규칙을 파일 이름과 줄 번호와 함께 모두 적었다.
- [ ] 각 규칙을 피라미드로 분류했다: 이미 강제됨 / 린트로 옮길 후보 / 코드 자체 후보 / 검증 층 후보 / 글로 남김. 목표 층을 표에 적었다.
- [ ] 코드 자체·검증 층 후보는 보고서에만 적고 구현하지 않았다.
- [ ] 글로 남긴 규칙마다 이유(얇은 글 층에 두는 근거)를 적었다.

## 승인과 변경
- [ ] 계획과 린터 설정 내용을 보여 주고 승인을 받은 뒤에만 파일을 만들거나 고쳤다. 승인 전에는 파일이 하나도 생기지 않았다(`git status --ignored`로 무시된 캐시 폴더까지 확인).
- [ ] 보고서에 점검 날짜, 피라미드 한 줄 요약, 규칙 분류 표(목표 층), 선택한 규칙과 이유, 기존 위반 목록, 글로 남긴 규칙, 코드·검증 층 후보가 있다.
- [ ] 옮길 후보를 고를 때 금지 API·경로 경계를 스타일 규칙보다 우선했거나, 사용자가 다른 규칙을 골랐다.
- [ ] 규칙은 사용자가 고른 적용 방식(경로 제한, 경고 수준, 보류)대로만 넣었다. 경고 수준은 린터가 지원한다고 확인한 경우에만 선택지로 줬다.
- [ ] 보고서 파일(`docs/correction-audit.md`, 이미 있으면 날짜를 붙인 이름) 하나만 새로 만들었고, 승인한 경우에 한해 기존 린터 설정 파일 하나에 규칙 하나만 추가했다.
- [ ] git 기록을 바꾸는 명령을 실행하지 않았다.
- [ ] 같은 규칙이 이미 있었다면 기존 항목을 하나도 지우지 않고 덧붙였다. Ruff는 `select` 대신 `extend-select`를 썼다.
- [ ] 추가한 규칙은 린터 내장 기능만 썼고(플러그인, 사용자 정의 규칙 없음), 규칙 이름과 설정 키를 공식 문서로 확인했으면 그 URL을, 설치된 린터의 규칙 설명이나 패키지 문서로 확인했으면 그 출처와 린터 버전을 승인 요청에 적었다. 확인하지 못한 규칙은 후보에서 뺐다.
- [ ] 컨텍스트 파일의 문장을 지우거나 바꾸지 않았다. 애플리케이션 코드·API·디렉터리 구조도 바꾸지 않았다.
- [ ] 기존 코드의 위반을 고치지 않았고, 새 린터나 의존성을 설치하지 않았다.

## 규칙 검증
- [ ] 래퍼 스크립트가 아니라 로컬에 설치된 린터를 직접 실행했고, 설치되지 않은 린터는 내려받지 않았다. 테스트와 타입 검사는 실행하지 않았다.
- [ ] 린터는 자동 수정을 끄고 파일을 바꾸지 않는 모드(Ruff는 `--no-fix --no-cache`)로만 실행했다.
- [ ] 설정이 오류를 냈다면 추가한 규칙만 되돌리고 다른 설정은 그대로이며 원인을 보고했다(오류가 없었으면 해당 없음).
- [ ] 린트 출력의 해당 규칙 위반 수를 3단계에서 센 개수와 비교했다. 적용 범위를 제한했다면 같은 범위로 다시 센 개수와 비교했고, 다르면 이유를 적었다. 적용 범위에 위반이 없었다면 표준 입력으로 위반 예시를 넣어 규칙이 걸리는 것을 확인했다.
- [ ] 오류 메시지에 무엇이 잘못됐는지와 고치는 방법이 있다.
- [ ] 보고서에 키·토큰 값이 없다.
