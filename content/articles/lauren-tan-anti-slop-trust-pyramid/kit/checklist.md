# 점검 체크리스트

## 규칙 목록
- [ ] 컨텍스트 파일이나 린터가 없거나 옮길 후보가 없으면 아무 파일도 바꾸지 않고 멈춘 뒤 이유를 알렸다.
- [ ] 컨텍스트 파일의 금지·강제 규칙을 파일 이름과 줄 번호와 함께 모두 적었다.
- [ ] 각 규칙을 설정 파일과 린트 출력으로 확인해 이미 강제됨, 옮길 후보, 글로 남김으로 분류했다.
- [ ] 글로 남긴 규칙마다 이유를 적었다.

## 승인과 변경
- [ ] 계획과 린터 설정 내용을 보여 주고 승인을 받은 뒤에만 파일을 만들거나 고쳤다.
- [ ] 보고서 파일(`docs/correction-audit.md`, 이미 있으면 날짜를 붙인 이름) 하나만 새로 만들었고, 승인한 경우에 한해 기존 린터 설정 파일 하나에 규칙 하나만 추가했다.
- [ ] git 기록을 바꾸는 명령을 실행하지 않았다.
- [ ] 추가한 규칙은 린터 내장 기능만 썼고(플러그인, 사용자 정의 규칙 없음), 규칙 이름과 설정 키를 공식 문서로 확인했으면 그 URL을, `--help`로 확인했으면 린터 버전과 확인한 출력 요약을 승인 요청에 적었다.
- [ ] 기존 위반이 있으면 경고 수준, 범위 제한, 보류 중 무엇으로 할지 사용자에게 물었다.
- [ ] 컨텍스트 파일의 문장을 지우거나 바꾸지 않았다.
- [ ] 기존 코드의 위반을 고치지 않았고, 새 린터나 의존성을 설치하지 않았다.

## 규칙 검증
- [ ] 린터는 자동 수정을 끄고 파일을 바꾸지 않는 모드(Ruff는 `--no-fix --no-cache`)로만 실행했다.
- [ ] 설정이 오류를 냈다면 추가한 규칙만 되돌리고 다른 설정은 그대로이며 원인을 보고했다(오류가 없었으면 해당 없음).
- [ ] 린트 출력의 해당 규칙 위반 수를 3단계에서 센 개수와 비교했다. 적용 범위를 제한했다면 같은 범위로 다시 센 개수와 비교했고, 다르면 이유를 적었다. 위반이 없었다면 규칙이 작동한다는 증거가 없다고 보고했다.
- [ ] 오류 메시지에 무엇이 잘못됐는지와 고치는 방법이 있다.
- [ ] 보고서에 키·토큰 값이 없다.
