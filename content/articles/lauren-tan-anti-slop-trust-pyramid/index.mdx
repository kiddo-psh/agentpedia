Lauren Tan은 2026년 11월 11일 AI Engineer CODE 2026 강연에서, 에이전트가 실수할 때마다 <Term id="context-file">컨텍스트 파일</Term>(CLAUDE.md나 AGENTS.md)에 "이렇게 하지 마라"라는 한 줄을 더하는 흔한 대응을 믿지 않는다고 말했습니다. 그는 그 한 줄 대신 에이전트가 같은 실수를 할 수 없게 만드는 검사와 코드 구조를 만듭니다. 강연 제목은 "All Code Is Slop (Except Mine)"이고, 여기서 <Term id="slop">슬롭</Term>은 에이전트가 쏟아 내는 질 낮은 코드를 가리킵니다.

Tan은 SpaceXSI의 프린시펄 엔지니어로, Grok Bot이라는 데스크톱 앱을 만드는 팀에서 일합니다. 강연 직전 달인 2026년 10월에 자신이 프로덕션에 낸 PR이 3,000개였다고 밝혔습니다. 이 글의 발언은 행사 측이 공개한 기계 생성 전사본으로 확인했습니다.

## 규칙 한 줄 대신 검사를 만든다

Tan은 에이전트를 고칠 때마다 먼저 묻는다고 말합니다. 이 교정을 자동 검사로 만들 수 없을까. 코드로 쓴 검사는 재현 가능하고, 그래서 글로 쓴 당부보다 믿을 수 있다는 이유입니다.

<KeyIdea title="교정은 규칙이 아니라 원인을 지우는 일입니다">
Tan은 검사를 더하는 데서 그치지 않습니다. API 설계와 구조를 바꿔 문제가 생길 자리 자체를 없애기도 합니다. 이렇게 교정이 쌓일수록 코드 리뷰에서 찾을 것이 줄고, 결국 에이전트가 자기 PR을 대부분 합칠 수 있게 된다고 Tan은 설명합니다.
</KeyIdea>

Tan은 에이전트가 낸 PR을 이렇게 믿을 수 있는 환경을 만드는 데 6개월이 걸렸고, 이제 그중 상당수는 자는 동안 나간다고 말합니다.

## 정원을 가꾸듯 코드베이스부터 치운다

Tan이 코드를 먼저 고치는 이유는 코드가 에이전트에게 가장 큰 입력이기 때문입니다. 코드베이스에 우회책, 안티 패턴, 폐기 예정 코드가 있으면 다음 에이전트는 그것을 "이미 자리 잡은 방식"으로 읽고 따라 합니다. Tan은 코드베이스를 정원에 빗댑니다. 잡초와 해충이 번지듯 나쁜 패턴도 번지니, 코드베이스를 깨끗하게 가꿔 두어야 에이전트가 좋은 패턴을 베낀다는 비유입니다.

## 교정을 구조로 바꾼 세 가지 사례

Tan은 강연에서 세 가지 사례를 들었습니다. 첫째는 Grok Bot 팀의 방식이고, 둘째와 셋째는 Tan이 Cursor 앱에서 "우리"가 겪었다며 소개한 문제와 Grok Bot 팀의 대응입니다. Cursor는 코딩 에이전트이고(2026년 11월 공식 문서 기준), 사례에 나온 Cursor 앱과 Grok Bot은 모두 JavaScript, HTML, CSS로 데스크톱 앱을 만드는 프레임워크인 Electron으로 만들어졌습니다.

### 위험한 API는 아예 막는다

Dune은 Tan의 팀이 Grok Bot용으로 만든 클라이언트 프레임워크로, Tan은 "Electron 앱을 위한 Next.js 같은 것"이라고 설명합니다. 팀은 데스크톱 앱을 만들며 얻은 교훈을 Dune의 제약과 <Term id="lint-rule">린트 규칙</Term>으로 담아 두었습니다. 그 교훈 하나는 이렇습니다.

<Quote source="ai-engineer-transcript" at="5:26">
anything that requires nuance to use well often leads to slop.
</Quote>

잘 쓰려면 미묘한 판단이 필요한 기능은 대개 슬롭으로 이어진다는 말입니다. Tan이 든 예는 React의 useEffect입니다. 쓸 곳이 있지만 자주 잘못 쓰이고, 에이전트도 잘 다루지 못한다고 합니다. 그래서 강연 당시 팀은 useEffect를 제품 코드에서 금지하고 Dune API 안의 몇몇 자리에서만 허용했습니다. Tan은 이로써 useEffect 오용이 범주째로 사라져, 코드 리뷰에서 다시 잡을 일이 없어졌다고 말합니다.

### 경계를 디렉터리로 만든다

Electron 앱은 창을 관리하고 운영체제 기능을 쓰는 main 프로세스와 웹 화면을 그리는 renderer 프로세스로 나뉩니다. Tan에 따르면 Cursor 앱에서는 에이전트가 main 쪽 코드를 renderer로 가져오는 일이 잦았고, 그 때문에 화면이 버벅였습니다. 언제 일인지는 밝히지 않았습니다.

강연 당시 Grok Bot과 Dune의 최상위 디렉터리 이름은 말 그대로 electron renderer와 electron main이었습니다. 둘 사이의 import는 의존성 그래프 분석기와 린트 규칙이 막았습니다. 에이전트에게 주의하라고 당부하는 대신, 어기면 검사에 걸리게 했습니다.

### 주석의 99%를 막는다

Tan에 따르면 에이전트는 올바르게 고치지 않은 이유를 코드 주석이나 문서, 규칙 파일에 적어 정당화합니다. Cursor 앱의 사례가 이를 보여 줍니다. Tan은 그 앱의 아키텍처에서 코드 편집기 VS Code의 명령형 스타일과 React의 선언형 스타일이 부딪혔다고 설명합니다. 그 틈마다 에이전트는 setTimeout 같은 명령형 타이머로 틈을 메웠습니다.

에이전트는 이 땜질이 왜 정당한지 설명하는 주석도 잔뜩 달았습니다. 어느새 타이머가 곳곳에 퍼졌고, 앱 성능이 크게 나빠졌습니다. Grok Bot 팀이 이 경험에서 내린 결론은 이렇습니다.

<Quote source="ai-engineer-transcript" at="8:23">
ban 99% of comments
</Quote>

## 컨텍스트 파일은 피라미드의 맨 아래 얇은 층이다

규칙을 코드로 옮긴다고 검증이 끝나지는 않습니다. Tan은 에이전트 환경을 네 겹으로 나눈 거꾸로 선 피라미드를 보여 줬습니다.

## 코드 리뷰는 검증 산출물을 보는 일로 줄었다

Tan은 코드가 들어오는 속도도 달라졌다고 말합니다. 2024년에는 출근하면 동료들이 쓴 PR 3개를 리뷰했는데, 이 강연 당시에는 그 수가 300개에 가까웠다고 합니다. 본인 경험에서 나온 숫자입니다. 그만큼 리뷰가 하는 일도 바뀌었습니다.

<Quote source="ai-engineer-transcript" at="9:49">
our code review process has now really shrunk into looking at verification artifacts instead.
</Quote>

리뷰어가 보는 것은 이제 코드가 아니라 영상, 스크린샷, 다이어그램, 형식 검증 결과 같은 검증 산출물입니다. Tan이 든 가장 기본적인 예는 <Term id="runtime-verification">런타임 검증</Term>입니다. 에이전트가 앱을 직접 실행하고, Chrome DevTools Protocol처럼 사람 개발자도 쓰는 디버깅 도구로 동작을 확인하는 방식입니다.

팀은 런타임 검증 스킬 안에 앱의 기능을 사용자 관점에서 나열한 <Term id="feature-map">기능 지도</Term>를 두어, 에이전트와 사람이 같은 이름으로 기능을 가리키게 했습니다. 스킬 안에는 직접 만든 CLI와 드라이버도 넣어 에이전트가 매번 다시 쓰게 했습니다. Tan은 이렇게 하면 토큰이 덜 들고 도구 자체를 테스트할 수 있다고 말합니다.

### 형식 검증과 속성 기반 테스트는 실험 단계였다

강연 당시 팀은 <Term id="formal-verification">형식 검증</Term>도 시험하고 있었습니다. 알림이 여러 기기를 오가는 흐름 같은 주요 동작은 TLA+로 모델 검사를 했습니다. 팀이 직접 만든 가상화 라이브러리에는 Lean을 써서 깜빡임이나 흔들림이 없는지 확인했습니다. Tan은 버그를 꽤 찾았지만 만능 해법은 아니고, 에이전트 환경의 또 한 겹으로 다룬다고 말합니다.

UI에는 Bombadil이라는 라이브러리로 <Term id="property-based-testing">속성 기반 테스트</Term>를 막 시작해, UI 버그 몇 개를 잡았다고 합니다. 같은 이름의 Antithesis 저장소는 웹과 터미널 UI용 속성 기반 테스트 도구라고 스스로 소개합니다. Tan은 이런 기법이 새롭지 않다고 합니다. 에이전트가 생기기 전에는 너무 비쌌던 테스트와 검증이 이제 쓸 만해졌다는 것입니다.

## 팀은 PR이 늘어도 되돌림이 늘지 않았다고 보고한다

Tan은 팀의 숫자도 내놓았습니다. 2026년 10월 한 달 동안 Grok Bot 팀은 11,000개의 PR을 프로덕션에 올렸습니다. 강연 당시 안정 버전 클라이언트는 하루 한 번쯤 새로 나왔습니다. 그달에 PR을 하나 이상 낸 사람은 약 227명이었습니다. 개인 수치인 앞의 3,000개와 달리 팀 전체의 수치입니다.

Tan에 따르면 되돌린 PR의 비율은 상대적으로 낮아졌고, 지금은 약 0.5%에서 안정적입니다. 앱이 아직 Electron인데도 시작, 입력, 새 채팅 열기, 채팅 전환이 출시 때보다 빨라졌다고 말합니다. 출시가 언제인지는 밝히지 않았습니다.

## 자동화는 기반을 다진 다음이다

강연 말미에 Tan은 순서를 조언합니다. 모든 것을 자동화하기 전에, 교정이 있을 때마다 코드베이스를 먼저 고치라고 합니다. 안티 패턴이 새로 생기지 않도록 린트 규칙을 만들고, 옛 사례를 정리하고, 검증을 강하게 하라는 것입니다. Tan은 에이전트가 코드를 짜고 고치는 작업을 안쪽 루프라고 부르고, 에이전트 수백, 수천 개를 한꺼번에 돌리는 자동화를 바깥 루프라고 부릅니다.

<Quote source="ai-engineer-transcript" at="15:40">
automating that loop just produces more slop
</Quote>

안쪽 루프가 슬롭을 만드는 채로 바깥 루프를 돌리면 슬롭만 늘어난다는 경고입니다. 기반이 서면 바깥 루프를 돌릴 수 있습니다. 강연 당시 Grok Bot은 새 릴리스를 낼 때마다 Cursor 프로젝트를 자동으로 새로 띄웠습니다. 이 프로젝트는 앱 전체를 실제 사용자처럼 써 보며 퍼징(무작위 입력으로 오류를 찾는 시험)하고, 찾은 버그마다 고치는 PR을 열어 자동으로 합쳤습니다. Tan은 제품 코드 대부분이 더는 깊은 사람 검토를 필요로 하지 않는다고 말합니다.

## 숫자는 자체 보고이고, 주석 금지는 한 팀의 선택이다

이 이야기에는 한계가 있습니다. 숫자는 모두 팀의 자체 보고입니다. Tan은 되돌림을 어떻게 세는지, 무엇을 기준으로 비율을 냈는지 밝히지 않았고, 컨텍스트 파일과 자동 검사를 비교한 통제 실험도 내놓지 않았습니다. 그러니 "자동 검사가 낫다"는 증거라기보다 한 팀의 보고로 읽어야 합니다. 제품 코드 대부분에 깊은 사람 검토가 더는 필요 없다는 주장도 이 보고에 기댑니다.

주석 99% 금지도 한 팀의 선택입니다. 주석이 필요한 다른 코드베이스에 그대로 옮길 수 있는지는 이 강연으로는 알 수 없습니다. Tan의 순서를 따르면, 린트나 타입 검사가 약한 코드베이스는 바깥 루프보다 그 기반을 먼저 갖춰야 합니다.

Tan은 환경을 만드는 데 6개월이 걸렸다고만 했을 뿐 들인 비용은 밝히지 않았습니다. 그래도 Tan이 교정마다 던지는 질문은 같습니다. 이것을 자동 검사로 만들 수 없을까.
