에이전트 PR을 믿으려면 같은 실수를 구조로 막아야 합니다.
Lauren Tan이 2026년 11월 11일 강연에서 한 주장입니다.
행사 이름은 AI Engineer CODE 2026입니다.
강연 제목은 All Code Is Slop (Except Mine)입니다.
<Term id="slop">슬롭</Term>은 질 낮은 에이전트 코드입니다.

Tan은 SpaceXSI 프린시펄 엔지니어이고, Grok Bot 데스크톱 앱 팀에서 일합니다.
강연 직전 2026년 10월, 실제 서비스 PR을 3,000개 냈습니다.

## 교정은 검사로 바뀐다

흔한 대응은 금지 한 줄을 더하는 일입니다.
자리는 <Term id="context-file">컨텍스트 파일</Term>입니다.
CLAUDE.md와 AGENTS.md가 그 파일입니다.
Tan은 그 한 줄을 믿지 않고, 고칠 때마다 검사로 바꿀 수 있는지 묻습니다.
코드 검사는 재현되니 글 당부보다 믿을 수 있습니다.

<KeyIdea title="교정은 원인을 지우는 일이다">
검사는 시작일 뿐입니다.
API와 구조를 바꿔 문제의 자리 자체를 없앱니다.
교정이 쌓이면 리뷰할 일이 줄고, 에이전트가 낸 PR을 대부분 합칩니다.
</KeyIdea>

에이전트의 PR을 믿을 수 있는 환경을 만드는 데 6개월이 걸렸다고 Tan은 말합니다.
지금은 그 PR 상당수가 Tan이 자는 동안 나갑니다.

## 코드베이스를 먼저 치운다

코드가 에이전트의 가장 큰 입력이라 코드부터 고칩니다.
우회책이나 잘못된 패턴이 있으면 다음 에이전트가 따라 합니다.
폐기 예정 코드도 같습니다.
자리 잡은 방식으로 읽기 때문입니다.
Tan은 코드베이스를 정원에 빗댑니다.
나쁜 패턴도 잡초처럼 번집니다.
깨끗해야 에이전트가 좋은 패턴을 베낍니다.

## 구조로 바꾼 사례가 셋이다

사례는 Grok Bot의 방식입니다.
Cursor 앱에서 겪은 일과 대응도 있습니다.
Tan은 뒤의 둘을 우리 경험으로 소개했습니다.
Cursor 앱과 Grok Bot은 둘 다 Electron 앱입니다.
Electron은 데스크톱 앱을 만드는 프레임워크입니다.
쓰는 기술은 셋입니다.

- JavaScript
- HTML
- CSS

### 위험한 API를 막는다

Dune은 Grok Bot용 클라이언트이고, Electron의 Next.js 같은 것이라 설명합니다.
데스크톱 교훈은 Dune의 제약에 담았습니다.
<Term id="lint-rule">린트 규칙</Term>에도 담았습니다.

<Quote source="ai-engineer-transcript" at="5:26">
anything that requires nuance to use well often leads to slop.
</Quote>

판단이 있어야 잘 쓰는 기능은 대개 슬롭이 됩니다.
React useEffect가 그 예이고, 쓸 곳은 있으나 사람과 에이전트가 자주 틀립니다.
강연 때 제품 코드에서는 금지하고 Dune API 몇 자리에서만 허용했습니다.
오용이 범주째 사라져 리뷰에서 다시 볼 일이 없어졌습니다.

### 경계를 디렉터리로 만든다

main 프로세스는 창과 운영체제 기능을 맡고, renderer는 웹 화면을 그립니다.
Cursor에서는 main 코드를 renderer로 가져와 화면이 버벅였습니다.
Grok Bot과 Dune의 최상위 이름은 다음입니다.

- electron main
- electron renderer
둘 사이 import는 의존성 그래프 분석기와 린트 규칙이 막습니다.
당부 대신, 어기면 검사에 걸립니다.

### 주석의 99%를 막는다

에이전트는 덜 고친 이유를 주석에 적어 정당화합니다.
문서와 규칙 파일에도 적습니다.
Cursor에서는 VS Code의 명령형과 React의 선언형이 부딪혔습니다.
틈을 setTimeout 같은 타이머로 메우고, 정당하다는 주석이 붙었습니다.
타이머가 퍼지자 성능이 크게 나빠졌습니다.

<Quote source="ai-engineer-transcript" at="8:23">
ban 99% of comments
</Quote>

주석은 쉽게 낡습니다.
검사는 주석을 강제하지 못합니다.
빠져나갈 구멍이 됩니다.
린트 오류가 대신 뿌리 원인을 고치라고 안내합니다.

2024년에는 출근하면 동료 PR 3개를 리뷰했고, 강연 때는 300개에 가까웠습니다.
본인 경험의 숫자이고, 리뷰의 일도 바뀌었습니다.

리뷰어가 보는 산출물은 다음입니다.

- 영상
- 스크린샷
- 다이어그램
- 형식 검증 결과

기본 예는 <Term id="runtime-verification">런타임 검증</Term>입니다.
에이전트가 앱을 실행하고 Chrome DevTools Protocol로 동작을 봅니다.
사람 개발자도 쓰는 디버거입니다.
스킬 안에 <Term id="feature-map">기능 지도</Term>가 있습니다.
기능을 사용자 이름으로 나열합니다.
직접 만든 CLI와 드라이버도 넣어, 매번 다시 쓰지 않게 했습니다.
토큰이 줄고 도구도 테스트됩니다.

### 형식 검증은 실험 단계였다

<Term id="formal-verification">형식 검증</Term>도 시험 중이었습니다.
기기 사이를 오가는 알림은 TLA+로 모델 검사했습니다.
자체 가상화 라이브러리는 Lean으로 깜빡임과 흔들림을 검사했습니다.
버그는 꽤 찾았으나 만능은 아니고, 환경의 한 겹으로 둡니다.
UI는 Bombadil로 <Term id="property-based-testing">속성 기반 테스트</Term>를 막 시작했습니다.
버그 몇 개를 잡았습니다.
같은 이름 Antithesis 저장소는 웹과 터미널 UI용 도구라고 스스로를 소개합니다.
기법은 새롭지 않고, 에이전트 전에는 너무 비싸 이제야 쓸 만합니다.

## 되돌림 비율은 낮아졌다

2026년 10월 Grok Bot 팀은 실제 서비스에 PR 11,000개를 올렸습니다.
안정 클라이언트는 하루 한 번쯤 나왔고, PR을 낸 사람은 약 227명이었습니다.
앞의 3,000개는 개인 수치입니다.
팀 전체 수치와는 다릅니다.
되돌린 비율은 낮아져 약 0.5%에서 안정입니다.
앱은 아직 Electron인데도 출시 때보다 빠른 동작이 있습니다.

- 시작
- 입력
- 새 채팅 열기
- 채팅 전환

## 자동화는 기반 다음이다

자동화 전에, 교정이 있을 때마다 코드베이스를 먼저 고칩니다.

- 잘못된 패턴을 린트 규칙으로 막습니다.
- 옛 사례를 정리합니다.
- 검증을 강하게 합니다.

안쪽 루프는 코드를 짜는 일과 고치는 일입니다.
바깥 루프는 수백·수천 에이전트의 자동화입니다.

<Quote source="ai-engineer-transcript" at="15:40">
automating that loop just produces more slop
</Quote>

안쪽이 슬롭이면 바깥은 슬롭만 늘립니다.
기반 뒤에 바깥을 돌립니다.
새 릴리스마다 Cursor 프로젝트가 자동으로 시작됐습니다.
앱을 사용자처럼 쓰고, 무작위 입력 퍼징으로 오류를 찾습니다.
버그마다 PR을 열어 자동으로 합쳤고, 제품 코드 대부분은 사람이 깊게 다시 보지 않습니다.

## 숫자는 한 팀의 보고다

숫자는 모두 자체 보고이고, 되돌림을 세는 법과 비교 기준은 없습니다.
통제 실험도 없어, 자동 검사가 낫다는 말의 근거로 읽으면 안 됩니다.
깊은 검토가 필요 없다는 말도 이 보고에 기댑니다.
주석 99% 금지는 한 팀의 선택이라, 다른 코드베이스로 옮길지는 알 수 없습니다.
린트와 타입이 약하면 바깥 루프보다 기반이 먼저입니다.
main을 renderer로 가져온 시점과 출시 시점은 강연에 없습니다.
6개월이 걸렸다는 말만 있고 비용은 없습니다.
