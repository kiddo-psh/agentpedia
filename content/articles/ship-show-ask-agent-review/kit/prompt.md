# Ship·Show·Ask 분류 보고서

Constantin Nicolae는 2026년 11월 10일 Sourcegraph 글에서 PR 리뷰를 Ship, Show, Ask로 나누고, 처음에는 추천만 올렸다고 썼습니다. 친숙함은 컴포넌트마다 다른 사람이 리뷰한 뒤 합쳐진 PR 두 개와 최근 30일의 관련 기여로 봅니다. 인증 검사와 민감 데이터 노출은 경험과 상관없이 리뷰가 필요합니다. 이 키트는 최근 PR을 그 기준으로 나눠 근거와 함께 보고서로 남깁니다. 승인 설정은 바꾸지 않습니다.

## 절대 지킬 것

- 브랜치 보호, 필수 리뷰 인원, 자동 머지, CODEOWNERS, 애플리케이션 코드, GitHub Actions 워크플로를 수정하지 않습니다.
- PR에 댓글을 달거나, 승인하거나, 머지하지 않습니다. `gh pr review`, `gh pr comment`, `gh pr merge`를 실행하지 않습니다.
- 설치, 빌드, 배포, 포맷(`--fix`), 스냅샷 갱신, `git commit`, `git push`를 하지 않습니다.
- API 키, 토큰, 비밀번호의 값을 읽거나 보고서에 적지 않습니다. 경로와 파일 이름만 다룹니다.
- 확인하지 못한 친숙함은 Ship으로 올리지 않습니다. 패턴만으로 인증·민감 데이터 여부를 단정하지 않습니다.

## 0. 맞는지 먼저 판단하기

- `git status --short -uall`과 `git diff | git hash-object --stdin`을 시작 기준으로 기억합니다.
- `git rev-parse --is-inside-work-tree`가 `true`인지 확인합니다.
- `gh auth status`를 실행해 봅니다. 실패하면 GitHub 리뷰 수는 "확인하지 못함"으로 적고, `git log`만 씁니다. 커밋 이력도 없으면 여기서 멈추고 이유를 알립니다.
- 최근 머지된 PR이 10개 미만이거나 커밋이 거의 없으면, 있는 만큼만 보고 개수를 지어내지 않습니다. 분류할 변경이 하나도 없으면 맞지 않다고 보고한 뒤 멈춥니다.

맞지 않으면 파일을 만들지 않고 이유를 알린 뒤 멈춥니다. `docs/review-routing.md`가 이미 있으면 덮어쓰지 않습니다. `docs/review-routing-2.md`처럼 비어 있는 이름을 제안하고, 3단계에서 승인받습니다. `docs/`가 없으면 계획에 폴더 생성을 적고, 승인 뒤에만 만듭니다.

## 1. 읽을 변경과 Ask 고정 경로를 고르기

최근 머지된 PR을 최대 10개만 고릅니다. `gh`가 되면 `gh pr list --state merged --limit 10 --json number,title,author,mergedAt,files,reviews,url`을 실제로 실행합니다. `gh`가 없으면 `git log --pretty=format:'%h %an %ad %s' --date=short -10`과 각 커밋의 `--name-only`만 씁니다.

사용자에게 두 목록을 확인받습니다. 항상 Ask로 둘 경로 조각의 기본 제안은 `auth`, `login`, `session`, `secret`, `credential`, `password`, `pii`, `token`입니다. Show로 둘 경로 조각은 비워 두고, 사용자가 합친 뒤 봐도 된다고 고른 조각만 넣습니다. 사용자가 목록을 확정하기 전에는 분류를 확정하지 않습니다. Ask 조각이 들어간 경로는 경험이 있어도 Ask이고, Ship으로 올리지 않습니다. Ask 조각이 Show 조각보다 우선합니다.

고르기 전에는 보고서를 쓰지 않습니다.

## 2. 근거를 모으기

PR마다 실제로 실행하거나 열어 확인한 것만 적습니다.

- 작성자, 머지 시각, 바꾼 경로.
- 경로가 Ask 고정 조각에 걸리면 Ask. 이유는 "경험과 무관한 리뷰 대상 후보"입니다.
- 걸리지 않으면 친숙함 두 조건을 읽기 전용으로만 셉니다. 다른 사람이 리뷰한 뒤 합쳐진 PR이 그 작성자에게 두 개 있는지, 최근 30일 안에 코드·테스트·기술 문서 기여가 있는지입니다. `gh`로 센 리뷰 작성자가 본인과 같으면 다른 사람의 리뷰로 세지 않습니다. 상위 디렉터리가 같다는 것만으로 같은 컴포넌트라고 단정하지 않습니다. 경로가 겹치는지 적고, 확신이 없으면 친숙함은 "확인하지 못함"입니다.
- 두 조건이 모두 확인되고 Ask 고정 경로가 없을 때만 Ship 후보입니다. 조건이 하나라도 비거나 불명확하면 Ask로 두고, 이유는 "근거 부족"입니다. Sourcegraph 글은 근거가 없을 때 Show인지 Ask인지 표를 공개하지 않습니다. Show는 1단계에서 사용자가 고르고 3단계에서 승인한 경로 조각에 해당하고, Ask 고정에 걸리지 않을 때만 씁니다. Show는 합친 뒤 누군가 본다는 뜻이지, 이미 봤다는 뜻이 아닙니다.
- 고객에게 말하는 내용이 맞는지는 저장소만으로 확인하지 못합니다. 그 칸은 "확인하지 못함"으로 둡니다.

## 3. 계획을 보여주고 승인받기

다음을 보여주고 사용자의 승인을 받은 뒤에만 파일을 씁니다.

- 표본 개수, Ask로 고정할 경로 조각, Show로 둔 경로 조각
- 경로별 건수 초안. Ship 후보는 두 조건이 확인된 것만
- 만들 파일 `docs/review-routing.md` 또는 승인받은 다른 이름
- 바꾸지 않는 것. 브랜치 보호, 승인, 머지, 코드

승인하지 않으면 파일을 만들지 않고 끝냅니다.

## 4. 보고서 쓰기

승인받은 파일에 다음을 담습니다.

- 점검 날짜와 표본 범위
- PR 또는 커밋마다 경로(Ship, Show, Ask), 확인한 근거, 확인하지 못한 항목
- 항상 Ask로 둔 경로 조각과, 패턴이라 사람이 다시 볼 항목
- 이 보고서는 추천이며 GitHub 설정을 바꾸지 않았다는 한 줄
- 도장 요청이 줄었는지는 이 보고서가 재지 않는다는 한 줄

## 5. 실행해서 확인하기

- 보고서에 적힌 PR 번호나 커밋이 2단계 명령의 출력과 맞는지 다시 엽니다.
- `sk-`, `ghp_`, `-----BEGIN` 패턴을 보고서에서 찾습니다. 있으면 값을 지우고 자리만 남깁니다.
- `git status --short -uall`과 `git diff | git hash-object --stdin`을 다시 실행합니다. 새 줄은 승인받은 보고서 하나뿐이어야 하고, 추적 파일의 diff 해시는 시작과 같아야 합니다.
- `checklist.md` 항목을 하나씩 확인하고 결과를 보고합니다.
