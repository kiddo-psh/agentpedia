# 목표: 검증 규칙의 자기 수정 위험을 막고 REVIEW.md·완화 시도 증거 남기기

Addy Osmani는 2026년 11월 Claude Code 팀 글에서 **검사가 자기를 채점하는 규칙을 고칠 수 있으면 그 검사는 깨진 것**이라고 썼다. 검증 루프·E2E·REVIEW.md·verify 스킬이 주제다. 이 키트는 레포의 검증 표면이 같은 변경에 열리는지 점검하고, 승인하면 `REVIEW.md`와 `docs/verifier-honesty.md`에 완화 시도 증거를 남긴다. 검증 명령을 `CLAUDE.md`에 덧붙이는 일은 Boris Cherny 키트 범위라 **하지 않는다**.

## 절대 지킬 것

- 승인받기 전에는 파일을 만들거나 고치지 않는다.
- 검증 명령을 `CLAUDE.md`/`AGENTS.md`에 덧붙이거나 실수 로그를 쌓지 않는다(Boris 범위).
- observe/enforce 커밋 게이트의 설정 키·제품 API를 추측해 쓰지 않는다. 팀에 그런 게이트가 있는지만 파일·훅·문서에서 읽고, 없으면 "없음"으로 적는다.
- Code Review 서비스 설정, 브랜치 보호, GitHub/GitLab 규칙을 바꾸지 않는다.
- 애플리케이션 코드와 테스트 본문을 수정하지 않는다.
- 커밋·푸시·PR 생성·의존성 설치·배포·포맷(`--fix`)·스냅샷 갱신을 하지 않는다.
- API 키·토큰 값을 출력하거나 보고서에 적지 않는다.

## 0. 맞는지 먼저 판단하기

레포를 읽고 다음을 확인한다. 시작 시점의 `git status --short`를 기록한다.

- git 레포인가
- 테스트·린트·타입 검사 명령, `REVIEW.md`, `.claude/skills/**/SKILL.md`, 커밋/푸시 훅 중 검증과 관련된 것이 하나라도 있는가. 또는 사용자가 REVIEW.md·verify 스킬을 새로 두려는가

검증 표면이 전혀 없고 사용자가 새 규칙도 원하지 않으면 **여기서 멈추고** 그 사실만 보고한다. 테스트 코드를 새로 작성하지 않는다.

## 1. 검증 표면 지도 만들기 (읽기 전용)

있는 것만 표로 모은다. 없는 항목은 "없음".

- `REVIEW.md`(루트·하위), `CLAUDE.md` 중 리뷰·검증 관련 문장(내용은 요약만)
- `.claude/skills/verify/SKILL.md` 및 이름에 verify가 들어간 스킬, `.claude/commands/`의 검증 명령
- `package.json` scripts / Makefile 등의 테스트·린트·타입 검사 후보
- pre-commit·husky·lefthook·`.claude/settings.json` hooks 중 검증·리뷰를 강제하는 것

각 행에 **같은 PR/작업 트리에서 함께 수정될 수 있는가**(자기 수정 위험)를 예/아니오로 적는다. Code Review가 `REVIEW.md`를 베이스·기본 브랜치에서 읽는다는 점은 공식 문서(https://code.claude.com/docs/en/code-review-customize)로 확인했다고 보고서에 밝힌다. 로컬 `/code-review`는 `REVIEW.md`를 안 읽는다는 문서 구분도 적는다.

## 2. 안전한 검증 명령만 실행해 확인하기

후보 스크립트 본문을 읽고, 파일을 바꾸지 않는 테스트·린트·타입 검사만 **실제로 실행**한다. 빌드·설치·배포·포맷·스냅샷 갱신·DB·외부 네트워크가 보이거나 불확실하면 실행하지 않고 이름만 적는다. 성공/실패와 시간을 기록한다. 성공한 명령이 없어도 보고서는 만들 수 있으나, `verify` 스킬 추가는 성공한 명령이 있을 때만 제안한다.

## 3. 완화 시도 초안 만들기 (아직 파일에 쓰지 않음)

자기 검증을 속이려는 변경이 어떤 모습인지 초안만 준비한다.

- 현재 `REVIEW.md`가 있으면 Important를 Nit로 낮추거나, "이 PR의 규칙 위반은 보고하지 말 것"처럼 완화하는 **가짜 패치 요지**를 적는다. 없으면 신설할 짧은 `REVIEW.md`와, 그것을 바로 약화하는 요지를 나란히 적는다.
- 왜 그 약화본이 **채점에 쓰이면 안 되는지**(베이스/기본 브랜치 사본, 보호 브랜치, 별도 PR로 규칙만 먼저 병합)를 문서 근거와 함께 한 단락으로 적는다.
- 레포에 Code Review·브랜치 보호가 없으면 그 공백을 "로컬만으로는 REVIEW.md 자기 수정이 막히지 않을 수 있음"으로 명시한다.

파일을 아직 바꾸지 않는다.

## 4. 계획을 보여주고 승인받기

다음을 보여주고 **승인을 받은 뒤에만** 적용한다. 승인받지 않은 항목은 건너뛴다.

1. `docs/verifier-honesty.md` 보고서 (이미 있으면 `docs/verifier-honesty-YYYY-MM-DD.md`)
2. 루트 `REVIEW.md` 신설 또는 보강 내용 전문(Important 정의, Nit 상한≤5, CI가 이미 막는 항목 제외, 행동 주장은 `file:line` 증거). 기존 문장은 삭제하지 않는다.
3. (선택) 2단계에서 성공한 명령만 담은 `.claude/skills/verify/SKILL.md` 최소본. 이미 프로젝트 verify 스킬이 있으면 보강만, 없거나 성공 명령이 없으면 건너뛴다.
4. 3단계 완화 시도 요지가 보고서에 들어가며, 약화본 `REVIEW.md`를 레포에 커밋하지는 않는다.

## 5. 승인된 범위만 적용하고 실행해 확인하기

- 보고서를 쓴다. 점검 날짜, 검증 표면 표, 자기 수정 위험, 완화 시도 요지와 방어 근거, 실패 3회 후 사람 개입을 이미 쓰는지(지시 파일·스킬·훅에서 읽은 근거), 실행한 명령, 시작/종료 `git status --short`를 넣는다.
- 승인한 `REVIEW.md`·`verify` 스킬만 추가/보강한다.
- `verify` 스킬을 추가/보강했다면 스킬에 적힌 명령을 다시 실행해 동작한다. 실패하면 이번 키트가 넣은 부분만 되돌리고 보고한다.
- `git status --short`를 시작 시점과 비교해, 새로 생기거나 바뀐 파일이 보고서·`REVIEW.md`·`.claude/skills/verify/` 아래뿐인지 확인한다.
