Anthropic Claude Code 팀의 Addy Osmani는 2026년 11월 16일 블로그에서, 팀 코드의 약 90%를 Claude가 작성하고 검토한다고 썼습니다. 그 규모에서는 에이전트가 자기 일을 증거로 확인하게 만드는 일이 성패를 가른다고 봅니다. 같은 날 공식 계정 ClaudeDevs도 이 글을 소개했고, 다음 날 NLP 연구자 Yoav Goldberg(X 계정 yoavgo)는 90%가 가능한 이유로 테스트 기법보다 제품이 비교적 단순하다는 반론을 올렸습니다.

## 검증 루프가 없으면 에이전트를 거의 병렬로 돌릴 수 없다

코딩 에이전트에게 일을 맡기면 사람이 모든 diff를 읽어야 품질이 나온다고 믿기 쉽습니다. Osmani는 그 전제를 뒤집습니다. 검증 수단이 없으면 사람이 결과를 일일이 봐야 해서 Claude를 한두 개만 돌릴 수 있고, 있으면 수십·수백 개를 병렬로 돌릴 수 있다고 말합니다.

<Quote source="osmani-verification">
Verification loops are the building block that lets you delegate more work to Claude. Without them, you can really only run one or two Claudes at a time, because you have to check everything yourself. With them, you can run dozens or hundreds in parallel.
</Quote>

내부 시험에서는 구조화된 파일 생성 작업에 채점자(grader)를 따로 두면, 일반 프롬프트 루프보다 과제 성공이 최대 10포인트 올랐고 어려운 문제에서 이득이 컸다고 합니다. 시험 설계의 세부(표본 수, 채점 기준)는 글에 없습니다. 그래도 방향은 분명합니다. 예전에는 비싸던 테스트·벤치마크·실제 실행이, 이제는 에이전트에게 자주 시킬 수 있는 값이 됩니다.

<KeyIdea title="결과가 아니라 증거를 검토한다">
Osmani가 말하는 자기 검증은 모델이 "됐다"고 말하는 일이 아닙니다. 테스트를 돌리고, 앱을 실행하고, 실패하면 고치고, 그래도 안 되면 사람에게 넘기는 <Term id="feedback-loop">피드백 루프</Term>입니다. 사람의 일은 모든 diff를 읽는 쪽에서, 무엇이 끝났는지의 기준을 정하고 증거를 보는 쪽으로 옮겨 갑니다.
</KeyIdea>

## 속이기 어려운 테스트에 먼저 투자한다

어떤 테스트든 피해야 할 실패 방식이 있습니다. 플레이키한 테스트는 에이전트에게 코드를 고치지 않고 다시 돌리는 습관을 심습니다. 느린 테스트는 배치마다 돌리는 횟수를 줄여 원인을 찾기 어렵게 합니다. 무거운 검사는 커밋 전에 두는 편이 낫다고 Osmani는 적습니다.

그다음 세 종류를 우선 투자 대상으로 꼽습니다.

### E2E는 기능이 됐는지 끝까지 보여 준다

하나만 고르라면 <Term id="e2e-test">E2E 테스트</Term>라고 합니다. 장바구니에 담고 결제하고 확인 페이지까지 가는 식의 실제 사용자 흐름입니다. 전체가 되거나 안 되거나라서 속이기가 어렵고, 끝난 기준도 분명합니다. 단위 테스트는 빠르지만, 에이전트와 테스트가 과제 전체를 이해하지 못하면 통과해도 기능이 깨질 수 있다고 말합니다.

웹이면 Claude Chrome 확장, 모바일이면 iOS·Android MCP, 데스크톱이면 computer use, 백엔드면 로컬 서비스 실행처럼, 에이전트에게 실제 시스템을 돌리고 볼 손과 눈을 주라고 권합니다. 사용자 관점의 경로·단축키·선택자·기대 결과를 적은 <Term id="feature-map">기능 지도</Term>는 채점 루브릭이 됩니다.

### 속성 기반 테스트는 사람이 빠뜨린 경계를  Mil다

많은 테스트는 "이런 사고가 날 것 같다"는 예상에 묶입니다. <Term id="property-based-testing">속성 기반 테스트</Term>는 깨지면 안 되는 성질을 먼저 적고, 라이브러리가 수천 개의 입력으로 반례를 찾게 합니다. Osmani가 든 예는 왕복 인코딩, 불변식(잔고가 음수가 되지 않는다), 멱등성, 최적화된 코드와 단순한 정답 코드의 동등성입니다. 에이전트가 만든 코드와 같은 편향으로 예시를 고르지 않는다는 점이 이 방식의 힘입니다.

### 차분 테스트는 옛 시스템을 정답으로 쓴다

동작이 같아야 하는 대규모 마이그레이션에는 <Term id="differential-test">차분 테스트</Term>가 맞다고 합니다. 같은 입력을 옛 시스템과 새 시스템에 넣고 결과가 다르면 버그이거나 허용해야 할 차이입니다. 무작위 입력이나 운영 트래픽 표본을 쓰고, 공백처럼 무관한 차이를 정규화하며, 달라져도 되는 항목은 승인 목록으로 관리하라고 적습니다.

## 팀은 앱을 돌리는 검증과 사람 개입 한도를 같이 둔다

테스트 종류만으로 끝이 아닙니다. Claude Code 팀이 실제로 검증을 붙이는 방식을 Osmani는 따로 적습니다.

가장 앞선 원칙은 "변경을 실행한다"입니다. iOS 변경을 시뮬레이터 없이 내지 않듯, Claude에게도 앱을 끝까지 돌리게 합니다. 시뮬레이터·앱 기동 절차는 `verify`라는 <Term id="agent-skill">에이전트 스킬</Term>로 레포의 `.claude/skills/`에 두고, 관련 코드 가까이에 여러 개 둘 수 있다고 합니다. 2026년 11월 Claude Code 공식 문서 기준으로는 번들 `/verify`가 있고, 프로젝트가 `.claude/skills/verify/SKILL.md`를 기록해 두면 이후 실행이 그 절차를 따릅니다. 세션 시작 때 호출 가능한 프로젝트 `verify` 스킬이 있으면(문서 기준 v2.1.286+), 커밋 직전에 쓰라는 지시가 붙습니다.

실패도 설계합니다. Claude가 검사를 돌리고 고치되, 같은 검사가 세 번을 넘겨도 실패하면 멈추고 사람을 부릅니다. 코드 소유자가 자기 영역의 검사를 쓰고 다듬어, 리뷰어를 부를 때 이유를 함께 말하게 합니다. 신뢰성 점검 목록 39항목은 diff에서 읽히는 트리거와 짝을 이뤄, 보통 3~10개만 골라 본다고 합니다.

리뷰어를 여러 겹 쌓기보다 기본 리뷰어 하나를 다듬는 쪽을 택합니다. `REVIEW.md`에 이 코드에서 무엇을 볼지 적고, 이후 라운드는 앞선 실패 맥락을 이어 받게 합니다.

## 검사가 자기 규칙을 고치면 그 검사는 이미 깨진 것이다

자기 검증에서 Osmani가 가장 강하게 못 박는 문장이 있습니다.

<Quote source="osmani-verification">
If a change can modify the check that judges it, the check is broken.
</Quote>

변경이 자기를 채점하는 규칙을 고칠 수 있으면 검사는 깨진 것입니다. 그래서 Code Review는 `REVIEW.md`를 풀 리퀘스트의 변경분이 아니라 베이스 브랜치나 기본 브랜치에서 읽습니다. 2026년 11월 공식 문서도 같은 규칙을 적습니다. 리뷰 동작을 바꾸려면 `REVIEW.md` 변경을 먼저 병합해야 하고, 보호된 기본 브랜치의 루트 파일에서만 Nit 상한·경로 제외·severity 완화 같은 지시가 적용됩니다. 로컬 `/code-review` 명령은 `REVIEW.md`를 읽지 않고 `CLAUDE.md`만 읽는다고 문서가 구분합니다.

팀은 리뷰를 커밋 단위에 고정하기도 합니다. 리뷰 중에 새 푸시가 들어오면 합격 판정이 낡은 커밋을 가리키게 됩니다. 값싼 검사는 먼저 돌립니다. 로컬에서 테스트·빌드·린트를 안 돌리고 푸시하면 공유 리뷰와 CI 시간을 쓰게 됩니다.

커밋마다 어떻게 검증했는지 도장을 남기고, 검증이 없었으면 `none`도 찍어둡니다. `/code-review`나 `/verify` 없이 커밋하려 하면 막는 게이트도 두었고, off·observe·enforce 모드가 있다고 합니다. observe는 막았을 상황을만 기록해 오탐을 보고, enforce는 실제로 막습니다. 커밋 메시지에 검증을 건너뛴 이유를 적을 수 있고, 한 세션에서 두 번 막히면 다음은 통과시켜 Claude가 끼이지 않게 한다고 적습니다. 이 게이트의 설정 키나 공개 제품 API는 글에 없고, 팀 레포 안의 운영 방식으로 읽어야 합니다.

놓친 사례는 규칙으로 바꿉니다. 사람 리뷰 댓글과 되돌린 PR에서 패턴을 뽑되, 최소 두 PR에서 나오고 diff로 식별 가능해야 후보가 됩니다. 에이전트 셋이 반박을 시도하고 사람이 PR로 승인합니다. 알려진 사고 PR에 버그 탐색기를 다시 돌렸을 때 둘 이상이 찾으면 탐지 가능한 버그로 보고, 작은 diff에서 놓치면 `REVIEW.md` 규칙 후보로 올립니다. 플레이키한 테스트는 건너뛰기·sleep·재시도로 통과시키지 못하게 하고, 원인을 못 찾으면 테스트를 지우고 이유를 남기게 합니다.

## 90% 주장은 반론과 한계를 같이 읽어야 한다

공식 계정이 글을 소개한 다음 날, Yoav Goldberg는 긴 노트로 반박했습니다. 팀이 사람 리뷰 없이 에이전트가 코드의 90%를 쓰고 검증한다고 자랑한 뒤 일반론적인 테스트 팁을 줬다고 요약합니다. 그가 보기에 가능한 이유는 자동 테스트 솜씨가 아니라, Claude Code가 본질적으로 매우 단순한 소프트웨어라는 점입니다. 효율 압박이 거의 없고, 경쟁자도 없으며, Claude Code 자체로 인한 해로운 버그나 데이터 손상 가능성이 작고, 많은 버그는 아래 LLM이 매우 좋아서 흡수·보정된다는 주장입니다.

<Quote source="yoavgo-rebuttal">
but my take is that the real reason they can pull it off is not their amazing auto-testing skills, but the fact that claude-code is essentially a very simple piece of software
</Quote>

이 반론은 검증 루프를 쓸모없다고 말하진 않습니다. 다만 같은 루프를 위험면이 큰 제품에 그대로 옮기기 전에, 제품의 복잡도와 실패 비용을 따지라는 경고에 가깝습니다. 또한 Osmani 글은 실패 세 번 뒤 사람 개입, 소유자 검사, 리뷰어 평가처럼 사람이 남는 지점을 적습니다. Goldberg가 말한 "사람 리뷰 없음"은 글의 모든 장치와 같지 않습니다. "~90%" 수치의 측정 단위·분모·독립 검증도 이 글만으로는 확인할 수 없습니다.

가져갈 실무 순서는 비교적 좁습니다. 에이전트가 실제로 돌릴 수 있는 검증을 주고, 플레이키·느린 검사를 고치며, 채점 규칙이 채점 대상과 같은 변경에 열리지 않는지 확인하는 일입니다. 그 위에서야 사람이 모든 diff를 읽는 대신 증거를 검토하는 쪽으로 옮길 수 있습니다.
