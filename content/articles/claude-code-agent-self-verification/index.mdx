2026년 11월 16일, Anthropic Claude Code 팀의 Addy Osmani가 블로그에 적었습니다. 팀 코드의 약 90%를 Claude가 쓰고 검토합니다. 이 규모에서는 증거 확인이 성패를 가릅니다. 같은 날 ClaudeDevs가 글을 소개했고, 다음 날 NLP 연구자 Yoav Goldberg가 반론을 올렸습니다. X 계정은 yoavgo입니다.

## 검증이 없으면 한두 개만 돌린다

모든 diff를 읽어야 품질이 난다고 믿기 쉽습니다. Osmani는 그 전제를 뒤집습니다. 검증이 없으면 사람이 결과를 일일이 보느라 Claude를 한두 개만 돌리고, 검증이 있으면 수십·수백 개를 병렬로 돌립니다.

<Quote source="osmani-verification">
Verification loops are the building block that lets you delegate more work to Claude. Without them, you can really only run one or two Claudes at a time, because you have to check everything yourself. With them, you can run dozens or hundreds in parallel.
</Quote>

사람이 확인하는 동안에는 많이 맡기지 못합니다. 루프가 있으면 일을 더 맡깁니다. 내부 시험도 그 차이를 봤습니다. 과제는 구조화된 파일 생성이었고, 채점자를 따로 두면 성공이 올랐습니다. 영어 이름은 grader입니다. 일반 프롬프트 루프보다 높았고, 최대 10포인트입니다. 어려운 문제에서 이득이 컸습니다. 그래서 이제는 테스트, 벤치마크, 실제 실행을 자주 시킬 수 있습니다. 예전에는 이 확인이 비쌌습니다.

<KeyIdea title="증거가 검토 대상입니다">
이 검증은 모델의 "됐다"가 아닙니다. 테스트를 돌리고 앱을 실행한 뒤, 실패하면 고치고 그래도 안 되면 사람에게 넘기는 <Term id="feedback-loop">피드백 루프</Term>입니다. 사람은 완료 기준과 증거를 봅니다.
</KeyIdea>

## 속이기 어려운 검사에 먼저 쓴다

질문은 그때 바뀝니다. 어떤 검사부터 두느냐입니다. 플레이키한 테스트는 코드를 고치지 않은 채 다시 돌리게 합니다. 느린 테스트는 배치마다 도는 횟수를 줄여 원인을 찾기 어렵게 합니다. 무거운 검사는 커밋 전에 둡니다.

### E2E는 기능이 됐는지 끝까지 보여 준다

하나만 고르면 <Term id="e2e-test">E2E 테스트</Term>입니다. 장바구니에 담고, 결제하고, 확인 페이지까지 가는 실제 사용자 흐름입니다. 전체가 되거나 안 되거나라, 속이기가 어렵습니다. 끝난 기준도 분명합니다. 단위 테스트는 빠릅니다. 과제 전체를 모르면 통과해도 기능이 깨질 수 있습니다.

에이전트에 시스템을 돌리고 볼 수단도 줍니다. 웹은 Claude Chrome 확장이고, 모바일은 iOS와 Android MCP입니다. 데스크톱은 computer use, 백엔드는 로컬 서비스 실행입니다. 사용자 관점에서 경로, 단축키, 선택자, 기대 결과를 적으면 그 목록이 <Term id="feature-map">기능 지도</Term>이고, 채점 루브릭이 됩니다.

### 속성 기반 테스트는 빠뜨린 경계를 찾는다

많은 테스트는 예상한 사고에만 묶입니다. <Term id="property-based-testing">속성 기반 테스트</Term>는 깨지면 안 되는 성질을 먼저 적고, 라이브러리가 수천 개의 입력에서 반례를 찾습니다. Osmani의 예는 왕복 인코딩, 잔고는 음수가 되지 않는다는 불변식, 멱등성, 최적화된 코드와 단순한 정답 코드의 동등성입니다. 예시를 고르는 쪽은 코드를 만든 에이전트가 아닙니다. 그래서 같은 편향이 끼어들지 않습니다.

### 차분 테스트는 옛 시스템을 정답으로 쓴다

<Term id="differential-test">차분 테스트</Term>는 동작이 같아야 하는 대규모 마이그레이션에 맞습니다. 같은 입력을 옛 시스템과 새 시스템에 넣습니다. 결과가 다르면 버그이거나, 허용할 차이입니다. 입력은 무작위이거나 운영 트래픽 표본입니다. 공백처럼 무관한 차이는 정규화하고, 달라져도 되는 항목은 승인 목록으로 둡니다.

## 세 번 넘으면 사람을 부른다

검사 종류만으로 끝나지는 않습니다. Osmani는 팀이 검증을 붙이는 방식을 따로 적습니다.

가장 앞선 원칙은 변경을 실행하는 일입니다. iOS 변경을 시뮬레이터 없이 내지 않고, Claude도 앱을 끝까지 돌립니다. 시뮬레이터와 앱 기동은 `verify`에 둡니다. <Term id="agent-skill">에이전트 스킬</Term>이고, 위치는 저장소 `.claude/skills/`입니다. 관련 코드 가까이에 여러 개 둘 수 있습니다. 번들 `/verify`가 있어서, 프로젝트가 `.claude/skills/verify/SKILL.md`를 적으면 그 절차를 따릅니다. 세션 시작 때 부를 수 있는 프로젝트 `verify`가 있으면 커밋 직전에 쓰라는 지시가 붙습니다. 버전은 v2.1.286 이상입니다. 2026년 11월 문서의 설명입니다.

실패도 설계합니다. Claude가 검사를 돌리고 고칩니다. 같은 검사가 세 번을 넘겨 실패하면 멈추고, 사람을 부릅니다. 코드 소유자가 맡은 영역의 검사를 쓰고 다듬습니다. 리뷰어를 부를 때는 이유를 함께 말합니다. 신뢰성 점검 목록은 39항목입니다. diff에서 읽히는 트리거와 짝을 이루고, 보통 3~10개만 골라 봅니다.

리뷰어를 여러 겹 쌓지 않습니다. 기본 리뷰어 하나를 다듬고, `REVIEW.md`에 이 코드에서 볼 것을 적습니다. 이후 라운드는 앞선 실패의 맥락을 이어 받습니다.

## 검사가 자기 규칙을 고치면 깨진다

`REVIEW.md`를 같은 변경이 고칠 수 있는지가 다음 문제입니다. Osmani가 가장 강하게 못 박는 문장입니다.

<Quote source="osmani-verification">
If a change can modify the check that judges it, the check is broken.
</Quote>

변경이 채점 규칙을 고칠 수 있으면 검사는 깨집니다. Code Review는 `REVIEW.md`를 베이스 브랜치에서 읽고, 기본 브랜치에서 읽기도 합니다. 풀 리퀘스트의 변경분에서는 읽지 않습니다. 2026년 11월 문서도 같은 규칙입니다. 리뷰 동작을 바꾸려면 `REVIEW.md`를 먼저 병합합니다. Nit 상한, 경로 제외, severity 완화는 보호된 기본 브랜치의 루트 파일에서만 적용됩니다. 로컬 `/code-review`는 `REVIEW.md`를 읽지 않습니다. `CLAUDE.md`만 읽습니다.

팀은 리뷰를 커밋 단위에 고정하기도 합니다. 리뷰 중에 새 푸시가 오면 합격이 낡은 커밋을 가리키기 때문입니다. 값싼 검사를 먼저 돌립니다. 로컬에서 테스트, 빌드, 린트를 건너뛰고 푸시하면 공유 시간을 씁니다. 쓰는 시간은 공유 리뷰와 CI입니다. 커밋마다 검증 도장을 남기고, 검증이 없었으면 `none`도 찍습니다. `/code-review` 없이 커밋하면 게이트가 막고, `/verify` 없이 커밋해도 막습니다. 모드는 off, observe, enforce입니다. observe는 막았을 상황만 기록해 오탐을 보는 모드이고, enforce는 실제로 막습니다. 커밋 메시지에 건너뛴 이유를 적을 수 있습니다. 한 세션에서 두 번 막히면 다음은 통과합니다. Claude가 끼이지 않게 하는 장치입니다.

놓친 사례는 규칙으로 바꿉니다. 사람 리뷰 댓글에서 패턴을 뽑고, 되돌린 PR에서도 뽑습니다. 후보가 되려면 최소 두 PR에 나와야 하고, diff로 식별도 가능해야 합니다. 에이전트 셋이 반박을 시도하고, 사람이 PR로 승인합니다. 알려진 사고 PR에 버그 탐색기를 다시 돌려, 둘 이상이 찾으면 탐지 가능한 버그로 봅니다. 작은 diff에서 놓치면 `REVIEW.md` 규칙 후보로 올립니다. 플레이키한 테스트는 건너뛰기, sleep, 재시도로 통과시키지 않습니다. 원인을 못 찾으면 테스트를 지우고, 이유를 남깁니다.

채점 규칙은 변경이 손댈 수 없는 브랜치에서 읽힙니다.

## 90% 주장은 반론과 한계를 같이 읽어야 한다

공식 계정이 글을 소개한 다음 날, Goldberg가 긴 노트로 반박했습니다. 팀이 사람 리뷰 없이 코드 90%를 자랑했고, 그 뒤 팁은 어디서나 통할 이야기였습니다.

<Quote source="yoavgo-rebuttal">
but my take is that the real reason they can pull it off is not their amazing auto-testing skills, but the fact that claude-code is essentially a very simple piece of software
</Quote>

자동 테스트 솜씨 때문이 아닙니다. 테스트 기법이 좋아서도 아닙니다. Goldberg가 보는 90%의 이유는 제품이 비교적 단순해서입니다. Claude Code는 매우 단순한 소프트웨어입니다. 효율 압박이 거의 없고, 경쟁자도 없습니다. Claude Code로 인한 해로운 버그 가능성이 작고, 데이터 손상 가능성도 작습니다. 많은 버그는 아래 LLM이 흡수하고, 아래 LLM이 버그를 보정하기도 합니다.

이 반론은 검증 루프를 버리자는 말이 아닙니다. 위험면이 큰 제품에 옮기기 전에, 제품의 복잡도와 실패 비용을 따지라는 경고입니다. Osmani 글에도 사람이 남는 지점이 있습니다. 실패 세 번 뒤의 사람 개입, 소유자 검사, 리뷰어 평가입니다. Goldberg의 사람 리뷰 없음은 이 장치 전부와 같지 않습니다.

약 90%의 측정 단위는 글에 없습니다. 분모도 없고, 독립 검증도 없습니다. 내부 시험의 표본 수와 채점 기준도 없습니다. 커밋 게이트의 설정 키도 없고, 공개 제품 API도 없습니다. 팀 저장소 안의 운영 방식으로 읽습니다.

실무에서 가져갈 순서는 좁습니다. 에이전트가 실제로 돌릴 검증을 주고, 플레이키한 검사와 느린 검사를 고칩니다. 채점 규칙이 같은 변경에 열리지 않는지 확인한 다음, 사람은 모든 diff 대신 증거를 검토합니다.
