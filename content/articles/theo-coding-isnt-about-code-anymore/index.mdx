Theo Browne이 2026년 11월 8일 영상에 경고를 남겼습니다. 코딩 방식을 지난 1년간 그대로 뒀다면 일자리가 위험합니다. 시작 20초쯤, 달릴 댓글을 이미 안다고 털어놓습니다. 진짜 엔지니어도 아니고 AI만 믿는 JavaScript 개발자라는 내용이고, 대상은 제품을 내며 역할을 고민하는 개발자입니다.

<Quote source="yt-video" at="1:10">
we're not really engineers anymore.
</Quote>

이제 정말 엔지니어가 아닙니다. 그러면 남는 역할은 무엇일까요.

## 역할은 정원사다

수년간 이 결론을 피했습니다. 틀렸다고 인정합니다. 기술 리드, PM, 디자이너, 비저너리가 아니라 정원사이고, 최선은 건강한 정원을 유지하는 일입니다. 영상 1분 28초에 예고한 주장이고, 틀리면 인플루언서라는 농담도 있습니다.

<KeyIdea title="정원사는 키우지 않고 가꾼다">
<Term id="gardening-metaphor">가드닝 비유</Term>입니다. 정원사는 식물을 직접 키우지 않습니다. 양분과 지지대를 마련하고, 지켜볼 장치도 둡니다. 잡초로 번지기 전에 바로잡습니다.
</KeyIdea>

슬픈 이야기로 남기길 원하지 않습니다. 구간은 영상 3분 15초~5분 45초입니다. 레고처럼 조각을 조립하는 즐거움이 사라질까 두렵기도 했지만, 지금은 어느 때보다 재미있습니다. 일주일에 한두 번은 새벽 6시에야 잠듭니다.

채널은 Theo - t3.gg, 개발자 대상 유튜브입니다. 2017년부터 2021년까지 Twitch에서 일했고, 영상 때 회사 Ping을 이끕니다. 앱 <Term id="t3-code">T3 Code</Term>와 채팅 T3 Chat을 만들며, 여러 코딩 에이전트를 한곳에서 돌립니다.

질문은 그때 바뀝니다. 이 비유는 어디서 왔을까요.

## 나쁜 PR은 환경을 고칠 기회다

뿌리는 에이전트 이전이고, 시점은 Twitch의 2019~2021년입니다. 대부분 일화에 연도가 없어, 말한 순서를 따릅니다. 제품 팀은 기능을 만들었고, 플랫폼 팀의 기반은 브라우저 클라이언트, 데이터베이스, 비디오 인프라였습니다. Theo는 제품 팀이었고, 플랫폼 회의에도 나갔습니다.

React 재작성 초기의 PR은 새 문서를 따른 나쁜 코드였습니다. Derek이 이유를 묻자 문서와 코드 예시를 보여 줬고, 30분 안에 Derek이 PR 두 개를 올렸습니다. 하나는 헷갈리던 문서이고, 하나는 헷갈리던 코드입니다.

그래서 나쁜 PR은 다음 실수를 막을 환경 수리 기회입니다. 놓치면 품질이 무너집니다. 슬롭이라 무관심했다는 댓글을 예상하지만 정반대입니다. 품질은 코드나 실력만의 일이 아니라, 소통과 조직의 일입니다. 평범한 엔지니어도, 뛰어난 엔지니어도, 해치지 않는 코드를 병합합니다.

이 이야기에 없던 것은 관리자와 깐깐한 리뷰입니다. 가드레일, 단위 테스트, 커버리지도 없었습니다. 좋은 제품이 자랄 플랫폼을 만들고, 제품 피드백으로 함께 자랍니다.

2021년 퇴사 뒤 1,500명 회사에서 직원 Theo뿐인 회사로 옮겼습니다. 옳은 일은 쉽고 틀린 일은 어렵게, 혼자여도 같았습니다. PR 절반쯤은 사용자에게 차이가 안 보였고, 그 절반이 나머지를 쉽게 합쳤습니다. 제품과 플랫폼을 오간 경험이 커리어에서 거의 무엇보다 컸습니다. 묶어 둔 <Term id="t3-stack">T3 스택</Term>도 믿을 플랫폼이 필요해 나왔습니다.

그 경험이, 에이전트가 코드를 쓰기 시작한 뒤에는 왜 더 커졌을까요.

## 환경이 10배 더 중요해졌다

마지막 수작업은 영상 26분께, T3 Chat 동기화 엔진을 Convex로 옮긴 일입니다. 직접 만든 백엔드였고, 에이전트에 맡겼으나 실패해 직접 했습니다. 25,000줄이 넘는 PR에 약 한 달이 걸렸습니다. 평생 마지막 수작업으로 봅니다.

이유는 유지보수나 데이터베이스 비용이 아니었습니다. 백엔드를 Theo만 알아 팀을 막았고, 이전 뒤 팀원 PR과 병합이 늘었습니다. 에이전트 전의 슬롭도 팀을 막았습니다. 누가 썼는지는 중요하지 않습니다. 이전 세대 슬롭이 다음 세대도 막습니다. 그래서 플랫폼 다듬기가 예전보다 10배 중요해졌습니다. 영상 30분 11초~30분 57초의 말이고, 이름을 가드닝이라 합니다.

<Quote source="yt-video" at="32:52">
we shouldn't be the ones growing the code.
</Quote>

코드를 키우는 쪽은 사람이 아니어야 합니다. 사람은 막히지 않게 자랄 땅만 만듭니다.

### 고치는 일의 값이 바뀌었다

훅을 넓히려고 GraphQL 클라이언트 Apollo를 2에서 3으로 올렸습니다. 깨진 TypeScript 수천 파일을 구글 시트로 나눠 맡겼고, 약 8명과 보조 인력이 한 달 넘게 걸렸습니다. 지금은 프롬프트 하나면 됩니다.

영상 몇 달 전 T3 Code의 <Term id="ci">CI</Term>와 타입 검사가 시간과 CPU를 먹었습니다. 세 명이 빨라지려고 TypeScript를 Rust로 다시 쓰는 중입니다. Twitch라면 Go 엔지니어 20명으로 TypeScript를 Go로 다시 쓸 수 있었습니다. 프런트엔드 600~800명의 대기만 줄이자고 벌일 일은 아니었습니다.

값이 이렇게 바뀌면, 사람이 참던 기다림은 에이전트에 어떻게 닿을까요.

## 마찰은 에이전트를 더 크게 막는다

주 10개이던 PR이 12~15개로 느는 정도가 사람 쪽입니다. 개발 서버가 5분이면 에이전트는 확인부터 막힙니다. 사람이 참던 마찰이 에이전트에는 훨씬 큽니다. 느린 개발 서버, 병렬을 막는 느린 CI, 느린 릴리스 파이프라인, 기다림이 부르는 캐시 낭비가 그 마찰입니다.

캐시 수명이 5분인데 검증이 더 길면 캐시가 만료됩니다. <Term id="prompt-cache-ttl">프롬프트 캐시</Term>가 처음부터 읽히고, 같은 내용을 다시 읽느라 토큰이 샙니다. Theo의 지적입니다.

<Quote source="yt-video" at="37:48">
Slop grows faster than weeds do.
</Quote>

슬롭은 잡초보다 빨리 자랍니다. 손을 놓으면 정원이 잡초가 됩니다.

## T3 Code는 테스트를 지우고 전송량을 잰다

슬롭이 잡초처럼 덮이기 전에 한 일이 있습니다. T3 Code에서 한 일은 테스트 삭제와 전송량 검사입니다.

### 단위 테스트를 절반 지웠다

PR 하나로 250,000줄이 사라졌습니다. T3 Code 단위 테스트 약 절반을 지운 결과입니다. 쓸모없는 테스트가 예외 경우 검사를 늘려 왔습니다. 막을 회귀는 영상 때까지 없었고, 회귀는 고친 기능이 다시 망가지는 일입니다. Theo가 기억하기로, 테스트 11,000개 가운데 다시 살린 것은 네 개쯤이었습니다. 지침을 바꿔 나쁜 테스트의 에이전트 스레드를 찾게 했습니다. 왜 넣었는지 물어 원인을 찾습니다.

### 전송량 검사로 하락을 막았다

wire protocol을 다듬어 큰 스레드도 5KB쯤이 됐습니다. 내 기기 서버가 휴대폰이나 다른 컴퓨터 화면으로 스레드를 보냅니다. 일주일간 올려 둔 성능을 작아 보이던 PR이 되돌렸습니다. 그래서 thread transfer impact 검사가 PR마다 자동으로 돕니다. 실제 에이전트 스레드 이벤트를 서버에서 화면까지 흘려 전송량 증가를 잽니다. 경로는 실제와 같게 흉내 냅니다. 결과는 PR에 찍히고, 나빠지면 빨간 X가 뜹니다. 45초 미만, 어쩌면 30초쯤이고, 식물 옆 말뚝에 비유합니다. babysitting agent가 이 피드백을 보고 대응합니다. 팀이 아끼는 최적화라는 사실도 에이전트가 얻습니다.
