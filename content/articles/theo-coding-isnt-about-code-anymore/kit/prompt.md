# 목표: 에이전트 피드백을 막는 환경 마찰을 재서 보고서로 남기기

Theo Browne는 2026년 11월 8일 영상에서 에이전트 시대 엔지니어를 코드가 잘 자라는 환경을 가꾸는 정원사로 보고, 느린 개발 서버·CI·캐시·릴리스 파이프라인이 사람보다 에이전트를 더 크게 막는다고 말한다. 쓸모없는 테스트가 엣지 케이스를 늘린다는 사례도 들지만, 그 수치와 삭제는 본인 설명이므로 이 키트는 **지우지 않는다**.
이 키트는 내 레포의 **환경 마찰**(CI 그래프·타임아웃·캐시, 로컬 검증 속도, 개발 서버 명령의 존재)을 점검해 보고서로 남긴다. 승인하면 이번 실행에서 성공한 가장 빠른 검증 명령 한 줄만 기존 지시 파일에 덧붙일 수 있다. 기본은 **읽기 전용 점검**이다.

## 절대 지킬 것

- 테스트 파일, CI 설정, 빌드 스크립트를 삭제하거나 수정하지 않는다. 지울 후보는 보고서에 근거만 적고 삭제는 제안하지 않는다.
- 개발 서버는 실행하지 않는다. 명령 이름과 설정 위치만 적는다.
- 사용자가 승인하지 않은 명령은 실행하지 않는다.
- 파일을 쓰는 명령(빌드, 설치, 배포, 포맷 `--fix`, 스냅샷 갱신, 마이그레이션)은 실행하지 않는다. 파일을 바꾸지 않는 테스트·린트·타입 검사만 실행한다.
- `git commit` 등 git 기록을 바꾸는 명령을 쓰지 않는다. 홈 디렉터리 전역 설정은 건드리지 않는다.
- API 키·토큰 값은 읽어서 출력하지 않는다.
- 실행 전후 `git status --short --ignored`를 비교하고, 달라진 파일은 되돌리지 말고 보고한다.
- Claude Code 버전·Project instructions·플러그인 `instructionFiles` 장문을 쓰지 않는다. 지시 파일 대상은 단순 규칙만 쓴다.

## 0. 맞는지 먼저 판단하기

- 현재 디렉터리가 사용자가 작업하는 git 레포이고, 테스트·린트·타입 검사 명령 또는 CI 설정 중 하나 이상이 있는지 확인한다.
- 둘 다 없으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알린다.

## 1. 환경 경로 파악하기 (읽기 전용)

- **CI**: 설정 파일(`.github/workflows/`, `.gitlab-ci.yml`, `.circleci/` 등) 위치, job/stage 연결(`needs`, `stages`), `timeout-minutes`(또는 동등 키), 캐시 키·경로. 3단계 이상 체인이나 timeout 10 이상이면 "느릴 수 있음"으로만 표시한다(상한값이라 단정하지 않는다).
- **로컬 검증**: `package.json` scripts, `Makefile`, `justfile` 등에서 테스트·린트·타입 검사 명령. 추측하지 말고 파일에서 읽는다.
- **테스트 규모**: 테스트 파일 개수와 종류(단위, 통합, e2e)를 구분할 수 있는 만큼.
- **개발 서버**: 설정에서 명령 이름만 적고 **실행하지 않는다**. 보고서에 "개발 서버 속도는 미측정"이라고 적는다.
- **캐시**: CI·도구 캐시 설정과, 프롬프트/아티팩트 캐시를 문서나 설정에서 언급하면 위치만 적는다. 외부 API 캐시 TTL을 추측하지 않는다.

## 2. 실행 계획 세우고 승인받아 시간 재기

실행할 로컬 검증 명령 목록과, 각 스크립트 본문에서 읽은 부작용 여부(쓰기·배포·DB·외부 호출)를 보여 준다. 부작용이 보이거나 불확실하면 실행하지 않고 이름만 적는다. 외부 DB·네트워크를 쓰는 테스트는 이름만 적는다. 타입 검사는 `incremental`·`composite`가 켜져 있으면 `--incremental false`를 붙일 수 있을 때만 실행한다. 스냅샷 갱신 옵션이 확인되지 않으면 실행하지 않는다. ESLint는 `--fix`와 `--cache` 없이 실행한다.

**사용자가 승인한 명령만** 실행한다. 실행 전 `git status --short --ignored`를 기록하고, 파일을 바꾸지 않는 테스트·린트·타입 검사를 하나씩 실행해 걸린 시간과 성공 여부를 적는다. 실행 후 달라진 파일은 되돌리지 말고 보고서에 적는다.

## 3. 보고서·덧붙이기 계획을 보여주고 승인받기

다음을 보여주고 **사용자의 두 번째 승인을 받은 뒤에만** 4단계를 진행한다.

- 1~2단계 결과: CI 그래프·timeout·캐시, 명령별 시간 표, 빠진 곳, 느릴 수 있는 곳, 가치가 낮아 보이는 테스트 후보(근거만, 삭제 제안 없음)
- 만들 보고서 파일 `docs/feedback-loop-audit.md`(이미 있으면 날짜 접미사)
- 선택: 이번 실행에서 **실제로 성공한** 가장 빠른 검증 명령 한 줄을 기존 지시 파일에 덧붙일지
  - 대상: 작업 디렉터리의 `CLAUDE.md` 또는 `.claude/CLAUDE.md`가 있으면 그 파일(`@AGENTS.md`만 import하는 얇은 파일이면 `AGENTS.md`). 둘 다 없고 `AGENTS.md`만 있으면 그 파일. 상위 디렉터리에만 지시 파일이 있거나 대상이 불명확하면 **건너뛰고** 보고서에 이유만 적는다. 새 파일은 만들지 않는다.
  - 덧붙일 정확한 한 줄 문구와 대상 경로를 승인 요청에 적는다.

## 4. 승인된 범위만 적용하기

- `docs/feedback-loop-audit.md`를 만든다(`docs/`가 없으면 함께 만든다). 이미 있으면 덮어쓰지 말고 `-YYYY-MM-DD` 새 파일로 쓴다. 점검 날짜, 개발 서버 미실행, CI 구성·timeout·캐시, 명령별 시간·결과, 테스트 규모, 빠진 곳, 느릴 수 있는 곳, 테스트 후보(삭제 권고 없음), 실행 부산물, `git status` 비교 한계, 권장 조치(테스트·CI 삭제 없음)를 넣는다.
- 승인했고 이번 실행에서 성공한 명령이 있을 때만, 3단계에서 승인한 파일 끝에 승인한 문구 그대로 한 줄만 덧붙인다. 기존 내용은 지우지 않는다.

## 5. 확인하기

- 시작과 끝의 `git status --short --ignored`를 비교해 승인한 파일 외 변경과 새 캐시·산출물을 보고한다. 이미 있던 무시 디렉터리 안 변경은 이 비교로 알 수 없음을 한계로 적는다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고한다.
