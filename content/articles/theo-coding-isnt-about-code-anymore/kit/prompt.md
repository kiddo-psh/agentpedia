# 목표: 에이전트가 변경을 검증하는 경로를 점검해 보고서로 남기기

Theo Browne는 2026년 11월 8일 영상에서 에이전트 시대 엔지니어의 일을 코드가 잘 자라는 환경을 가꾸는 일로 설명하며, 느린 개발 서버·CI·릴리스 파이프라인이 사람보다 에이전트를 더 크게 막고, 쓸모없는 테스트는 불필요한 엣지 케이스를 늘린다고 말한다. 이 키트는 내 레포의 검증 경로를 점검한다. **테스트를 지우거나 CI를 고치지 않는다.** 이 키트는 마찰이 어디 있는지 찾아 보고서로 남기는 첫 단계까지만 한다. 마찰을 없애는 일과 PR 검사 추가는 보고서를 본 사람이 한다. Theo의 테스트 삭제 사례는 한 팀의 본인 설명이므로 후보를 보고서에 적기만 하고 삭제 여부는 사람이 정한다.

## 절대 지킬 것

- 테스트 파일, CI 설정, 빌드 스크립트를 삭제하거나 수정하지 않는다. 지울 후보는 보고서에 적기만 한다.
- 사용자가 승인하지 않은 명령은 실행하지 않는다.
- 파일을 쓰는 명령(빌드, 설치, 배포, 포맷 `--fix`, 스냅샷 갱신, 마이그레이션)은 실행하지 않는다. 파일을 바꾸지 않는 테스트, 린트, 타입 검사만 실행한다.
- `git commit` 등 git 기록을 바꾸는 명령을 쓰지 않는다. 홈 디렉터리 전역 설정은 건드리지 않는다.
- API 키·토큰 값은 읽어서 출력하지 않는다.
- 실행 전후 `git status --short --ignored`를 비교하고, 달라진 파일은 되돌리지 말고 보고한다.

## 0. 맞는지 먼저 판단하기

- 현재 디렉터리가 사용자가 작업하는 git 레포이고, 테스트·린트·타입 검사 명령이 하나 이상 있는지 확인한다.
- 명령이 하나도 없으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알린다.

## 1. 경로 파악하기 (읽기 전용)

- CI 설정 파일(`.github/workflows/`, `.gitlab-ci.yml`, `.circleci/` 등)의 위치와 단계, 어떤 이벤트에서 도는지
- `package.json`의 scripts, `Makefile`, `justfile` 등에서 테스트·린트·타입 검사·개발 서버 명령
- 테스트 파일 개수와 종류(단위, 통합, e2e)를 구분할 수 있는 만큼
- 명령은 추측하지 말고 실제 설정 파일에서 읽는다.

## 2. 실행 계획 세우고 승인받아 시간 재기

먼저 실행할 명령 목록과, 각 스크립트 본문에서 읽은 부작용 여부(쓰기·배포·DB 마이그레이션·외부 서비스 호출)를 사용자에게 보여 준다. 부작용이 보이거나 불확실한 명령은 실행하지 않고 이름만 적는다. 테스트 설정 파일(vitest/jest config, setup 파일)과 환경 변수 파일 이름을 읽어 외부 DB·네트워크·원격 서비스를 쓰는지 확인하고, 쓰거나 불확실하면 그 테스트 명령은 이름만 적고 실행하지 않는다. 타입 검사는 tsconfig의 `incremental`·`composite` 값을 확인하고, 켜져 있으면 `--incremental false`를 붙일 수 있을 때만 실행한다. 스냅샷을 쓰지 않는 옵션(예: Jest `--ci`, Vitest `run --update=none`; 설치된 버전의 `--help`로 옵션 지원을 확인한다)이 해당 도구에 있는지 확인하고, 확인되지 않으면 실행하지 않고 이름만 적는다. ESLint는 `--fix`와 `--cache` 없이 실행한다. Jest 캐시처럼 도구가 기본으로 만드는 캐시는 막지 않고 보고서에 부산물로 적는다.

**사용자가 승인한 명령만** 실행한다. 실행 전 `git status --short --ignored`를 기록하고, 파일을 바꾸지 않는 테스트·린트·타입 검사를 하나씩 실행해 걸린 시간과 성공 여부를 적는다. 실행 후 달라진 파일은 되돌리지 말고 보고서에 적는다.

## 3. 보고서 계획을 보여주고 승인받기

다음을 보여주고 **사용자의 두 번째 승인을 받은 뒤에만** 4단계를 진행한다.

- 1~2단계 결과 표 (명령, 위치, 걸린 시간, 결과)
- 빠진 곳(예: CI 없음, 린트 없음)과 느릴 수 있는 곳, 가치가 낮아 보이는 테스트 후보(근거와 함께 적되 삭제는 제안하지 않고 사용자 판단에 맡긴다), 권장 조치(테스트 삭제는 권장 조치에 넣지 않는다)
- 만들 보고서 파일 `docs/feedback-loop-audit.md`
- 덧붙일 대상 파일의 경로와 덧붙일 한 줄의 정확한 문구(예: `검증: npm test`), 그리고 대상 파일을 정한 근거(버전, 설정값, CLAUDE.md 유무). 건너뛰면 건너뛰는 이유

대상 파일은 다음 순서로 정한다. 이 규칙은 Claude Code 기준이다. 다른 에이전트로 실행 중이면 덧붙이기는 건너뛰고 보고서에만 결과를 남긴다.

- 작업 디렉터리의 `./CLAUDE.md` 또는 `./.claude/CLAUDE.md`가 있으면 그 파일. 단 `@AGENTS.md`만 import하는 얇은 파일이면 AGENTS.md. 작업 디렉터리에는 없고 상위 디렉터리에만 CLAUDE.md가 있으면 덧붙이지 않고 건너뛰며 보고서에 이유를 적는다.
- `~/.claude/CLAUDE.md`와 조직 관리형 CLAUDE.md는 이 조건에서 세지 않는다(2026년 11월 공식 문서 기준). `CLAUDE.md`·`.claude/CLAUDE.md`·`CLAUDE.local.md`가 작업 디렉터리와 그 상위에 모두 없고 AGENTS.md만 있으면, 다음 조건을 모두 확인했을 때만 AGENTS.md. `claude --version`이 2.1.281 이상(공식 문서상 AGENTS.md 직접 읽기의 최소 버전은 2.1.277이고, Bedrock이나 텔레메트리를 끈 일부 세션 보정이 2.1.281에 들어갔다), Project instructions 설정이 `claude-md-or-agents-md`(기본값) 또는 `claude-md-and-agents-md`(`claude-md`나 `managed-only`이면 읽히지 않는다), AGENTS.md 내장 플러그인을 끄지 않음(2026년 11월 Claude Code 공식 문서 기준). `~/.claude/settings.json`은 전체를 출력하지 말고 `pluginConfigs` 키만 찾아 읽는다(예: grep으로 `agents-md@builtin` 줄만). `cc-plugin-agents-md@builtin`(2.1.285 미만은 `agents-md@builtin`) 항목 아래 `options.instructionFiles` 값을 보고, 항목이 없으면 기본값으로 본다. 조직 관리형 설정이나 `--settings` 파일에서 값이 바뀌었을 수 있으므로, 이 세션 시작 때 AGENTS.md가 로드됐다는 안내가 있었는지 또는 사용자가 `/context all`의 Memory files에서 AGENTS.md가 보이는지 확인해 알려 주는 것을 최종 근거로 삼는다. 확인되지 않으면 건너뛴다. 업그레이드 직후 첫 세션에는 AGENTS.md가 읽히지 않을 수 있다. 작업 디렉터리나 상위에 `CLAUDE.local.md`만 있으면 AGENTS.md는 읽히지 않으므로 덧붙이지 않고 보고서에 이유를 적는다.
- 둘 다 없으면 건너뛴다.

## 4. 승인된 범위만 적용하기

- `docs/feedback-loop-audit.md`를 만든다(`docs/`가 없으면 함께 만든다). 이미 있으면 덮어쓰지 말고 `-YYYY-MM-DD`를 붙인 새 파일로 쓴다. 보고서에는 점검 날짜, 개발 서버는 실행하지 않아 속도를 재지 못했다는 점, 명령별 시간·결과 표, CI 구성, 테스트 파일 수와 종류, 빠진 곳, 느릴 수 있는 곳, 가치가 낮아 보이는 테스트 후보(근거만, 삭제 권고 없이), 실행 중 새로 생긴 캐시·산출물, `git status` 비교의 한계(이미 있던 무시 디렉터리 안의 변경은 알 수 없음), 3단계의 대상 파일 판정 근거 또는 건너뛴 이유, 권장 조치를 넣는다.
- 승인했고, 이번 실행에서 실제로 돌려 성공한 명령이 있을 때만 3단계에서 승인받은 파일의 끝에, 승인받은 문구 그대로 한 줄만 덧붙인다. 기존 내용은 지우지 않는다. 대상 파일이 정해지지 않았거나 성공한 명령이 없으면 건너뛰고 보고서에 이유를 적는다.

## 5. 확인하기

- 무시된 파일을 포함한 시작과 끝의 `git status --short --ignored` 목록을 비교해, 새로 생기거나 사라진 파일과 승인한 파일 외의 변경을 보고한다. 새로 생긴 캐시·산출물도 되돌리지 말고 보고한다. 이미 존재하던 무시 디렉터리(`coverage/`, `.next/` 등) 안의 변경은 이 비교로 알 수 없으므로 보고서에 한계로 적는다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고한다.
