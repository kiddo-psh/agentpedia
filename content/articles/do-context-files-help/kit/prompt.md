# 목표: 내 컨텍스트 파일의 각 줄을 코드로 알 수 있는 내용인지, 실제 실패와 이어진 규칙인지 따져 보고, 승인한 줄만 지웁니다.

2026년에 정확도를 직접 잰 연구 두 편(Gloaguen 외, Khatri)은 CLAUDE.md·AGENTS.md 같은 컨텍스트 파일이 코딩 에이전트의 정확도를 올린다는 증거를 찾지 못했습니다. 이 키트는 파일에 무엇을 더하지 않고, 코드로 알 수 있는 줄을 골라 지우는 일만 합니다. 이 키트가 성능이나 비용을 개선한다고 주장하지 않습니다.

## 절대 지킬 것

- 새 규칙, 설명, 섹션을 **추가하지 않습니다.** 줄이기만 합니다.
- 수정 대상은 레포 루트와 하위 폴더의 `CLAUDE.md`, `AGENTS.md`뿐입니다. 그 밖의 파일(`.cursorrules`, `GEMINI.md` 등)은 고치지 않습니다.
- 코드, 테스트, 홈 디렉터리의 전역 설정(`~/.claude`, `~/.codex` 등)은 수정하지 않습니다.
- 승인받은 줄만 지웁니다. 추측으로 지우지 않습니다.
- 커밋하지 않고, 삭제 전후 성능이나 비용을 측정하지 않습니다.

## 0. 맞는지 먼저 판단하기

아래를 확인합니다. 해당하지 않으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알립니다.

- 현재 디렉터리가 사용자의 레포이고, 루트나 하위에 `CLAUDE.md` 또는 `AGENTS.md`가 하나 이상 있습니다.
- 모든 대상 파일의 비어 있지 않은 줄을 합쳐 10줄 미만이면 줄일 것이 없다고 알리고 멈춥니다.
- git 저장소이고, 대상 파일에 커밋되지 않은 변경이 없습니다(`git status --short <파일>`이 비어 있음). 아니면 멈추고 먼저 커밋하거나 stash하도록 안내합니다.
- `docs/context-file-audit.md`가 이미 있으면 덮어쓰지 말고 멈춘 뒤 파일명을 어떻게 할지 묻습니다.
- 대상 파일이 `git check-ignore`로 무시되는 파일이면 git으로 되돌리거나 검증할 수 없으므로 멈추고 사용자에게 알립니다.
- 시작 기준선으로 레포 전체의 `git status --short` 결과와 `git rev-parse HEAD`를 기록해 둡니다.

## 1. 줄 단위로 읽고 분류하기 (읽기 전용)

컨텍스트 파일을 줄 단위로 읽고(빈 줄은 세지 않습니다) 각각을 분류합니다. 여러 줄로 이어진 목록 항목은 줄마다 번호를 매겨 같은 분류로 묶습니다.

- **A. 코드로 알 수 있음**: 디렉터리 구조, 사용 언어와 프레임워크, `package.json`·설정 파일에서 읽히는 명령, 코드를 읽으면 드러나는 구조 설명.
- **B. 코드만으로는 알 수 없음**: 팀의 비표준 관행, 코드에 드러나지 않는 금지 사항, 환경 제약.
- **C. 판단 불가**: 사용자에게 물어야 합니다.

A로 분류한 줄은 실제 파일이나 명령으로 **직접 확인합니다.** 예를 들어 "테스트는 `npm test`로 돌립니다"라는 줄은 `package.json`을 열어 실제로 있는지 봅니다. 확인은 파일을 열어 보거나 `--help`, `--version`처럼 상태를 바꾸지 않는 명령으로만 합니다. 빌드, 테스트, 설치, 배포, 마이그레이션 명령은 실행하지 않습니다. 실행해야만 확인되는 줄은 C로 분류합니다. 파일이 말하는 내용이 코드와 어긋나 있으면 A가 아니라 C로 분류하고, 어떤 점이 다른지 계획 보고에 적습니다. 고쳐 쓰지 않으며 삭제는 사용자가 명시한 경우에만 후보로 올립니다.

`@경로` import 줄은 삭제 후보로 올리지 않습니다. 가리키는 파일이 레포 안의 `CLAUDE.md`나 `AGENTS.md`이면 같은 감사 대상에 포함합니다. 그 밖의 파일(다른 이름의 파일, 레포 밖이나 홈 디렉터리의 파일)은 읽기만 하고 삭제 후보에도 올리지 않으며, 계획 보고에 "감사 제외 import"로 경로만 알립니다. 도구가 자동으로 다시 써 넣는 블록(주석 등으로 '자동 생성'이라 표시된 부분)은 지워도 되살아나므로 C로 분류하고 사용자에게 알립니다.

B로 분류한 줄은 각각 **어떤 실제 실패나 사고와 이어져 있는지** 사용자에게 묻습니다. 사례가 없다고 답한 줄도 기본적으로 유지로 두고, 사용자가 삭제를 원한다고 명시한 줄만 삭제 후보로 올립니다.

## 2. 계획을 보여주고 승인받기

다음을 보여주고 **사용자의 승인을 받은 뒤에만** 3단계를 진행합니다.

- 파일별 줄 수와 A·B·C 분류 개수
- 삭제 후보 줄 목록과 각 줄의 근거(어느 파일이나 명령으로 확인했는지)
- 유지할 줄과 이유
- 삭제하면 내용 없이 남는 제목과 빈 줄(별도 후보로 표시하고, 승인 전에는 지우지 않습니다)
- 만들 보고서 파일: `docs/context-file-audit.md`

삭제 후보가 0줄이거나 사용자가 한 줄도 승인하지 않으면 파일을 만들지 말고 멈춘 뒤 이유만 알립니다.

## 3. 승인된 범위만 적용하기

- `docs/context-file-audit.md`를 만듭니다(`docs/` 폴더가 없으면 함께 새로 만듭니다). 점검 날짜, 파일별 표(파일, 줄 번호, 분류, 근거, 결정), 그리고 **삭제한 줄의 원문 전문**을 파일명과 원래 줄 번호와 함께 담습니다. 이렇게 남겨 되돌릴 수 있게 합니다. 삭제할 줄에 비밀번호, 토큰, 내부 주소처럼 보이는 값이 있으면 원문 대신 자리표시자로 바꿀지 사용자에게 먼저 묻습니다.
- 승인한 줄만 컨텍스트 파일에서 삭제합니다. 다른 줄은 건드리지 않습니다.

## 4. 직접 확인하기

- `git diff`, `git diff --stat`, `git status --short`를 실제로 실행해 결과를 보고합니다. 추측으로 '삭제만 있습니다'라고 쓰지 않습니다.
- 삭제한 뒤 `git diff`로 확인합니다. 삭제만 있고 추가된 줄이 없어야 합니다.
- 삭제한 줄이 가리키던 명령(빌드, 테스트 등)이 파일 없이도 `package.json` 같은 곳에서 확인되는지 다시 봅니다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고합니다.
