2026년 2월, ETH 취리히의 Gloaguen 연구진이 논문 한 편을 처음 공개했습니다. 컨텍스트 파일에 uv가 적혀 있으면, 에이전트는 작업 하나에 파이썬 패키지 도구 uv를 평균 1.6번 썼습니다. 적혀 있지 않으면 0.01번도 쓰지 않았습니다(v3 기준). 에이전트는 파일을 정말로 읽고 따랐습니다. 그런데 따른다고 해서 문제도 더 잘 풀까요?

2026년 1월부터 7월까지 처음 제출된 연구 세 편이 이 질문을 각자 다른 잣대로 재 봤습니다.

## 다들 믿는 통념은 무엇입니까

대부분의 개발자는 <Term id="context-file">컨텍스트 파일</Term>을 쓰면 에이전트가 더 잘한다고 믿습니다. 레포를 처음 보는 에이전트에게 지도를 쥐여 주는 일이라고 생각하기 때문입니다.

ETH 취리히 컴퓨터과학과의 Thibaud Gloaguen은 같은 학과의 Martin Vechev, LogicStar.ai 연구자 두 명 등 공저자 네 명과 함께 이 믿음을 직접 재 보기로 했습니다. 논문은 2026년 2월에 처음 올라왔고, 9월에 세 번째 판(v3)이 나왔습니다. 아래 Gloaguen 연구의 수치는 모두 v3 기준입니다.

## 컨텍스트 파일을 넣어도 성공률은 오르지 않았습니다

Gloaguen 연구진은 에이전트 네 가지를 시험했습니다. Claude Code(Sonnet-4.5), Codex(GPT-5.2와 GPT-5.1 mini), Qwen Code(Qwen3-30b-coder)입니다. 벤치마크는 두 개였습니다. 하나는 <Term id="swe-bench">SWE-bench</Term> Lite의 300개 작업(11개 레포)입니다. 다른 하나는 연구진이 새로 만든 CTXbench입니다. PR 5,694개에서 12개 레포, 138개 작업을 골랐습니다.

LLM이 만든 컨텍스트 파일은 성공률을 올리지 못했습니다. SWE-bench에서 약 -0.5%p, CTXbench에서 약 -2%p였습니다. 둘 다 우연과 구분되지 않았습니다. 개발자가 직접 쓴 컨텍스트 파일은 CTXbench에서 약 +2.4%p였습니다. 이것도 우연과 구분되지 않았습니다. 다만 개발자가 쓴 파일과 LLM이 만든 파일의 차이는 유의했습니다(p=3.8%).

<Quote source="gloaguen-2026">
providing context files does not generally improve task success rates
</Quote>

컨텍스트 파일을 줘도 작업 성공률은 대체로 오르지 않는다는 뜻입니다. 연구진은 레포 개요도 따로 살폈습니다. 모델 제공사가 권하는 레포 개요는 에이전트가 PR과 관련된 파일에 더 빨리 닿게 해 주지 못했습니다.

## 컨텍스트 파일이 바꾼 것은 행동과 비용이었습니다

Gloaguen 연구(v3)에서 바뀐 것은 성공률이 아니라 행동이었습니다. 에이전트는 테스트를 더 돌렸습니다. 파일을 더 많이 탐색하고 읽었습니다. 레포 전용 도구도 더 썼습니다.

그 대가는 <Term id="inference-cost">추론 비용</Term>이었습니다. 같은 연구에서 LLM이 만든 컨텍스트 파일은 평균 비용을 SWE-bench에서 약 20%, CTXbench에서 약 23% 늘렸습니다. 둘 다 유의한 차이였습니다. 개발자가 쓴 컨텍스트 파일도 단계를 평균 3.34개 늘렸습니다. 비용은 최대 19% 늘었습니다.

추론 토큰도 늘었습니다. Gloaguen 연구진이 GPT-5.2에서 잰 값은 다음과 같습니다.

| GPT-5.2 추론 토큰 | SWE-bench Lite | CTXbench |
|---|---|---|
| LLM이 만든 컨텍스트 파일 | 약 +22% | 약 +14% |
| 개발자가 쓴 컨텍스트 파일 | (해당 없음) | 약 +20% |

개발자가 쓴 컨텍스트 파일은 CTXbench에만 있습니다.

<KeyIdea title="컨텍스트 파일은 행동을 바꿨지만 성공률은 바꾸지 못했습니다">
에이전트는 적어 둔 도구를 더 쓰고 테스트를 더 돌렸습니다. 하지만 성공률 상승으로는 이어지지 않았고, 비용만 늘었습니다.
</KeyIdea>

## 실행 시간은 오히려 줄었다는 연구도 있습니다

싱가포르경영대학교(Singapore Management University)의 Jai Lal Lulla와 Christoph Treude는 하이델베르크대, 밤베르크대, 킹스칼리지런던 연구자들과 함께 다른 잣대를 썼습니다. 모두 여섯 명입니다. 2026년 1월에 처음 제출하고 3월에 개정한 논문입니다. 인용한 수치는 v1과 v2에서 같습니다.

Lulla 연구진은 Codex(gpt-5.2-codex)로 10개 레포의 PR 124개를 돌렸습니다. AGENTS.md가 있을 때와 없을 때를 짝지어 비교했습니다. AGENTS.md가 있을 때 실행 시간 중앙값이 28.64% 낮았습니다. 출력 토큰 중앙값은 16.58% 적었습니다.

이 연구는 정답 여부를 평가하지 않았습니다. 연구진은 무작위로 고른 결과물 50개만 직접 확인했습니다. 비어 있거나 엉뚱한 수정이 아닌지 본 것입니다. 저자들은 이 차이를 "연관(associated)"이라고 표현합니다. 에이전트는 Codex 하나뿐입니다. 작업 설명은 LLM(gpt-oss-120b)이 PR에서 만들어 냈습니다.

Gloaguen은 성공률과 비용을, Lulla는 실행 시간과 출력 토큰을 쟀습니다. 잰 것이 달라 한쪽이 다른 쪽을 뒤집는다고 보기는 어렵습니다. 그렇다면 성공률을 다시, 이번에는 에이전트 두 종류로 재 보면 어떨까요?

## 두 에이전트로 다시 재도 성공률 차이는 없었습니다

2026년 7월 28일, 독립 연구자 Prakhar Khatri가 혼자 쓴 <Term id="ablation-study">절제 연구</Term>를 올렸습니다. 세 연구 중 가장 늦게 처음 제출된 것입니다(Gloaguen 연구의 v3 개정은 9월). Khatri는 두 에이전트를 같은 작업에 돌렸습니다. Claude Code(claude-sonnet-4-6)와 Codex CLI(gpt-5.5)입니다.

대상은 Python 레포 3개(pdm, firebase-admin-python, opshin)였습니다. Claude는 15개, Codex는 17개 작업을 맡았습니다. 조건마다 3번씩 반복했습니다.

조건은 세 가지입니다.

- **none**: 레포 컨텍스트를 전혀 주지 않습니다.
- **always_on**: AGENTS.md 전문을 매번 에이전트에게 넣어 줍니다.
- **위키 방식**(논문의 selective): 주제별 위키 파일을 작업 공간에 두고, 에이전트가 필요할 때 읽게 합니다.

다만 위키 내용이 AGENTS.md와 같은 레포는 opshin뿐입니다. pdm과 firebase-admin-python에서는 자동 생성된 더 넓은 위키(AGENTS.md의 약 10배, 18배 분량)를 썼습니다.

Khatri 연구의 성공률은 다음과 같았습니다.

| | none | always_on | 위키 방식 |
|---|---|---|---|
| Claude | 53.3% | 55.6% | 55.6% |
| Codex | 58.8% | 56.9% | 52.9% |

<Quote source="khatri-2026">
Context strategy does not measurably move correctness on either agent
</Quote>

컨텍스트를 어떻게 줘도 성공률은 측정할 만큼 움직이지 않았다는 뜻입니다.

Khatri는 차이가 얼마나 작은지도 따졌습니다. <Term id="equivalence-testing">동등성 검정</Term>으로 보면 효과는 Claude에서 10%p, Codex에서 15%p 안쪽으로 묶였습니다. 실제로 관측된 차이는 Claude에서 2.3%p, Codex에서 5.9%p였습니다. 저자는 표본이 작아 이것을 강한 동등성 주장으로 내세우지는 않습니다.

Khatri는 실패의 원인도 짚습니다. 에이전트는 레포 지식이 모자라서 실패하지 않았습니다. 기능을 설계하고, 패턴을 고르고, 정확히 연결하는 구현 능력에서 실패했습니다. 아슬아슬하게 실패한 작업 두 개를 골라 다시 돌려 봤지만, 실제 AGENTS.md는 실패를 통과로 바꾸지 못했습니다.

## 남은 신호는 시간이었지만 탐색 결과입니다

Khatri 연구에서 효율 쪽에는 작은 신호가 하나 남았습니다. opshin의 AGENTS.md에는 전체 테스트가 20분을 훌쩍 넘긴다는 경고가 있습니다. 이 레포에서는 컨텍스트를 줬을 때 Claude의 실행 시간이 약 24% 짧았습니다. 다만 작업이 5개뿐이라 통계적으로 유의하지 않았습니다(p=0.125). 전체 테스트를 다시 돌리는 횟수도 작업 4개 중 3개에서 줄었습니다. 저자는 이 결과를 사후 탐색 결과로만 다룹니다.

저자는 결론에서 컨텍스트가 성공률이 아니라 비용과 시간 면에서 쓸모를 보일 수도 있다고 적습니다.

## 증거가 없다는 말은 효과가 없다는 말이 아닙니다

Khatri 연구는 작업이 15~17개뿐이라, 작은 효과는 애초에 볼 수 없는 설계입니다. 저자도 <Term id="statistical-power">검정력</Term>이 낮다고 먼저 밝힙니다. 10%p 효과를 확실히 보려면 작업이 대략 120~200개 필요합니다.

그러므로 이 결과를 "효과가 없다"로 읽으면 안 됩니다. "큰 효과는 없어 보이지만, 작은 효과는 이 설계로 볼 수 없다"가 정확합니다.

다른 한계도 있습니다. 레포는 Python 3개뿐입니다. AGENTS.md를 Claude에는 시스템 프롬프트로, Codex에는 사용자 메시지 앞에 넣었습니다. 그래서 두 에이전트를 같은 조건으로 비교하기 어렵습니다.

<Quote source="khatri-2026">
Results may not generalize to other languages, larger codebases, or repositories with exceptionally detailed context files.
</Quote>

다른 언어, 더 큰 코드베이스, 아주 상세한 컨텍스트 파일을 가진 레포에는 결과가 일반화되지 않을 수 있다는 뜻입니다.

연구마다 결론이 다른 이유로, Khatri는 작업을 고르는 방식을 의심합니다. 한 에이전트에게만 알맞은 난이도의 작업을 골랐다면, 다른 에이전트에게는 그 작업이 너무 쉽거나 너무 어렵습니다. 그러면 컨텍스트 파일의 효과가 보이지 않습니다. 실제로 두 에이전트가 모두 맡은 15개 작업 가운데 6개는 한쪽 에이전트에게만 성공과 실패가 엇갈린 작업이었습니다. 확인된 설명은 아니고 가설입니다.

## 그래서 결론은 무엇입니까

Gloaguen 연구진은 초록에서 컨텍스트 파일이 비표준 코딩 관행을 지정할 때 유용하다고 적습니다. 성능을 올리려는 시도는 도입 전에 엄격히 평가해야 한다고도 말합니다. 결론 절에서는 컨텍스트 파일에 코드베이스에 이미 있는 것을 넘어서는 구체적인 지시만 담아야 한다고 적습니다.

세 연구는 2026년 1~7월에 처음 제출됐고, 시험한 모델은 연구마다 다릅니다. Gloaguen은 Sonnet-4.5, GPT-5.2, GPT-5.1 mini, Qwen3-30b-coder를, Lulla는 gpt-5.2-codex를, Khatri는 claude-sonnet-4-6과 gpt-5.5를 썼습니다. 이후 나온 모델에서도 같은 결과가 나오는지는 이 연구들이 답하지 않습니다. Gloaguen 연구는 생성된 코드의 효율이나 보안도 재지 않았습니다.

이 세 연구 중 어느 것도 컨텍스트 파일이 쓸모없다고 결론짓지 않았습니다. 다만 성공률을 올리려고 줄을 늘릴 이유도 세 연구에서는 찾지 못했습니다.
