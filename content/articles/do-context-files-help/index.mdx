2026년 2월, ETH 취리히의 Gloaguen 연구진이 논문 한 편을 처음 공개했습니다. 컨텍스트 파일에 uv가 적혀 있으면 에이전트는 작업 하나에 파이썬 패키지 도구 uv를 평균 1.6번 썼습니다. 적혀 있지 않으면 평균 0.01번 미만이었습니다(v3 기준). 에이전트가 파일을 실제로 읽고 따랐다는 뜻입니다. 남는 질문은 지시를 따르면 문제도 더 잘 푸느냐입니다.

2026년 1월부터 7월까지 처음 제출된 연구 세 편이 이 질문을 각자 다른 기준으로 재 봤습니다.

<Term id="context-file">컨텍스트 파일</Term>을 두면 에이전트가 더 잘할 거라고 흔히 생각합니다. 레포를 처음 보는 에이전트에게 안내서를 건네는 셈이라고 여기기 때문입니다.

Thibaud Gloaguen은 ETH 취리히 컴퓨터과학과 연구자입니다. 같은 학과의 Martin Vechev, LogicStar.ai 연구자 두 명 등 공저자 네 명과 함께 이 믿음을 직접 검증했습니다. 논문은 2026년 2월에 처음 올라왔고 9월에 세 번째 판(v3)이 나왔습니다. 이 글에 나오는 Gloaguen 연구의 수치는 모두 v3 기준입니다.

연구진이 시험한 에이전트는 네 가지입니다. Claude Code(Sonnet-4.5), Codex(GPT-5.2와 GPT-5.1 mini), Qwen Code(Qwen3-30b-coder)입니다. 벤치마크는 두 개를 썼습니다. 하나는 <Term id="swe-bench">SWE-bench</Term> Lite의 작업 300개(11개 레포)입니다. 다른 하나는 연구진이 새로 만든 CTXbench입니다. PR 5,694개에서 12개 레포, 작업 138개를 골랐습니다.

결과부터 보면 LLM이 만든 컨텍스트 파일은 성공률을 올리지 못했습니다. SWE-bench에서 약 -0.5%p, CTXbench에서 약 -2%p였고 둘 다 우연과 구분되지 않았습니다. 개발자가 직접 쓴 파일은 CTXbench에서 약 +2.4%p였습니다. 이 역시 우연과 구분되지 않았습니다. 다만 개발자가 쓴 파일과 LLM이 만든 파일 사이의 차이는 유의했습니다(p=3.8%).

<Quote source="gloaguen-2026">
providing context files does not generally improve task success rates
</Quote>

컨텍스트 파일을 줘도 작업 성공률은 대체로 오르지 않았습니다. 연구진은 모델 제공사가 권하는 레포 개요도 따로 살폈습니다. 개요가 있어도 에이전트가 PR과 관련된 파일을 더 빨리 찾지는 못했습니다.

성공률 대신 달라진 것은 에이전트의 행동이었습니다. 컨텍스트 파일이 있으면 에이전트는 테스트를 더 자주 돌렸습니다. 파일도 더 많이 찾아 읽었고, 레포 전용 도구도 더 썼습니다.

그만큼 <Term id="inference-cost">추론 비용</Term>이 늘었습니다. LLM이 만든 파일은 평균 비용을 SWE-bench에서 약 20%, CTXbench에서 약 23% 늘렸습니다. 둘 다 유의한 차이였습니다. 개발자가 쓴 파일도 단계를 평균 3.34개 늘렸고, 비용은 최대 19% 늘었습니다.

추론 토큰도 늘었습니다. 연구진이 GPT-5.2에서 잰 값은 다음과 같습니다.

| GPT-5.2 추론 토큰 | SWE-bench Lite | CTXbench |
|---|---|---|
| LLM이 만든 컨텍스트 파일 | 약 +22% | 약 +14% |
| 개발자가 쓴 컨텍스트 파일 | (해당 없음) | 약 +20% |

개발자가 쓴 컨텍스트 파일은 CTXbench에만 있어서 SWE-bench 칸은 비어 있습니다.

<KeyIdea title="컨텍스트 파일은 행동을 바꿨지만 성공률은 그대로였습니다">
에이전트는 파일에 적힌 도구를 더 쓰고 테스트도 더 돌렸습니다. 하지만 성공률은 오르지 않았고 비용만 늘었습니다.
</KeyIdea>

비용 대신 실행 시간을 본 연구에서는 결과가 조금 달랐습니다. Jai Lal Lulla와 Christoph Treude는 싱가포르경영대학교(Singapore Management University) 소속입니다. 하이델베르크대, 밤베르크대, 킹스칼리지런던 연구자들과 함께 모두 여섯 명이 논문을 썼습니다. 2026년 1월에 처음 제출했고 3월에 개정했습니다. 이 글에서 인용한 수치는 v1과 v2가 같습니다.

연구진은 Codex(gpt-5.2-codex)로 10개 레포의 PR 124개를 돌렸습니다. 같은 작업을 AGENTS.md가 있을 때와 없을 때로 짝지어 비교했습니다. AGENTS.md가 있으면 실행 시간 중앙값이 28.64% 낮았고, 출력 토큰 중앙값은 16.58% 적었습니다.

이 연구는 결과가 정답인지 평가하지 않았습니다. 연구진은 무작위로 고른 결과물 50개만 직접 열어 보고, 비어 있거나 엉뚱한 수정이 아닌지 확인했습니다. 저자들이 이 차이를 "연관(associated)"이라고만 표현하는 이유입니다. 에이전트는 Codex 하나뿐이고, 작업 설명은 LLM(gpt-oss-120b)이 PR을 보고 만들었습니다.

두 연구는 잰 대상이 다릅니다. Gloaguen은 성공률과 비용을, Lulla는 실행 시간과 출력 토큰을 쟀습니다. 그래서 한쪽 결과가 다른 쪽을 뒤집는다고 보기는 어렵습니다. 성공률을 다른 에이전트 두 종류로 다시 잰 연구는 7월에 나왔습니다.

2026년 7월 28일, 독립 연구자 Prakhar Khatri가 혼자 쓴 <Term id="ablation-study">절제 연구</Term>를 올렸습니다. 세 연구 중 가장 늦게 처음 제출된 논문입니다(Gloaguen 연구의 v3 개정은 9월). Khatri는 Claude Code(claude-sonnet-4-6)와 Codex CLI(gpt-5.5)에 같은 작업을 맡겼습니다.

대상은 Python 레포 3개(pdm, firebase-admin-python, opshin)입니다. Claude는 작업 15개, Codex는 17개를 맡았고 조건마다 3번씩 반복했습니다. 비교한 조건은 세 가지입니다.

- **none**: 레포 컨텍스트를 전혀 주지 않습니다.
- **always_on**: AGENTS.md 전문을 매번 에이전트에게 넣어 줍니다.
- **위키 방식**(논문의 selective): 주제별 위키 파일을 작업 공간에 두고, 에이전트가 필요할 때 읽게 합니다.

위키 내용이 AGENTS.md와 같은 레포는 opshin뿐입니다. pdm과 firebase-admin-python에서는 자동 생성한 더 넓은 위키를 썼습니다. 분량은 AGENTS.md의 약 10배, 18배였습니다.

성공률은 다음과 같았습니다.

| | none | always_on | 위키 방식 |
|---|---|---|---|
| Claude | 53.3% | 55.6% | 55.6% |
| Codex | 58.8% | 56.9% | 52.9% |

<Quote source="khatri-2026">
Context strategy does not measurably move correctness on either agent
</Quote>

두 에이전트 모두, 컨텍스트를 어떤 방식으로 줘도 정답률이 측정할 만큼 달라지지 않았습니다.

Khatri는 차이가 얼마나 작은지도 따졌습니다. <Term id="equivalence-testing">동등성 검정</Term>으로 보면 효과는 Claude에서 10%p, Codex에서 15%p 안쪽이었습니다. 실제로 관측된 차이는 Claude 2.3%p, Codex 5.9%p였습니다. 다만 표본이 작아서 저자는 이 결과를 강한 동등성 주장으로 내세우지 않습니다.

실패 원인도 따로 살폈습니다. Khatri에 따르면 에이전트가 실패한 이유는 레포 지식 부족이 아니었습니다. 기능을 설계하고, 알맞은 패턴을 고르고, 코드를 정확히 연결하는 구현 단계에서 막혔습니다. 아슬아슬하게 실패한 작업 두 개를 골라 다시 돌려 봤지만, 실제 AGENTS.md를 줘도 통과하지 못했습니다.

효율 쪽에는 작은 신호가 하나 남았습니다. opshin의 AGENTS.md에는 전체 테스트가 20분을 훌쩍 넘긴다는 경고가 적혀 있습니다. 이 레포에서는 컨텍스트를 줬을 때 Claude의 실행 시간이 약 24% 짧았습니다. 하지만 작업이 5개뿐이라 통계적으로 유의하지 않았습니다(p=0.125). 전체 테스트를 다시 돌린 횟수도 작업 4개 중 3개에서 줄었습니다. 저자는 이 결과를 사후 탐색 결과로만 다룹니다.

결론에서 저자는 컨텍스트의 쓸모가 성공률이 아니라 비용과 시간에서 드러날 수도 있다고 적습니다.

이 결과를 읽을 때 조심할 점이 있습니다. Khatri 연구는 작업이 15~17개뿐이라 작은 효과는 처음부터 잡아낼 수 없는 설계입니다. 저자도 <Term id="statistical-power">검정력</Term>이 낮다고 먼저 밝힙니다. 10%p 효과를 확실히 확인하려면 작업이 대략 120~200개 필요합니다.

따라서 이 결과를 "효과가 없다"로 읽으면 안 됩니다. 큰 효과는 없어 보이지만 작은 효과는 이 설계로 확인할 수 없다고 읽어야 정확합니다.
