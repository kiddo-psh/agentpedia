컨텍스트 파일은 성공률을 대체로 올리지 못했습니다. Gloaguen 연구진이 2026년 2월 논문에서 내린 결론입니다. 소속은 ETH 취리히입니다. 9월에 v3로 개정했습니다.

2월 v1 초록은 성공률이 낮아지는 경향을 적었습니다. 6월 개정부터 표현이 바뀌었습니다. 대체로 올리지 못한다는 표현입니다. 파일에 uv가 있으면 작업 하나에 평균 1.6번 씁니다. 없으면 평균 0.01번 미만입니다. uv는 파이썬 패키지 도구입니다. 에이전트가 파일을 읽고 따른 증거입니다.

남는 질문은 지시를 따르면 문제도 더 잘 푸느냐입니다. 2026년 1월부터 7월까지 처음 제출된 연구가 이 질문을 쟀습니다. 연구는 세 편입니다. 기준은 연구마다 다릅니다. 모델은 다음입니다.

## LLM이 만든 파일은 성공률을 올리지 못했다

<Term id="context-file">컨텍스트 파일</Term>이 있으면 더 잘한다고 흔히 생각합니다. 저장소를 처음 보는 에이전트에 안내서를 주는 셈입니다.

Gloaguen은 ETH 취리히 컴퓨터과학과 연구자입니다. 공저자는 네 명입니다. 같은 학과의 Martin Vechev가 있습니다. LogicStar.ai 연구자는 두 명입니다. 이 믿음을 직접 검증했습니다. 아래 Gloaguen 수치는 v3입니다.

시험한 조합은 네 가지입니다. 벤치마크는 둘입니다. <Term id="swe-bench">SWE-bench</Term> Lite입니다. 작업은 300개입니다. 저장소는 11개입니다. 다른 하나는 CTXbench입니다. 연구진이 새로 만들었습니다. PR 5,694개에서 골랐습니다. 저장소는 12개입니다. 작업은 138개입니다.

LLM이 만든 파일은 성공률을 올리지 못했습니다. SWE-bench에서는 약 -0.5%p입니다. CTXbench에서는 약 -2%p입니다. 둘 다 우연과 구분되지 않았습니다. 개발자가 직접 쓴 파일은 CTXbench에서 약 +2.4%p입니다. 이 역시 우연과 구분되지 않았습니다. 개발자 파일과 LLM 파일의 차이는 유의했습니다.

| 비교 | p |
|---|---|
| 개발자 파일과 LLM 파일 | 3.8% |

<Quote source="gloaguen-2026">
providing context files does not generally improve task success rates
</Quote>


연구진은 개발사가 권하는 저장소 개요도 봤습니다. 개요가 있어도 PR 관련 파일을 더 빨리 찾지 못했습니다.

### 성공률은 그대로이고 행동과 비용이 바뀐다

성공률은 그대로였습니다. 달라진 것은 에이전트의 행동입니다. 파일이 있으면 테스트를 더 자주 돌립니다. 파일도 더 많이 읽습니다. 저장소 전용 도구도 더 씁니다.

<Term id="inference-cost">추론 비용</Term>이 늘었습니다. LLM이 만든 파일의 평균 비용은 SWE-bench에서 약 20% 늘었습니다. CTXbench에서는 약 23% 늘었습니다. 둘 다 유의한 차이입니다. 개발자가 쓴 파일은 단계를 평균 3.34개 늘렸습니다. 비용은 최대 19% 늘었습니다.

추론 토큰도 늘었습니다. GPT-5.2에서 잰 값은 다음입니다. 표는 GPT-5.2 추론 토큰입니다.

| 파일 | SWE-bench Lite | CTXbench |
|---|---|---|
| LLM 작성 | 약 +22% | 약 +14% |
| 개발자 작성 | 해당 없음 | 약 +20% |

개발자가 쓴 파일은 CTXbench에만 있습니다. 그래서 SWE-bench 칸은 비어 있습니다.

<KeyIdea title="행동은 바뀌고 성공률은 그대로입니다">
에이전트는 적힌 도구를 더 씁니다. 테스트도 더 돌립니다. 성공률은 오르지 않았습니다. 비용만 늘었습니다.
</KeyIdea>

## AGENTS.md가 있으면 시간은 줄고 정답은 재지 않았다

비용 대신 시간을 본 연구는 결과가 조금 달랐습니다. Jai Lal Lulla와 Christoph Treude의 연구입니다. 소속은 싱가포르경영대학교입니다(Singapore Management University).

함께 쓴 곳은 하이델베르크대입니다. 밤베르크대도 있습니다. 킹스칼리지런던도 있습니다. 모두 여섯 명입니다. 2026년 1월에 처음 제출했습니다. 3월에 개정했습니다. 이 글의 수치는 v1과 v2가 같습니다.

Codex로 10개 저장소의 PR 124개를 돌렸습니다. 같은 작업을 AGENTS.md 유무로 짝지었습니다. 있으면 실행 시간 중앙값이 28.64% 낮았습니다. 출력 토큰 중앙값은 16.58% 적었습니다.

이 연구는 정답 여부를 평가하지 않았습니다. 무작위로 고른 결과물 50개만 직접 열었습니다. 비어 있거나 엉뚱한 수정이 아닌지 봤습니다. 저자들은 이 차이를 연관이라고 부릅니다. 영어로는 associated입니다. 에이전트는 Codex 하나입니다. 작업 설명은 LLM이 PR을 보고 만들었습니다.

두 연구는 잰 대상이 다릅니다. Gloaguen은 성공률과 비용을 쟀습니다. Lulla는 실행 시간과 출력 토큰을 쟀습니다. 한쪽이 다른 쪽을 뒤집는다고 보기는 어렵습니다. 성공률을 에이전트 두 종류로 다시 잰 연구는 7월에 나왔습니다.

## 주는 방식을 바꿔도 성공률은 그대로였다

2026년 7월 28일 Prakhar Khatri가 논문을 올렸습니다. 독립 연구자이고 혼자 썼습니다. <Term id="ablation-study">절제 연구</Term>입니다. 세 연구 중 처음 제출은 가장 늦습니다. Gloaguen v3 개정은 9월입니다.

Khatri는 두 에이전트에 같은 작업 15개를 맡겼습니다. Codex에는 2개를 더 줬습니다. 에이전트는 Claude Code와 Codex CLI입니다. 대상은 Python 레포 3개입니다.

- pdm
- firebase-admin-python
- opshin

조건마다 3번씩 반복했습니다. 비교 조건은 셋입니다.

- none은 저장소 컨텍스트를 주지 않습니다.
- always_on은 AGENTS.md 전문을 매번 넣습니다.
- 위키 방식은 주제별 위키를 작업 공간에 둡니다. 에이전트가 필요할 때 읽습니다. 논문의 이름은 selective입니다.

위키와 AGENTS.md가 같은 저장소는 opshin뿐입니다. pdm은 자동으로 만든 더 넓은 위키를 썼습니다. firebase-admin-python도 그렇습니다. 분량은 AGENTS.md의 약 10배와 18배입니다.

성공률은 다음입니다.

| | none | always_on | 위키 |
|---|---|---|---|
| Claude | 53.3% | 55.6% | 55.6% |
| Codex | 58.8% | 56.9% | 52.9% |

<Quote source="khatri-2026">
Context strategy does not measurably move correctness on either agent
</Quote>


차이가 얼마나 작은지도 따졌습니다. <Term id="equivalence-testing">동등성 검정</Term>으로 보면 효과가 작습니다. Claude에서는 10%p 안쪽입니다. Codex에서는 15%p 안쪽입니다. 관측된 차이의 최댓값은 Claude 2.3%p입니다. Codex는 5.9%p입니다. none과 위키 방식 사이입니다. 표본이 작아 강한 동등성으로 내세우지 않습니다.

### 막힌 곳은 구현 단계다

실패 원인도 따로 봤습니다. 저장소 지식이 부족해서가 아니었습니다. 막힌 단계는 다음입니다.

- 기능을 설계합니다.
- 알맞은 패턴을 고릅니다.
- 코드를 정확히 잇습니다.

아슬아슬하게 실패한 작업 두 개를 다시 돌렸습니다. 실제 AGENTS.md를 줘도 통과하지 못했습니다.

### 효율에서는 작은 신호가 하나 남았다

효율에는 작은 신호가 하나 있습니다. opshin의 AGENTS.md는 전체 테스트가 20분 넘게 걸린다고 적습니다. 이 저장소에서 컨텍스트를 주면 Claude 시간이 짧아졌습니다. 약 24%입니다. 작업은 5개뿐입니다. 통계로 보면 유의하지 않습니다.

| 항목 | p |
|---|---|
| Claude 시간 | 0.125 | 전체 테스트를 다시 돌린 횟수도 줄었습니다. 작업 4개 중 3개입니다. 저자는 이 결과를 사후 탐색으로만 다룹니다.

논의에서는 비용과 지연에 쓸모가 있을 수 있다고 적습니다. 정답을 바꾸지 못해도 그렇습니다. 결론에서는 남은 효율 신호를 좁게 봅니다. 좁은 작업 방식의 변화일 뿐이라고 정리합니다.

## 한계
