# 목표: 내 에이전트 워크플로의 숨은 가정과 자기 평가를 점검하기

Anthropic Labs의 글(2026년 3월 24일)은 하네스의 모든 구성요소가 "모델이 혼자 못 한다"는 가정이며, 모델이 좋아지면 그 가정이 낡을 수 있다고 말합니다. 또 결과물을 만든 에이전트와 평가하는 에이전트를 나누고, 평가 에이전트가 실행 중인 결과물을 직접 조작해 채점하는 방식을 소개합니다.
이 키트는 이 레포의 에이전트 워크플로를 읽고 두 가지를 점검해 보고서로 남깁니다. 기본은 **읽기 전용 점검**입니다.

## 절대 지킬 것

- 에이전트 설정, 훅, 스크립트, 프롬프트 파일, 애플리케이션 코드를 수정하거나 삭제하지 않습니다. 단, 3단계에서 사용자가 승인한 지침 파일 한 곳에 규칙 한 줄을 추가하는 것은 예외입니다.
- 레포 밖 홈 설정(`~/.claude`, `~/.codex`)은 읽기만 하고 보고서에 내용을 옮기지 않습니다.
- 새 도구나 에이전트를 설치하지 않습니다.
- 비밀 값(키, 토큰)은 읽어도 출력하거나 보고서에 적지 않습니다.
- `CLAUDE.local.md`와 `.claude/settings.local.json`은 읽되 보고서에는 파일 경로와 단계 이름만 적고 내용은 옮기지 않습니다.

## 0. 맞는지 먼저 판단하기

아래를 확인합니다. 해당하지 않으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알립니다.

- 이 레포에 코딩 에이전트용 지침이나 워크플로가 있는지 확인합니다. 아래 위치를 찾습니다.
  - 지침 파일: `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/AGENTS.md`, `CLAUDE.local.md`, 디렉터리별 `AGENTS.override.md`(하위 폴더의 `AGENTS.md`도 읽습니다)
  - `.claude/` 아래: `rules/`, `agents/`, `skills/`, `settings.json`, `settings.local.json`(훅 설정)
  - `.cursor/rules/*.mdc`
  - 레포 안의 훅, 스크립트, 프롬프트 파일
  - 홈 설정: `~/.codex/AGENTS.override.md`(있으면 이것이 우선) 또는 `~/.codex/AGENTS.md`. 읽기만 합니다.
  - 홈 설정만 있는 경우는 이 레포에 맞다는 근거로 세지 않습니다.
- 에이전트에게 여러 단계로 나눈 작업을 시키고 있거나 그럴 계획인지 확인합니다. 한 번에 끝나는 단순 작업뿐이면 점검할 것이 없다고 알리고 멈춥니다.

## 1. 단계 목록 만들기 (읽기 전용)

파일을 읽어서 에이전트 워크플로의 단계를 나열합니다. 없는 파일은 "없음"으로 적습니다. 추측하지 말고 실제 파일에서 확인한 내용만 적습니다.

각 단계마다 아래 다섯 가지를 표로 적습니다.

- 단계 이름과 근거 파일
- 이 단계가 모델이 혼자 못 한다고 가정하는 것 (예: "한 번에 끝까지 못 한다", "자기 코드의 오류를 못 찾는다")
- 이 단계의 결과물을 만드는 쪽과 검증하는 쪽이 같은가
- 완료 기준이 실행으로 확인되는가, 아니면 에이전트의 자기 보고에 의존하는가
- 완료 기준을 작업 시작 전에 문서나 파일로 정했는가, 검증이 코드를 읽는 것에 그치는가 아니면 실행·조작(테스트, 앱 실행, 브라우저 조작)까지 하는가

## 2. 진단하기

- **자기 평가**: 만든 쪽이 스스로 "다 됐다"고 판단하는 단계를 표시합니다. 에이전트가 코드를 읽고 "문제 없음"이라고 판단하는 단계는 자기 평가로 표시합니다. 테스트, 린트, 앱 실행처럼 실행 결과로 확인하는 단계는 에이전트의 판단과 독립적이므로 자기 평가로 보지 않습니다(별도 평가 에이전트가 있다는 뜻은 아닙니다).
- **낡았을 수 있는 가정**: 모델이 좋아져서 더 이상 필요 없을 수 있는 단계를 후보로 표시합니다. 단, 이 글의 비용·시간 수치를 이 레포의 예측으로 쓰지 않습니다. 후보는 "하나씩 빼서 결과를 비교해 볼 대상"일 뿐입니다.
- **실행으로 확인되는 기준**: 완료 기준이 문장뿐이고 실행 명령이 없는 항목을 표시합니다. 실행할 후보 명령은 이 단계에서 이름만 적고, 실제 실행은 3단계 승인을 받은 뒤에 합니다. 명령은 추측하지 말고 레포에서 실제로 확인합니다.
  - 파일을 바꾸지 않는다고 package.json·Makefile에서 확인한 테스트·린트·타입 검사 명령만 후보로 삼습니다.
  - 스크립트 본문에 `--fix`, `--write`, `--update`, `--coverage`, 빌드, 설치가 있거나 캐시·산출물을 쓰는 옵션이 있으면 후보에서 뺍니다.
  - 실행 전 해당 스크립트와 pre/post 스크립트가 파일 쓰기, 빌드, DB, 외부 네트워크를 쓰지 않는지 확인합니다. 확신이 없으면 실행하지 말고 이름만 적습니다.
  - 그 밖의 명령(스냅샷 갱신, `--fix`, `--write`, 빌드, 설치, 포맷)은 실행하지 않습니다.
  - 실행 직후 `git status --short --ignored`에 새 파일이 나오면 지우지 말고 경로를 보고서에 적고 사용자에게 알립니다. 저장소가 git이 아니면 명령 실행 전후의 파일 목록(`find` 결과)을 비교합니다.

## 3. 계획을 보여주고 승인받기

다음을 보여주고 **사용자의 승인을 받은 뒤에만** 4단계를 진행합니다.

- 1~2단계 결과 요약 표와 실행할 명령 목록
- 만들 보고서 파일: `docs/harness-assumptions.md`
- `docs/`가 없으면 만들어도 되는지 함께 승인받습니다.
- 선택 항목: 지침 파일 한 곳에 규칙 한 줄 추가 (예: "완료를 선언하기 전에, 코드를 읽은 판단이 아니라 테스트나 앱 실행 결과로 확인한다"). 대상은 하나만 고릅니다. 우선순위는 다음과 같습니다.
  1. 먼저 `CLAUDE.md`·`.claude/CLAUDE.md`와 `AGENTS.md`가 둘 다 있고 불러오기(`@AGENTS.md`)가 없으면 3번으로 갑니다. 그 밖에 `CLAUDE.md`(또는 `.claude/CLAUDE.md`)가 있으면 그 파일에, 그 파일이 `@AGENTS.md`를 불러오면 `AGENTS.md`에 넣습니다.
     - `CLAUDE.md`와 `.claude/CLAUDE.md`가 둘 다 있으면 `@AGENTS.md`를 불러오는 쪽이 있을 때 `AGENTS.md`, 없을 때 루트 `CLAUDE.md`를 고르고 어느 쪽인지 승인 요청에 적습니다.
  2. `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`가 모두 없고 `AGENTS.md`(또는 `.claude/AGENTS.md`)만 있으면 그 파일에 넣습니다.
  3. `CLAUDE.md`와 `AGENTS.md`가 둘 다 있고 불러오기가 없으면 어느 쪽에 넣을지 사용자에게 묻습니다. `CLAUDE.md`와 `.claude/CLAUDE.md`는 없고 `CLAUDE.local.md`만 있으면(`AGENTS.md`가 있든 없든) 이 항목은 건너뜁니다. `CLAUDE.local.md` 자체는 대상으로 고르지 않습니다.
  - 아무것도 없으면 파일을 새로 만들지 말고 한 줄 추가 항목을 건너뜁니다.
  - Claude Code(v2.1.277 이상)는 기본 설정(Project instructions = claude-md-or-agents-md)에서 작업 디렉터리나 상위에 `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md` 중 하나라도 있으면 그 파일들만 읽고, 하나도 없을 때만 `AGENTS.md`를 읽습니다(2026년 11월 공식 문서 기준, https://code.claude.com/docs/en/memory). 따라서 그 파일들이 있는데 `AGENTS.md`에 넣은 규칙은 불러오기가 없으면 Claude Code에 적용되지 않습니다. 승인 요청에는 이 한 줄을 반드시 적습니다. 선택한 파일이 `CLAUDE.md`이면 Codex에는 적용되지 않고, `AGENTS.md`이면 Claude Code는 불러오기가 있거나 `CLAUDE.md`·`.claude/CLAUDE.md`·`CLAUDE.local.md`가 모두 없을 때만 읽습니다.

사용자가 승인하지 않거나 답이 없으면 4단계를 하지 말고 파일을 하나도 만들지 않은 채 대화에서 요약 표만 보여 주고 끝냅니다. 일부만 승인하면 승인한 항목만 합니다.

## 4. 승인된 범위만 적용하기

- `docs/harness-assumptions.md`가 이미 있으면 덮어쓰지 말고 알린 뒤 다른 이름을 승인받습니다.
- `docs/harness-assumptions.md`를 만듭니다. 점검 날짜, 단계 표, 자기 평가로 보이는 단계, 줄여 볼 후보, 실행으로 확인되지 않는 완료 기준, 실행한 명령(없으면 "실행 안 함")과 각 명령 직후 `git status` 결과를 담습니다.
- 사용자가 승인한 경우에만 지침 파일에 규칙 한 줄을 추가합니다. 다른 내용은 건드리지 않습니다.

## 5. 실행해서 확인하기

- 보고서의 단계 표가 실제 파일 내용과 맞는지 파일 경로로 다시 대조합니다.
- 지침 파일을 고쳤다면 `git diff`로 추가한 줄이 승인한 한 줄뿐인지 확인합니다.
- `git status --short`로 바뀐 파일이 `docs/harness-assumptions.md`와 승인한 지침 파일뿐인지 확인합니다. git 저장소가 아니면 확인을 건너뛰지 말고 작업 전후 파일 목록을 비교합니다.
- 실제로 만든 보고서 경로에 대해 `grep -nEi "(sk-[A-Za-z0-9]{16,}|ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|xox[baprs]-|-----BEGIN|(api[_-]?key|token|secret|password)\s*[:=])" <보고서 경로>`에 아무것도 나오지 않는지 확인합니다. 이 검사는 흔한 패턴만 잡으므로 보고서를 한 번 눈으로도 읽습니다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고합니다.
