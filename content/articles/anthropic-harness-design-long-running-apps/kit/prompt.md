# 목표: 내 에이전트 워크플로의 숨은 가정과 자기 평가를 점검하기

Anthropic Labs 팀의 Prithvi Rajasekaran이 쓴 글(2026년 3월 24일)은 하네스의 모든 구성요소에 "모델이 혼자 못 한다"는 가정이 담겨 있으며, 모델이 좋아지면 그 가정이 낡을 수 있다고 말한다. 결과물을 만든 쪽과 평가하는 쪽을 나누는 것은 강력한 수단이지만 평가 쪽도 LLM이라 관대함이 바로 사라지지는 않았고, 하네스를 줄일 때는 구성요소를 한 번에 하나씩 빼며 영향을 살피라고 한다.
이 키트는 이 레포의 에이전트 워크플로를 읽어 가정을 표로 남기고, **실제 워크플로 하나**에 대해 maker≠evaluator 분리 제안만 보고서에 적는다. 기본은 **읽기 전용 점검**이다. 지침 파일에 한 줄을 덧붙이지 않는다.

## 절대 지킬 것

- 에이전트 설정, 훅, 스크립트, 프롬프트 파일, 지침 파일, 애플리케이션 코드를 수정하거나 삭제하지 않는다.
- 레포 밖 홈 설정(`~/.claude`, `~/.codex`)은 읽기만 하고 보고서에 내용을 옮기지 않는다.
- 새 도구나 에이전트를 설치하지 않는다. 평가 에이전트·새 하네스를 실제로 만들지 않는다.
- 비밀 값(키, 토큰)은 읽어도 출력하거나 보고서에 적지 않는다.
- `CLAUDE.local.md`와 `.claude/settings.local.json`은 읽되 보고서에는 파일 경로와 단계 이름만 적고 내용은 옮기지 않는다.

## 0. 맞는지 먼저 판단하기

아래를 확인한다. 해당하지 않으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알린다.

- 이 레포에 코딩 에이전트용 지침이나 워크플로가 있는지 확인한다.
  - 지침: `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/AGENTS.md`, `CLAUDE.local.md`, 디렉터리별 `AGENTS.override.md`
  - `.claude/` 아래: `rules/`, `agents/`, `skills/`, `settings.json`, `settings.local.json`
  - `.cursor/rules/*.mdc`
  - 레포 안의 훅, 스크립트, 프롬프트 파일
  - 홈 설정은 읽기만 하며, 홈만 있는 경우는 이 레포에 맞다는 근거로 세지 않는다.
- 에이전트에게 여러 단계로 나눈 작업을 시키고 있거나 그럴 계획인지 확인한다. 한 번에 끝나는 단순 작업뿐이면 멈추고 알린다.

## 1. 단계 목록 만들기 (읽기 전용)

파일을 읽어 에이전트 워크플로 단계를 나열한다. 추측하지 말고 실제 파일에서 확인한 내용만 적는다. 각 단계마다 표로:

- 단계 이름과 근거 파일
- 이 단계가 모델이 혼자 못 한다고 가정하는 것
- 결과물을 만드는 쪽과 검증하는 쪽이 같은가
- 완료 기준이 실행으로 확인되는가, 아니면 에이전트의 자기 보고에 의존하는가
- 완료 기준을 작업 시작 전에 문서·파일로 정했는가, 검증이 코드 읽기에 그치는지 실행·조작까지 하는가

## 2. 진단하기

- **자기 평가**: 만든 쪽이 스스로 "다 됐다"고 판단하는 단계. 코드를 읽고 "문제 없음"이라고 하는 단계는 자기 평가다. 테스트·린트·앱 실행처럼 실행 결과로 확인하면 자기 평가로 보지 않는다(별도 평가 에이전트가 있다는 뜻은 아니다).
- **낡았을 수 있는 가정**: 모델이 좋아져서 빼 볼 수 있는 단계 후보. 글의 비용·시간 수치를 이 레포 예측으로 쓰지 않는다. "하나씩 빼서 비교해 볼 대상"으로만 적는다.
- **실행으로 확인되는 기준**: 완료 기준이 문장뿐이고 실행 명령이 없는 항목. 후보 명령은 이름만 적고, 실행은 3단계 승인 뒤에만 한다. 파일을 바꾸지 않는다고 확인한 테스트·린트·타입 검사만 후보로 삼는다. `--fix`/`--write`/`--update`/빌드/설치가 있거나 확신이 없으면 실행하지 않는다. 실행 직후 `git status --short --ignored`에 새 파일이 나오면 지우지 말고 경로를 적는다.

## 3. maker≠evaluator 제안 초안 (읽기 전용)

1~2단계에서 고른 **실제 다단계 워크플로 하나**에 대해 제안만 적는다. 구현하지 않는다.

- 지금: 누가 만들고 누가 검증하는가 (같은 에이전트 / 같은 세션 / 사람)
- 제안: 만드는 단계와 평가하는 단계를 어떻게 나눌지 (역할, 입력, 채점 기준이 실행으로 확인되는지)
- 한계: 평가 쪽도 LLM이면 관대할 수 있음 → 평가 프롬프트·채점 기준을 여러 번 고쳐 볼 여지
- 줄이기: 나중에 한 구성요소씩 빼며 재평가하라는 주의

## 4. 계획을 보여주고 승인받기

다음을 보여주고 **승인을 받은 뒤에만** 5단계를 진행한다. 가정 보고서와 분리 제안 파일을 **각각** 승인받고, 승인되지 않은 항목은 건너뛴다.

- 1~3단계 결과 요약 표와 실행할 명령 목록
- `docs/harness-assumptions.md`
- `docs/harness-split-proposal.md` (이미 있으면 날짜 접미사)
- `docs/`가 없으면 만들어도 되는지 함께 승인받는다.

승인하지 않으면 파일을 만들지 않고 대화에서 요약 표만 보여 주고 끝낸다.

## 5. 승인된 범위만 적용하기

- 승인한 경우 `docs/harness-assumptions.md`를 만든다(이미 있으면 다른 이름 승인). 점검 날짜, 단계 표, 자기 평가 단계, 줄여 볼 후보, 실행으로 확인되지 않는 완료 기준, 실행한 명령(없으면 "실행 안 함")과 직후 `git status`를 담는다.
- 승인한 경우 `docs/harness-split-proposal.md`에 3단계 제안만 담는다. 구현·설치는 하지 않는다.
- 지침 파일·훅·스크립트는 수정하지 않는다.

## 6. 실행해서 확인하기

- 보고서의 단계 표가 실제 파일 내용과 맞는지 경로로 다시 대조한다.
- `git status --short`로 바뀐 파일이 보고서뿐인지 확인한다. git이 아니면 작업 전후 파일 목록을 비교한다.
- 보고서에 대해 `grep -nEi "(sk-[A-Za-z0-9]{16,}|ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|xox[baprs]-|-----BEGIN|(api[_-]?key|token|secret|password)\s*[:=])" <보고서 경로>`에 아무것도 나오지 않는지 확인하고, 흔한 패턴만 잡으므로 한 번 눈으로도 읽는다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고한다.
