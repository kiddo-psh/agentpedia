화면만 봐서는 끊긴 곳이 보이지 않습니다. Prithvi Rajasekaran이 2026년 3월 24일 Anthropic Labs 글에 적었습니다. Rajasekaran은 Claude의 프런트엔드 디자인 스킬을 다룹니다. 장시간 코딩 하네스도 다룹니다.

주문은 2D 레트로 게임 메이커 한 문장이었습니다. 넣을 기능은 네 가지입니다.

- 레벨 편집기
- 스프라이트 편집기
- 엔티티 동작
- 직접 플레이하는 테스트 모드

에이전트 하나가 20분 동안 9달러를 썼습니다. 화면은 그럴듯했습니다. 엔티티는 입력에 반응하지 않았습니다. 코드를 열어 보니 엔티티 정의와 게임 런타임 사이 배선이 끊겨 있었습니다.

## 셋을 나누자 플레이가 된다

같은 주문을 세 갈래로 나눈 틀이 <Term id="agent-harness">하네스</Term>입니다.

- 계획
- 생성
- 평가

6시간과 200달러 끝에 플레이 모드가 동작했습니다. 모델은 Opus 4.5입니다. 실험 시작 당시 최고 코딩 모델이었습니다. 글은 에이전트를 더 붙이는 쪽으로 가지 않습니다. 비용을 적은 뒤 하네스를 의심합니다.

## 만든 쪽의 칭찬을 평가 쪽이 맡는다

남은 실패는 두 가지입니다.

- 컨텍스트 창이 차면 일관성이 무너집니다.
- 평범한 결과도 에이전트가 자신 있게 칭찬합니다.

컨텍스트 창은 한 번에 기억하는 분량입니다. 검증 가능한 작업에서도 판단이 어긋납니다.

<Quote source="anthropic-harness-design">
Separating the agent doing the work from the agent judging it proves to be a strong lever to address this issue.
</Quote>

만드는 쪽과 <Term id="evaluator-agent">평가 에이전트</Term>를 나눕니다. 평가 쪽도 대규모 언어 모델이라 점수가 후합니다. 그래도 평가 프롬프트를 다듬기가 더 쉽습니다. 생성 쪽이 결과를 비판하게 하는 일보다 쉽습니다. 고칠 대상도 분명해집니다.

## 디자인 평가가 도약을 끌어낸다

게임보다 먼저 프런트엔드 디자인에서 시험했습니다. 기준은 네 가지이고, 양쪽이 함께 받았습니다.

- 디자인 품질
- 독창성
- 완성도
- 기능성

완성도와 기능성은 기본으로 잘했습니다. 비중은 디자인 품질과 독창성에 더 뒀습니다. 평가 쪽은 점수 해설이 붙은 예시로 기준을 맞췄습니다. <Term id="playwright-mcp">Playwright MCP</Term>로 살아 있는 페이지를 조작했습니다. 그런 다음 점수와 비평을 냈습니다. 생성 쪽은 평가마다 다듬을지 바꿀지 고릅니다. 한 번에 5~15번 반복했습니다. 길게는 네 시간이 걸렸습니다.

네덜란드 미술관 사이트가 사례입니다. 아홉 번째에는 어두운 랜딩 페이지가 나왔습니다. 기대한 범위 안이었습니다. 열 번째에 그 페이지를 버렸습니다. CSS 원근법으로 체크무늬 바닥의 3D 전시실을 만들었습니다. 작품은 벽에 자유롭게 걸립니다. 문으로 전시실을 오갑니다. 한 번에 만드는 방식에서는 이런 도약이 없었습니다.

기준 문구가 결과를 비슷한 모양으로 몰았습니다. "최고의 디자인은 미술관 수준이다"가 그 예입니다. 점수는 대체로 올랐습니다. 오름은 일직선이 아니었습니다. 마지막보다 중간 반복이 나은 때도 잦았습니다.

## 앱은 계약으로 시험 범위를 고정한다

한 화면과 돌아가는 앱은 다릅니다. 같은 구조를 Opus 4.5로 앱 전체에 넓혔습니다. 계획 쪽은 짧은 요청을 명세로 키웁니다. 길이는 한 문장에서 네 문장 사이입니다. 범위는 크게 잡습니다. 초점은 제품 맥락과 큰 틀의 기술입니다. 세부 구현은 미리 정하지 않습니다. 이른 결정이 틀리면 아래로 번집니다. AI 기능도 넣으라고 했습니다.

생성 쪽이 만들 것과 확인 방법을 제안합니다. 평가 쪽과 합의할 때까지 고칩니다. 이 합의가 <Term id="sprint-contract">스프린트 계약</Term>입니다. 명세가 큰 그림이라 이 단계가 필요했습니다. 레벨 편집기 3번 스프린트의 기준은 27개였습니다.

코드는 계약 뒤에 씁니다. 생성 쪽이 점검한 뒤 넘깁니다. 평가 쪽은 앱을 사용자처럼 클릭합니다. 시험은 세 곳입니다.

- 화면
- API
- 데이터베이스 상태

채점 기준은 네 가지입니다.

- 제품 깊이
- 기능성
- 시각 디자인
- 코드 품질

기준마다 하한선이 있습니다. 하나라도 못 넘으면 그 스프린트는 실패입니다. 에이전트끼리는 파일로 소통합니다.

## 플레이는 됐지만 벽과 안내가 빠진다

Opus 4.5 하네스는 기능을 16개로 늘렸습니다. 스프린트는 10개입니다. 캔버스는 화면 전체를 썼습니다. 패널 크기도 알맞았습니다. 스프라이트 편집기는 더 풍부했습니다. 앱 안에서 말로 게임의 부분을 만들었습니다. 엔티티를 움직여 플레이했습니다. 단독 실행은 거기까지 가지 못했습니다.

물리가 거칠어 캐릭터가 플랫폼과 겹쳤습니다. AI 레벨에는 넘을 수 없는 큰 벽이 있었습니다. 레벨을 만드는 방식의 한계입니다. 앱은 스프라이트와 엔티티부터 만들라고 안내하지 않았습니다. 기반 모델의 제품 감각이 부족한 부분입니다.

<Quote source="anthropic-harness-design">
The harness was over 20x more expensive, but the difference in output quality was immediately apparent.
</Quote>

비용은 20배가 넘었습니다. 품질 차이는 한눈에 보였습니다.

사각형 채우기는 드래그 양 끝에만 타일을 놓았습니다. `/frames/reorder`가 `/{frame_id}`보다 뒤에 있었습니다. 서버는 reorder를 프레임 번호로 읽어 422 오류를 냈습니다. 요청 값을 처리하지 못한 응답입니다.

기본 상태의 평가는 두 문제가 있었습니다.

- 문제를 찾고도 통과시켰습니다.
- 시험은 겉핥기였습니다.

<KeyIdea title="평가 프롬프트는 로그와 함께 고칩니다">
평가 로그를 읽고, 판단과 어긋난 사례를 프롬프트에 반영했습니다. 여러 번 고친 뒤에도 놓친 것이 있습니다.

- 사소한 레이아웃
- 직관적이지 않은 조작
- 깊이 중첩된 기능의 버그

평가 단계를 넣으면 이 손보기도 맡습니다.
</KeyIdea>

## 모델이 나아지면 리셋은 빠진다

<Quote source="anthropic-harness-design">
every component in a harness encodes an assumption about what the model can't do on its own
</Quote>

구성요소마다 혼자 못 한다는 가정이 들어 있습니다. 가정은 처음부터 틀리기도 합니다. 모델이 나아지면 낡기도 합니다. 이 생각은 2024년 12월 Building Effective Agents와 이어집니다. 그 글은 가장 단순한 해법부터 시작합니다. 복잡도는 필요할 때만 올립니다.

앞선 장시간 하네스의 모델은 Sonnet 4.5입니다. 그 리셋은 이번 Opus 4.5 하네스에 없습니다. <Term id="context-reset">컨텍스트 리셋</Term>은 창을 비웁니다. 새 에이전트는 구조화된 인수인계 문서를 받습니다. <Term id="compaction">컴팩션</Term>은 대화를 줄여 같은 에이전트가 이어 갑니다.

일부 모델은 한계가 가깝다고 믿으면 작업을 서두릅니다. 이름은 <Term id="context-anxiety">컨텍스트 불안</Term>입니다. Sonnet 4.5는 이 경향이 강했습니다. 컴팩션만으로는 부족했습니다. 리셋이 필수였습니다. 대가는 세 가지입니다.

- 에이전트 사이 조율이 복잡해집니다.
- 토큰이 더 듭니다.
- 지연이 늘어납니다.

Opus 4.5는 이 경향을 대체로 없앴습니다. 그래서 Opus 4.5 하네스는 리셋을 쓰지 않습니다. 컨텍스트 관리는 남았습니다. 컨텍스트가 차면 Claude Agent SDK가 압축합니다. 빌드 전체는 한 세션으로 이어 갔습니다. SDK는 Claude Code의 세 가지를 코드에서 부릅니다.

- 도구
- 에이전트 루프
- 컨텍스트 관리

언어는 Python과 TypeScript입니다.

## 한 번에 줄인 시도는 실패한다

크게 덜어내고 새 아이디어를 넣었지만 원래 결과가 나오지 않았습니다. 어느 부분이 결과를 좌우하는지도 알 수 없었습니다. 그래서 구성요소를 한 번에 하나씩 뺐습니다. 뺄 때마다 최종 결과를 비교했습니다.

Opus 4.5로 첫 결과를 낸 뒤 줄이는 중에 Opus 4.6이 나왔습니다. 4.6의 출시 글이 적은 변화는 세 가지입니다.

- 계획을 더 신중하게 합니다.
- 작업을 더 오래 이어 갑니다.
- 코드 리뷰와 디버깅이 나아집니다.

이 출시가 하네스를 줄일 이유를 하나 더 보탰습니다.

처음 뺀 것은 스프린트 구성입니다. 계획 쪽과 평가 쪽은 남겼습니다. 계획이 없으면 명세 없이 바로 만들기 시작합니다. 범위는 작아집니다. 기능도 덜해집니다.

## 평가는 혼자 못 하는 일에서만 값을 한다

평가를 빌드 뒤 한 번으로 옮겼습니다. 4.5에서는 한계 근처의 문제를 잡았습니다. 4.6에서는 혼자 하는 범위가 넓어졌습니다. 그 안쪽의 평가는 낭비가 됐습니다.

<Quote source="anthropic-harness-design">
The practical implication is that the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo.
</Quote>

평가를 둘지는 모델이 바뀔 때마다 다시 묻습니다.

### 줄인 하네스의 평가 비용은 10% 미만이다

브라우저 DAW를 Web Audio API로 만들게 했습니다. 하는 일은 세 가지입니다.

- 작곡
- 녹음
- 믹싱

생성 쪽은 두 시간 넘게 작업했습니다. Opus 4.5 때 필요했던 스프린트 분할은 없었습니다. 결과는 3시간 50분입니다. 비용은 124.70달러입니다.

| 단계 | 시간 | 비용 |
|---|---|---|
| 계획 | 4.7분 | $0.46 |
| 생성 1차 | 2시간 7분 | $71.08 |
| 평가 1차 | 8.8분 | $3.24 |
| 생성 2차 | 1시간 2분 | $36.89 |
| 평가 2차 | 6.8분 | $3.09 |
| 생성 3차 | 10.9분 | $5.88 |
| 평가 3차 | 9.6분 | $4.06 |

혼자 어려운 곳에서는 평가가 도움이 됐습니다. 평가 세 번의 합은 10.39달러입니다. 전체 124.70달러의 10%가 안 됩니다. 1차가 찾은 빈틈은 세 가지입니다.

- 클립을 끌지 못했습니다.
- 악기 UI가 없었습니다.
- 시각 효과 편집기가 없었습니다.

2차가 찾은 빈틈도 세 가지입니다.

- 녹음은 껍데기뿐이었습니다.
- 클립 크기 조절이 없었습니다.
- 분할이 없었습니다.

Claude는 소리를 듣지 못합니다. 음악 취향을 채점하는 일은 약했습니다. 앱은 전문가용과 거리가 멉니다. 프롬프트만으로 짧은 곡이 하나 나왔습니다. 곡의 요소는 여섯 가지입니다.

- 템포
- 조성
- 멜로디
- 드럼 트랙
- 믹서 레벨
- 리버브

## 한계는 비교 한 쌍에 있다

숫자 비교는 게임 메이커 한 쌍입니다. DAW에는 단독 실행과 견준 숫자가 없습니다. 품질 판단은 인상입니다. 반복 실행과 평가 점수는 공개되지 않았습니다. 이 비용을 다른 프로젝트에 그대로 넣기는 어렵습니다. DAW에 쓴 모델 이름은 공개되지 않았습니다. 빌드 뒤 한 번이라는 말과 표의 세 번은 이어지지 않습니다.

결론은 하네스를 줄이라는 말이 아닙니다.

- 쓰는 모델로 실험하고 로그를 읽습니다.
- 복잡한 작업은 쪼개고, 부분마다 전문 에이전트를 붙여 봅니다.
- 새 모델이 나오면 필요 없는 단계는 빼고, 새 단계는 더합니다.

<Quote source="anthropic-harness-design">
the space of interesting harness combinations doesn't shrink as models improve.
</Quote>

조합은 줄지 않고 자리만 옮깁니다. 다음 조합을 찾는 일이 AI 엔지니어의 일입니다. 어느 단계가 플레이를 살렸는지는 20분 실행과 6시간 실행을 떼어 재지 않았습니다. 후보는 세 가지입니다.

- 계획
- 스프린트 계약
- 평가

다음 모델에 필요한지는 하나씩 빼 봐야 압니다.
