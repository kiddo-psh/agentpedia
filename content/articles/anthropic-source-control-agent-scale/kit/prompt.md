# 목표: 에이전트 규모에서 먼저 막힐 소스컨트롤·빌드·CI 병목 찾기

2026년 10월 Anthropic Engineering은 에이전트 덕에 코딩이 빨라지자 병목이 소스컨트롤·빌드·CI로 옮겨 갔다고 밝혔다. Scion 이전은 본문 맥락일 뿐, **일반 레포에 git 대체를 권하지 않는다.**
이 키트는 이 레포에서 에이전트 규모로 먼저 막힐 SC·빌드·CI 병목만 진단해 보고서로 남긴다. 기본은 **읽기 전용 점검**이다.

## 절대 지킬 것

- 버전 관리 시스템, CI 설정, 애플리케이션 코드를 고치지 않는다.
- git 저장소를 다른 시스템으로 옮기자고 권하지 않는다. 원문 저자들도 Scion이 일반용 git 대체재가 아니라고 밝혔다.
- 비밀 값(토큰, 키)을 읽어도 출력하거나 보고서에 적지 않는다. 이름과 위치만 다룬다.
- 보고서에 근거 없는 수치를 적지 않는다. 확인한 값만 쓴다.

## 0. 맞는지 먼저 판단하기

- 이 레포에 CI 설정(`.github/workflows/`, `.gitlab-ci.yml`, `Jenkinsfile`, `.circleci/config.yml`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `.buildkite/` 등)이 있는지 확인한다.
- 위 파일이 없어도 README나 `package.json` 스크립트가 외부 CI를 가리키면, 멈추기 전에 사용자에게 CI 설정이 어디 있는지 묻는다.
- 그래도 없으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알린다. CI도 머지 규칙도 없는 레포는 이 키트의 대상이 아니다.

## 1. 읽어서 정리하기 (읽기 전용)

설정 파일과 git 기록만 읽는다. 읽기 전용 명령만 실행하고, 실행해서 확인한 값만 쓴다. 명령을 추측하지 않는다.

- CI 한 번이 하는 일: 체크아웃 방식(전체, 얕은 복제, 스파스), 의존성 설치, 빌드, 테스트의 순서와 캐시 사용
- 머지 규칙: 파일에서 읽을 수 있는 것(`.github/workflows/`의 `merge_group` 트리거, `CODEOWNERS`, 머지 방식 안내 문서)만 적는다. 브랜치 보호와 필수 체크 설정은 파일에 없으면 '확인 불가(저장소 설정 화면에서 확인 필요)'로 적고 추측하지 않는다. 읽기 전용 `gh api repos/{owner}/{repo}/branches/<기본 브랜치>/protection` 호출은 3단계 계획에 넣고 승인받은 뒤에만 한다. `<기본 브랜치>`는 `git symbolic-ref --short refs/remotes/origin/HEAD`로 얻는다(`{branch}` 자리표시자는 현재 체크아웃 브랜치로 바뀌므로 쓰지 않는다). 404나 403이 나오면 '보호 없음'으로 단정하지 말고 '확인 불가(권한 부족 또는 미설정)'로 적는다.
- 리뷰 규칙: 필수 승인 수, 코드 소유자 파일, 사소한 변경과 중요한 변경을 구분하는 규칙이 있는지
- 최근 변경량: 먼저 `git rev-parse --is-shallow-repository`로 이력이 잘렸는지 확인한다. 잘렸으면 '측정 불가'로 적는다. 아니면 `git log --first-parent --since='12 weeks ago' --format=%cs <기본 브랜치>`의 날짜를 주 단위로 세어 적고, 사용한 명령도 함께 적는다. 센 값은 '머지 방식에 따라 PR 수 또는 커밋 수에 가까운 근사치'라고 보고서에 적는다.

## 2. 병목 후보 꼽기

변경이 지금의 열 배가 된다고 가정하고, 아래 중 먼저 막힐 곳을 근거와 함께 꼽는다.

- CI 체크아웃과 의존성 설치에 드는 시간과 트래픽
- 머지 직렬화(머지 큐나 브랜치 최신화 요구)
- 사람 리뷰 대기
- 동시에 올라온 변경끼리의 충돌을 잡는 방법

각 후보에 "확인한 근거"와 "추측"을 구분해 적는다.

## 3. 계획을 보여주고 승인받기

다음을 보여주고 **사용자의 승인을 받은 뒤에만** 4단계를 진행한다. 승인하지 않으면 파일을 만들지 않고 1~2단계 요약만 출력한 뒤 끝낸다.

- 1~2단계 결과 요약
- 만들 보고서 파일: `docs/agent-scale-bottlenecks.md`
- 실제로 측정할 명령이 있다면 그 목록 (파일을 바꾸지 않는 명령만, 예: `git count-objects -vH`, `git rev-list --count HEAD`). 클론, 설치, 빌드처럼 파일을 만드는 명령은 이 키트에서 실행하지 않고, 사용자가 직접 재 볼 명령으로 보고서의 '다음에 확인할 일'에 적는다.

## 4. 승인된 범위만 적용하기

- `docs/agent-scale-bottlenecks.md`가 이미 있으면 덮어쓰지 말고 멈춰서 다른 파일명을 묻는다. `docs/` 폴더가 없으면 만들기 전에 사용자에게 알린다.
- 보고서에는 점검 날짜, 항목 표(CI 한 번이 하는 일·캐시 사용·머지 규칙·리뷰 규칙·최근 변경량), 병목 후보와 근거, 측정 절, 사용자가 다음에 확인할 일을 담는다.
- 3단계에서 승인된 측정 명령을 실행했다면 명령과 결과 수치를 보고서의 '측정' 절에 그대로 적는다. 승인하지 않았다면 이 절은 '측정하지 않음'으로 둔다.
- 다른 파일은 건드리지 않는다.

## 5. 실행해서 확인하기

- 보고서에 적은 명령과 수치를 실제로 다시 실행하거나 파일에서 다시 읽어 일치하는지 확인한다.
- `git status --porcelain`으로 새 파일이 `docs/agent-scale-bottlenecks.md`(와 새로 만든 `docs/`)뿐인지 확인한다.
- `grep -nE 'sk-[A-Za-z0-9]|ghp_|github_pat_|AKIA[0-9A-Z]{8}|xox[bp]-|-----BEGIN' docs/agent-scale-bottlenecks.md`가 아무것도 출력하지 않는지 확인한다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고한다.
