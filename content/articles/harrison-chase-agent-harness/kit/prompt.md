# 목표: 범용 하네스로 충분한지, 어떤 게이트·평가·트레이스가 비는지 점검하기

Harrison Chase의 인터뷰를 다룬 2026년 8월 Saytrace 요약은 에이전트를 모델, 하네스, 컨텍스트로 나누고, 실패가 모델 능력보다 공급된 컨텍스트 질 탓인 경우가 많다고 설명한다(2026년 8월 공개 요약 기준이며 이후 바뀌었을 수 있다). Saytrace는 요약이 직접 인용이 아니라고 밝혔고, Chase의 직접 발언은 확인되지 않았다. Chase는 처음엔 범용 하네스로 가치를 얻고, 사용 사례가 분명해지면 게이트와 점검 단계를 더하며, 미션 크리티컬이면 과제별 벤치마크(정확도·지연·비용)와 상세 트레이스로 컨텍스트가 어떻게 쌓였는지 보라고 한다.
이 키트는 그 틀로 이 레포의 에이전트 설정을 점검해 보고서로 남기고, 승인하면 실패·컨텍스트 기록 템플릿만 추가한다. **검증 명령을 지시 파일에 덧붙이는 일은 하지 않는다**(그건 Boris Cherny 키트 범위다). 기본은 **읽기 전용 점검**이다.

## 절대 지킬 것

- 기존 코드 로직, `CLAUDE.md`·`AGENTS.md`, 에이전트 훅, 미들웨어 구현은 수정하지 않는다.
- 외부 서비스에 가입하거나 트레이싱 도구를 설치하지 않는다.
- 홈 디렉터리(`~/`)의 전역 설정은 고치지 않는다. 필요하면 사용자가 직접 할 일을 보고서에 적는다.
- API 키, 토큰 값은 읽어서 출력하거나 파일에 적지 않는다.
- `git commit` 등 git 기록을 바꾸는 명령은 쓰지 않는다.

## 0. 맞는지 먼저 판단하기

아래에 해당하지 않으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알린다.

- 이 레포에서 코딩 에이전트를 쓴다. (`CLAUDE.md`, `AGENTS.md`, `.claude/`, `.codex/`, `.cursor/` 중 하나 이상으로 확인한다.)
- 테스트, 린트, 타입 검사 중 실행 가능한 검증 명령이 하나 이상 있다.

## 1. 컨텍스트 공급 점검 (읽기 전용)

- **고정 컨텍스트**: 매 세션 항상 로드되는 파일(`CLAUDE.md`, `AGENTS.md`, `.cursor/rules` 중 `alwaysApply: true`인 규칙)과 핵심 지시를 정리한다. 경로·조건이 붙은 규칙(`.claude/rules/`의 paths, Cursor의 globs·description)은 동적 컨텍스트로 분류한다.
- **동적 컨텍스트**: 작업 중 필요할 때 읽게 하는 것(`docs/`, 스킬, MCP 서버)을 정리한다.
- 고정 컨텍스트의 지시가 실제 레포와 어긋나는 곳(없는 경로, 바뀐 명령)을 표시한다.
- 하네스가 고정·동적 컨텍스트를 **언제** 넘기는지 단서가 있으면 적는다(훅, 규칙 적용 조건, 스킬 호출 시점). 없으면 "시점 불명"으로 적는다.

## 2. 게이트·평가·트레이스 점검 (읽기 전용)

- **게이트·점검 단계**: 승인 프롬프트, 권한 허용 목록, 훅, CI 게이트, 플랜 후 실행 같은 "여기서 멈춘다/검사한다" 단계가 있는지 찾고 근거 경로를 적는다. 없으면 "없음"으로 적고 만들지 않는다.
- **검증 명령**: `package.json`, `Makefile`, CI 설정에서 후보를 찾는다. 실행 전 `git status --short`를 기록한다. 파일을 쓰지 않는 린트·테스트·타입 검사만 실행한다. 상태를 바꾸는 명령(배포, 마이그레이션, 삭제, 파일을 쓰는 빌드, `--fix`, `--update`)은 실행하지 않는다. 실행 후 `git status --short`를 비교하고, 달라진 파일은 되돌리지 말고 보고한다.
- **평가·벤치마크**: 과제별 eval 스크립트·회귀 세트가 있으면 위치와 실행 명령을 적는다. 정확도 외에 **지연·토큰·비용**을 재는지도 적는다. 없으면 "없음"(만들지 않는다).
- **트레이스**: 도구 호출·프롬프트·컨텍스트가 어떻게 쌓였는지 볼 수 있는 곳(세션 로그 UI, 트레이싱 제품, 로컬 로그 경로)을 적는다. 모르면 "확인하지 못함". Chase 관점에서 "실패 시 컨텍스트 스택을 되짚을 수 있는가?"에 예/아니오로 답한다.

## 3. 범용 vs 맞춤 판정 (읽기 전용)

1~2단계를 바탕으로 한 줄 판정을 내린다. 추측으로 제품을 추천하지 않는다.

- **범용 하네스로 충분**: 게이트가 거의 없고, 실패가 드물며, 평가·트레이스 없이도 운영 가능하다.
- **게이트를 더할 시점**: 같은 실패가 반복되거나, 사용 사례가 분명해 특정 점검 단계가 필요해 보인다. 빠진 게이트 후보만 적는다(구현하지 않는다).
- **미션 크리티컬에 가깝다**: 평가(지연·비용 포함)나 트레이스 없이 바꾸기 위험한 흐름이다. 빠진 평가·트레이스만 적는다.

## 4. 계획을 보여주고 승인받기

다음을 보여주고 **사용자의 승인을 받은 뒤에만** 5단계를 진행한다. 보고서와 실패 기록 템플릿을 **각각** 승인받고, 승인되지 않은 항목은 건너뛴다.

- 1~3단계 결과 요약 표 (항목, 위치, 상태, 빠진 곳)와 범용 vs 맞춤 판정
- 만들 보고서: `docs/agent-harness-audit.md`
- 실패·컨텍스트 기록용 `docs/agent-failures.md` 템플릿을 만들지 여부
- 이미 존재하는 파일이 있으면 덮어쓰지 말고 알린다. 승인받은 경우에만 `-YYYY-MM-DD`를 붙인 새 파일로 쓴다.

## 5. 승인된 범위만 적용하기

- 승인한 경우에만 `docs/agent-harness-audit.md`를 만든다. 점검 날짜, 고정·동적 컨텍스트, 게이트·점검 단계, 검증 명령과 실행 결과, 평가·벤치마크와 지연·비용 여부, 트레이스 확인 위치, 범용 vs 맞춤 판정, 빠진 곳과 권장 조치를 담는다. **지시 파일에 검증 명령을 덧붙이지 않는다.**
- 승인한 경우에만 `docs/agent-failures.md`에 날짜, 증상, 에이전트가 받은 컨텍스트(고정·동적 요약), 트레이스에서 본 것, 원인, 고친 곳 칸이 있는 템플릿을 만든다.

## 6. 실행해서 확인하기

- 이번에 만들거나 수정한 모든 파일에 키나 토큰 값이 들어가지 않았는지 `sk-`, `ghp_`, `-----BEGIN` 패턴을 grep으로 찾는다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고한다.
