# 목표: 삭제 후보 한 건의 증거를 모아 보고서로 남기기

Rodrigo Roim은 2026년 10월 14일 OpenAI 개발자 블로그 글에서, Codex에게 정리를 맡기면서 사용 증거를 스스로 찾게 했고, 모델은 삭제마다 이유를 적었다고 썼다. 기사 claim은 **지우기 전에 증거를 모은다**는 순서다.
이 키트는 같은 순서를 한 건에만 따른다. **증거를 보고서로 남기고 코드는 지우지 않는다**(Astra가 지운 범위까지는 가지 않는다).

## 절대 지킬 것

- 코드, 설정, 플래그를 삭제하거나 수정하지 않는다. 삭제 범위는 보고서에 제안만 한다.
- 브랜치, 커밋, PR을 만들지 않는다.
- 운영 설정이나 외부 서비스에 접속해 값을 바꾸지 않는다.
- API 키, 토큰, 비밀번호의 값을 읽거나 보고서에 적지 않는다. 이름과 위치만 다룬다.
- 설치, 빌드, 배포, 포맷(`--fix`), 스냅샷 갱신 명령을 실행하지 않는다.

## 0. 맞는지 먼저 판단하기

- `git status --short -uall` 결과와 `git diff | git hash-object --stdin` 해시를 시작 시점 기준으로 기억해 둔다. 이미 바뀐 파일이 있어도 멈추지는 않지만, 마지막에 시작 시점과 비교한다.
- 현재 디렉터리가 git 레포이고 `git rev-parse --is-shallow-repository`가 `false`이며 `git log`로 변경 이력을 볼 수 있는지 확인한다. 얕은 복제이면 이력 증거는 "확인하지 못함"으로 적고, 이력이 핵심인 후보라면 멈추고 알린다.
- 삭제 후보가 될 만한 것(오래된 기능 플래그, 안 쓰는 함수·모듈, 끝난 실험 설정)이 하나라도 있는지 본다.

이 조건이 맞지 않으면 **아무것도 바꾸지 말고 멈춘 뒤** 이유를 알린다. 같은 이름의 `docs/deletion-evidence.md`가 이미 있으면 덮어쓰지 말고 `docs/deletion-evidence-2.md` 같은 새 이름을 제안하고 3단계에서 승인받는다. `docs/` 폴더가 없으면 3단계 계획에 폴더 생성을 적고 승인받은 뒤 만든다.

## 1. 후보 한 건 고르기

후보 3개를 찾아 사용자에게 보여 주고 한 건을 고르게 한다. 고르기 전에는 다음 단계로 가지 않는다.

## 2. 증거 모으기 (읽기 전용)

고른 후보에 대해 실제로 실행하거나 열어 확인한 것만 적는다. 추측한 결과는 쓰지 않는다.

- 정의 위치와 코드 안의 사용처. 이름이 문자열, 설정 파일, 리플렉션, 동적 호출로 쓰일 가능성도 함께 찾는다. 검색에서 `.env*`, `*.pem`, `*secret*` 같은 비밀 값 파일은 제외하고, 그런 파일에 이름이 있는지만 이름 단위로 보고한다.
- `git log`로 본 최근 변경 이력과 관련 커밋 메시지.
- 이 후보를 언급한 기록. 로컬 `git log --all --grep=<이름>`과 `git log -S<이름>`으로 먼저 찾고, 이슈와 PR은 이미 로그인된 읽기 전용 조회(예: `gh issue list --search`, `gh pr list --search`)로만 확인한다. 댓글, 라벨, 생성 같은 쓰기 동작은 하지 않는다. 조회할 수 없는 출처는 "확인하지 못함"으로 적는다.
- 코드에 박아 둔 기본값과 로컬 재정의는 "사용 중"의 증거로도 "미사용"의 증거로도 세지 않는다. 이름이나 주석에 `permanent`, `영구`, `killswitch` 같은 표시가 있으면 보고서의 "사람에게 넘길 질문"에 반드시 올린다.
- 킬스위치, 장애 대응, 안전장치로 남겨 둔 것일 가능성. 코드 주석, 이름, 문서에서 단서를 찾는다.
- 운영에서 실제로 쓰이는지 알려 주는 자료(로그, 프로파일링, 설정 콘솔)는 사용자에게 어디서 볼 수 있는지 묻는다. 직접 접속하지 않는다.

## 3. 계획을 보여주고 승인받기

다음을 보여 주고 **사용자의 승인을 받은 뒤에만** 보고서를 쓴다.

- 고른 후보와 모은 증거 요약
- 만들 보고서 파일: `docs/deletion-evidence.md`(또는 위에서 제안한 새 이름)
- 보고서에 담을 삭제 범위 제안(파일과 줄, 지우지 않는다는 점 명시)

승인하지 않으면 파일을 만들지 않고 종료한다. 수정 요청이 있으면 계획만 고쳐 다시 승인받는다.

## 4. 보고서 쓰기

승인받은 보고서 파일에 다음을 담는다.

- 후보와 점검 날짜
- 확인한 출처와 결과
- 확인하지 못한 것과 그 이유
- 사람이 판단해야 할 질문 (예: 운영에서 아직 쓰이는지, 안전장치인지)
- 제안하는 삭제 범위와, 삭제 전에 필요한 추가 확인

## 5. 실행해서 확인하기

- 보고서의 파일 경로와 줄 번호가 실제 레포와 맞는지 다시 열어 확인한다.
- 보고서에 비밀 값이 들어가지 않았는지 `sk-`, `ghp_`, `-----BEGIN` 패턴을 grep으로 찾는다.
- `git status --short -uall`과 `git diff | git hash-object --stdin`을 다시 실행해 시작 시점과 비교하고, 새 줄이 승인받은 보고서 파일 하나뿐이며 추적 파일의 diff 해시가 같은지 확인한다.
- `checklist.md`의 항목을 하나씩 점검하고 결과를 보고한다.
