2026년 10월 14일 OpenAI Core Experimentation 팀의 Rodrigo Roim은 개발자 블로그에서, 코딩 에이전트 Codex에게 <Term id="dead-code">죽은 코드</Term> 정리를 맡기고 지워도 되는 근거를 에이전트가 스스로 찾게 했고, 에이전트는 삭제마다 이유도 적어 냈다고 썼습니다. 프롬프트는 한 문장이었고, 확인할 곳으로 Slack과 실험·<Term id="feature-flag">기능 플래그</Term> 플랫폼 <Term id="statsig">Statsig</Term>를 예로 들었을 뿐입니다. 이어서 낡은 실험을 정리할 때는 몇 해 묵은 플래그 하나를 Codex가 비용까지 조사하고도 지우지 않고 사람에게 넘겼습니다.

Roim이 속한 팀은 프런트엔드 변경부터 모델 서빙 효율 개선까지, 회사 전체의 실험을 지원하는 소프트웨어를 만들고 유지합니다. 이 글은 그 팀이 쌓인 코드를 어떻게 치웠는지 설명합니다.

글은 2026년 10월 14일에 올라왔지만 작업 날짜는 적혀 있지 않습니다. 죽은 코드 정리를 시간을 쪼개 두 주 동안 했다는 말뿐입니다. 아래 수치는 모두 OpenAI 팀이 자기 제품과 레포에서 낸 내부 결과이며, 독립적으로 검증되지 않았습니다.

## 기존 분석 도구는 예외 상황을 놓쳐서 삭제가 두려웠다

코드를 지우는 일은 늘 위험했습니다. Roim은 에이전트 이전에 많은 소프트웨어 팀이 <Term id="static-analysis">정적 분석</Term>과 런타임 로그를 엮은 복잡한 시스템으로 안 쓰는 코드를 찾았다고 씁니다. 그런 시스템과 꼼꼼한 리뷰가 있어도 실수는 났고, 그는 잘못 지워서 생긴 사고를 여러 번 기억한다고 합니다.

실패 원인은 분석이 놓치는 예외였습니다. 실행 중에 이름으로 코드를 불러내는 리플렉션은 정적 분석에 잡히지 않습니다. 겉보기에 안 쓰이는 코드가 나중에 장애를 완화할 때 켜는 경로일 수도 있습니다. Roim은 이런 예외가 너무 많아 다 따지기 어렵다고 씁니다.

<KeyIdea title="삭제마다 근거를 남기자 리뷰가 빨라졌습니다">
정적 분석과 로그는 코드 안만 봅니다. Roim이 Codex에게 맡긴 일은 PR, Slack, 프로젝트 트래커 같은 코드 밖의 기록까지 읽고 삭제마다 이유를 적는 것이었고, 그 덕분에 리뷰가 빨라졌다고 합니다.
</KeyIdea>

## 프롬프트가 예로 든 곳보다 더 많은 출처를 에이전트가 찾아 읽었다

먼저 좁은 시도가 있었습니다. 이 글에는 모델이 셋 나옵니다. 이전 세대인 GPT-5.6 Sol, 그 뒤에 나온 GPT-6 Astra, 그리고 비슷한 결과를 더 싼 비용으로 냈다고 원문이 소개하는 GPT-6.1 Sol입니다. 원문은 GPT-6.1 Sol의 출시 시점을 설명하지 않습니다. 글에 따르면 GPT-5.6 Sol은 이전 세대 모델이고, GPT-6 Astra는 그 뒤에 나온 모델입니다. Roim이 GPT-5.6 Sol에게 영역과 검증 기준을 정해 주면, 모델이 정적 분석 코드를 직접 짜서 죽은 코드를 지웠습니다. 이런 좁은 프롬프트는 기존 정적 분석 시스템보다 만들고 유지하기 쉬웠고, 신뢰도는 비슷했다고 합니다.

다음에는 범위를 넓혔습니다. Roim은 이 짧은 프롬프트가 GPT-5.6 Sol이 온전히 다루기에는 너무 모호했다고 씁니다. 그는 GPT-6 Astra로 시도했고, 프롬프트는 이렇습니다.

<Quote source="openai-maintaining">
Can you help identify and clean up dead code in the repo please, feel free to check slack, statsig [a feature flag and experimentation platform we use], or any other source you need to confirm that things are indeed no longer being used and can be cleaned up or simplified
</Quote>

프롬프트가 예로 든 곳은 Slack과 Statsig뿐이었습니다. Astra는 거기에 더해 과거 PR, 내부 프로젝트 트래커, 운영 성능 프로파일링 표까지 열어, 지울 줄이 실제로 실행된 적 없는지 확인했습니다. 삭제마다 이유도 적었고, 그 덕분에 리뷰가 빨라졌다고 Roim은 전합니다.

규모도 컸습니다. 엔지니어 다섯 명이 프롬프트를 변형해 여러 레포에 돌렸고, 병합한 PR이 1,400건을 넘고 지운 코드가 80만 줄을 넘었습니다. 작업의 대부분은 두 주 동안, 그것도 다른 일과 병행하며 했다고 합니다. 리뷰는 영향받는 프로젝트를 아는 팀들에 나눠 맡겼습니다.

측정할 수 있는 효과도 있었습니다. 예를 들어 한 서비스의 컨테이너 이미지가 3.31GB에서 1.72GB로 48% 줄었습니다.

## 낡은 실험은 지워도 되는지 더 따져야 한다

죽은 코드는 안 쓰이면 끝입니다. 낡은 실험은 사정이 다릅니다. 코드가 아직 운영에서 돌 수도 있고, 언제든 바뀔 수 있는 자격 평가(실험을 어느 사용자나 요청에 보여 줄지 판정하는 조건)에 기대고 있을 수도 있어 정적 분석만으로는 더 어렵습니다. 팀은 원래 결정적인 정적 분석과 데이터베이스 조회를 합친 스크립트를 GPT-5.6 Sol로 만들어 썼는데, 놓치는 것이 많았습니다.

죽은 코드 정리가 잘되자 Roim은 낡은 실험에도 짧은 프롬프트를 써 보기로 했습니다. 어디서 시작할지 몰라 Astra와 함께 아이디어를 내고, 새 스레드에서 쓸 짧은 프롬프트를 Astra에게 쓰게 했습니다. Astra가 쓴 프롬프트는 이렇습니다. `{A}`, `{B}`는 원문 그대로이며, 프로젝트 이름을 가린 자리로 보입니다.

<Quote source="openai-maintaining">
Find and remove substantial dead code associated with stale, constant Statsig gates/configs or abandoned experiments in projects \{A\} and \{B\}. Verify live Statsig configuration and check git history and overlapping PRs. Preserve production behavior, operational safeguards and gates/configs intended as killswitches or similar.
</Quote>

운영 중인 Statsig 설정과 git 이력, 겹치는 PR을 먼저 확인하고, 운영 동작과 안전장치, <Term id="killswitch">킬스위치</Term> 같은 용도의 설정은 그대로 두라는 뜻입니다. 이 프롬프트는 SDK 대체값(fallback)과 로컬 재정의(local override)는 무시하라고 했고, 정리 하나당 작은 초안 PR 하나를 열어 요약에 Statsig 콘솔 링크를 달게 했습니다.

Roim은 초안 PR에 댓글을 달았습니다. 그다음 그 댓글을 반영해 코드베이스 전체를 훑는 새 프롬프트를 Astra에게 쓰게 하고, 우선순위도 함께 잡게 했습니다. 이 프롬프트는 `/goal`로 시작합니다. 원문은 `/goal`을 설명하지 않지만, 2026년 11월 OpenAI 공식 문서는 `/goal`을 작업이 끝나거나 멈추거나 추가 입력이 필요할 때까지 계속 추구하는 목표를 정하는 명령으로 설명합니다(해당 문서는 ChatGPT 데스크톱 앱 기준으로 쓰여 있습니다). 프롬프트는 검증된 후보를 병렬로 처리할 수 있는 작업 묶음으로 나눈 마크다운 보고서를 요구했고, 보고서에는 운영 값, 증거, 담당자, 호출 위치, 확인한 평가 비용이나 CPU 비용을 넣게 했습니다. 가장 강한 제약은 한 줄이었습니다.

<Quote source="openai-maintaining">
Do not modify live configurations or services.
</Quote>

운영 설정과 서비스는 읽기만 하라는 제약이었습니다. 글은 이 프롬프트의 일부를 생략했고, 생략한 부분은 운영 동작 검증, 오래된 항목 우선, 의도된 안전장치 보존, SDK 대체값 해석에 관한 지시라고만 밝힙니다.

Astra는 낡은 실험마다 CPU 비용을 쟀습니다. 상위 결과는 몇 해 동안 아무도 낡았다고 보지 못한 실험에 얽힌 큰 효율 이득이었습니다. Roim은 큰 결과를 정리하기 전에 직접 검증했고, 이 정리로 실험과 기능 플래그 수백 개가 사라졌습니다.

## 영구 플래그는 지우지 않고 사람에게 넘겼다

Roim의 글이 전하는 가장 긴장되는 장면은 Astra가 지우지 않은 플래그입니다. 몇 해 전 한 엔지니어가 내부 개발자가 테스트 목적으로 신기능 플래그 전부를 덮어쓸 수 있게 하는 플래그를 만들었습니다. 이 플래그를 다른 모든 기능에 연결한 파이썬 코드 한 줄이 수백 개의 비슷한 매핑 사이에 묻혀 있었고, Astra는 이 줄이 CPU 사용을 크게 퍼뜨린다(fan-out)는 것을 찾아냈습니다. Astra는 이 CPU 비용을 조사했습니다. 하지만 플래그 관리 콘솔에 "Permanent"라고 표시돼 있고 운영상 용도가 남아 있을 수 있다는 이유로 사람의 검토를 요청했습니다.

검토 뒤에 플래그는 지워졌습니다. 주요 영향 서비스에서 CPU가 약 0.42% 줄 것으로 추정됐습니다. 이 플래그는 CPU를 많이 쓰고 있었지만, 콘솔에 영구 플래그로 표시돼 있어 아직 운영상 쓰임이 있을 수 있었습니다. 순서는 이렇습니다. 에이전트가 비용을 재고, 애매한 것은 사람에게 넘기고, 사람이 확인한 뒤에 지웁니다.

## 제안 일부는 이득보다 복잡했고, 모델마다 결과가 달랐다

한계도 있었다고 Roim은 씁니다.

<Quote source="openai-maintaining">
some proposals added more complexity than their expected benefit justified, so prioritization and measurement remained an important part of our workflow.
</Quote>

제안 일부는 기대 이득보다 복잡했고, 그래서 우선순위를 정하고 효과를 재는 일이 계속 필요했다는 뜻입니다.

모델 선택도 결과를 갈랐습니다. Ultra는 원문이 모델 이름 끝에 붙여 쓰는 추론 강도 설정으로, 정의는 설명하지 않습니다. Roim은 같은 프롬프트로 한 레포의 특정 하위 디렉터리들(파일 6,000개 이상, 코드 100만 줄 이상, Python·TypeScript·Go·Rust)을 점검하게 하고 결과를 직접 검토했습니다. GPT-6 Astra Ultra는 109.06달러로 142건, GPT-6.1 Sol Ultra는 15.12달러로 131건, GPT-6.1 Sol Medium은 5.27달러로 86건을 찾았습니다(점검 날짜는 원문에 없습니다). 원문은 이 비교에서 GPT-6.1 Sol Ultra가 GPT-6 Astra Ultra 발견 건수의 92%를 API 비용의 14%로 냈다고 정리합니다.

Ultra 설정끼리 비교했을 때 차이는 주로 다른 플래그의 의존성으로 쓰인 상수 플래그에서 났고, 이를 Astra만 찾았습니다. Roim은 이런 차이를 알면 프롬프트를 고칠 수 있다고 봅니다. 다만 이 보정은 2026년 10월 기준이고, 새 모델이 나오면 필요 없어질 수 있으니, 프롬프트를 다시 살피라고 권합니다.

그가 권하는 시작점은 작습니다.

Codex에게 사례 하나를 찾고, 증거를 모으고, 작은 초안 PR을 제안하게 하라고 권합니다. 안 쓰는 코드, 낡은 플래그, 불안정한 테스트 중 하나로 시작해 하위 디렉터리, 코드베이스 전체 순으로 넓히고, 단계마다 코드 리뷰 의견을 다음 프롬프트에 반영하라고 덧붙입니다. 에이전트는 코드를 직접 지웠지만, 지우기 전에 근거를 모았고 영구 플래그 한 건은 사람에게 넘겼습니다.
