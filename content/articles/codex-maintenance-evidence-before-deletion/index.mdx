2026년 10월 14일, OpenAI의 Rodrigo Roim이 개발자 블로그에 정리 과정을 적었습니다. 회사 전체의 실험을 지원하는 팀이 소프트웨어를 만들고 유지합니다. 손대는 범위는 프런트엔드 변경부터 모델 서빙 효율까지이고, 그 사이에 쌓인 코드를 Codex에 맡겼습니다. 대상은 <Term id="dead-code">죽은 코드</Term>였고, 지워도 되는 근거는 에이전트가 직접 찾았습니다. 지울 때마다 이유도 적었습니다.

프롬프트는 한 문장이었습니다. 예로 든 곳은 Slack과 <Term id="statsig">Statsig</Term>입니다. Statsig는 <Term id="feature-flag">기능 플래그</Term> 플랫폼입니다. 분석이 예외를 놓치던 자리에서, 에이전트는 무엇을 열어 봤을까요.

## 예외를 놓치면 삭제가 무섭다

코드를 지우는 일은 늘 위험했습니다. 에이전트 이전에도 많은 팀이 안 쓰는 코드를 찾았고, <Term id="static-analysis">정적 분석</Term>과 실행 로그를 엮었습니다. 꼼꼼한 리뷰가 있어도 실수는 났습니다. Roim은 잘못 지워서 생긴 사고를 여러 번 기억합니다.

실패의 원인은 분석이 놓치는 예외였습니다. 리플렉션은 실행 중에 이름으로 코드를 불러내므로, 정적 분석에 잡히지 않습니다. 안 쓰여 보이는 코드가 나중에 켜는 경로일 수 있고, 장애를 완화할 때 쓰는 경로이기도 합니다. 예외가 너무 많아 다 따지기 어렵다고 Roim은 적었습니다.

<KeyIdea title="삭제 근거가 리뷰를 빠르게 했습니다">
정적 분석과 로그는 코드 안만 봅니다. Codex가 코드 밖 기록까지 읽고 삭제마다 이유를 적었습니다. 코드 밖 기록은 다음입니다.

- PR
- Slack
- 프로젝트 트래커
</KeyIdea>

짧은 프롬프트가 그 기록까지 열었는지는, 맡긴 범위에 따라 갈렸습니다.

## 예로 든 곳보다 많은 기록을 연다

먼저 좁은 시도가 있었습니다. 2026년 10월 14일 글에 나온 모델은 셋입니다. 이전 세대 GPT-5.6 Sol, 그 뒤의 GPT-6 Astra, 더 싼 비용으로 비슷한 결과를 낸 GPT-6.1 Sol입니다. 글은 GPT-5.6 Sol을 이전 세대 모델로 두고, GPT-6 Astra를 그다음 모델로 둡니다.

Roim이 GPT-5.6 Sol에 영역과 검증 기준을 정해 주면, 모델이 정적 분석 코드를 직접 짜고 그 코드로 죽은 코드를 지웠습니다. 좁은 프롬프트는 기존 시스템보다 만들고 유지하기 쉬웠고, 신뢰도는 비슷했습니다.

다음에는 범위를 넓혔습니다. 이 짧은 프롬프트는 GPT-5.6 Sol에 너무 모호해서, Roim은 GPT-6 Astra로 시도했습니다.

<Quote source="openai-maintaining">
Can you help identify and clean up dead code in the repo please, feel free to check slack, statsig [a feature flag and experimentation platform we use], or any other source you need to confirm that things are indeed no longer being used and can be cleaned up or simplified
</Quote>

예로 든 곳은 Slack과 Statsig뿐이었습니다. Astra는 거기에 더해 과거 PR, 내부 프로젝트 트래커, 운영 성능 프로파일링 표를 열었습니다. 지울 줄이 실제로 실행된 적 없는지를 보고, 삭제마다 이유를 적었습니다. 그래서 리뷰가 빨라졌습니다.

규모도 컸습니다. 엔지니어 다섯 명이 프롬프트를 변형해 여러 저장소에 돌렸고, 병합한 PR은 1,400건을 넘습니다. 지운 코드는 80만 줄을 넘습니다. 작업의 대부분은 두 주 동안이었고, 다른 일과 병행했습니다. 리뷰는 영향받는 프로젝트를 아는 팀들에 나눴습니다.

잴 수 있는 효과도 있었습니다. 한 서비스의 컨테이너 이미지가 3.31GB에서 1.72GB로 줄었고, 48%입니다.

죽은 코드는 안 쓰이면 끝입니다. 아직 운영에서 돌 수 있는 실험은 그때부터 다른 문제입니다.

## 낡은 실험은 자격부터 확인한다

코드가 아직 운영에서 돌 수 있고, 자격 평가에 기대고 있을 수 있습니다. 자격 평가는 실험을 누구에게 보일지 정하는 조건이고, 언제든 바뀔 수 있습니다. 그래서 정적 분석만으로는 더 어렵습니다.

팀은 스크립트를 GPT-5.6 Sol로 만들어 썼습니다. 규칙대로 움직이는 정적 분석과 데이터베이스 조회를 합쳤는데, 놓치는 것이 많았습니다. 죽은 코드 정리가 잘되자 Roim은 낡은 실험에도 짧은 프롬프트를 써 보기로 했습니다. 어디서 시작할지 몰라 Astra와 아이디어를 냈고, 새 스레드의 짧은 프롬프트를 Astra에 쓰게 했습니다. `{A}`와 `{B}`는 원문 그대로입니다. 프로젝트 이름을 가린 자리로 보입니다.

<Quote source="openai-maintaining">
Find and remove substantial dead code associated with stale, constant Statsig gates/configs or abandoned experiments in projects \{A\} and \{B\}. Verify live Statsig configuration and check git history and overlapping PRs. Preserve production behavior, operational safeguards and gates/configs intended as killswitches or similar.
</Quote>

프롬프트는 운영 중인 Statsig 설정을 먼저 확인하고, git 이력과 겹치는 PR도 확인합니다. 운영 동작과 안전장치, <Term id="killswitch">킬스위치</Term> 용도는 그대로 두고, SDK 대체값과 로컬 재정의는 무시합니다. 정리 하나당 작은 초안 PR 하나를 열고, 요약에 Statsig 콘솔 링크를 답니다.

Roim은 초안 PR에 댓글을 달고, 그 댓글을 반영한 새 프롬프트를 Astra에 쓰게 했습니다. 코드베이스 전체를 훑으면서 우선순위도 함께 잡습니다. 이 프롬프트는 `/goal`로 시작합니다. 원문은 `/goal`을 설명하지 않습니다. OpenAI 공식 문서에서 `/goal`은 목표를 정하는 명령이고, 그 목표는 작업이 끝나거나, 멈추거나, 사람의 입력이 필요해질 때까지 이어집니다.

프롬프트는 마크다운 보고서를 요구했습니다. 검증된 후보는 작업 묶음으로 나누고, 묶음은 병렬로 처리할 수 있습니다. 보고서에는 운영 값, 증거, 담당자, 호출 위치, 평가 비용 또는 CPU 비용을 넣습니다.

가장 강한 제약은 한 줄이었습니다.

<Quote source="openai-maintaining">
Do not modify live configurations or services.
</Quote>

운영 중인 설정과 서비스는 바꾸지 말라고 막아 둔 줄입니다. 글은 이 프롬프트의 일부를 생략했고, 생략한 지시는 운영 동작 검증, 오래된 항목 우선, 의도된 안전장치 보존, SDK 대체값 해석뿐이라고 밝힙니다.

Astra는 낡은 실험마다 CPU 비용을 쟀습니다. 상위 결과는 큰 효율 이득이었고, 몇 해 동안 아무도 낡았다고 보지 못한 실험이었습니다. Roim은 큰 결과를 정리하기 전에 직접 검증했습니다. 이 정리로 실험과 기능 플래그 수백 개가 사라졌습니다.

그래도 Astra가 지우지 않은 플래그가 있습니다.

## 영구 플래그는 지우지 않고 넘긴다

몇 해 전 한 엔지니어가, 내부 개발자가 테스트로 신기능 플래그 전부를 덮어쓰게 하는 플래그를 만들었습니다. 이 플래그를 모든 기능에 잇는 파이썬 한 줄이 비슷한 매핑 수백 개 사이에 있었고, Astra는 그 줄이 CPU 사용을 크게 퍼뜨린다는 것을 찾았습니다. 영어로는 fan-out입니다. CPU 비용은 조사했지만 직접 지우지는 않았습니다. 콘솔 표시가 Permanent여서 운영상 용도가 남아 있을 수 있었고, 사람 검토를 요청했습니다.

검토 뒤에 플래그는 지워졌습니다. 주요 영향 서비스의 CPU가 약 0.42% 줄 것으로 추정됐습니다. 에이전트가 비용을 재고, 애매한 것은 사람에게 넘기고, 사람이 본 뒤에 지웁니다.

  after="에이전트가 사용 증거를 모으고 애매한 것은 사람에게 넘깁니다."

증거는 Slack, Statsig, git 이력에서 모으고, 삭제마다 이유를 적습니다. 질문은 그때로 넘어갑니다. 그 복잡함을 기대 이득이 받쳐 줬는지입니다.

## 복잡한 제안은 재고 나서 남긴다

<Quote source="openai-maintaining">
some proposals added more complexity than their expected benefit justified, so prioritization and measurement remained an important part of our workflow.
</Quote>

제안 일부는 기대 이득보다 복잡했습니다. 우선순위를 정하는 일과 효과를 재는 일은 계속 필요했습니다.

모델 선택도 결과를 갈랐습니다. Ultra는 모델 이름 끝에 붙는 추론 강도입니다. Roim은 같은 프롬프트로 한 저장소의 하위 디렉터리를 점검하게 했고, 결과를 직접 검토했습니다. 대상은 파일 6,000개 이상, 코드 100만 줄 이상이고, 언어는 Python, TypeScript, Go, Rust입니다.

GPT-6 Astra Ultra는 109.06달러로 142건입니다. GPT-6.1 Sol Ultra는 15.12달러로 131건이고, GPT-6.1 Sol Medium은 5.27달러로 86건입니다. GPT-6.1 Sol Ultra의 발견은 GPT-6 Astra Ultra 건수의 92%이고, API 비용은 14%입니다. Ultra끼리의 차이는 주로 상수 플래그에서 났습니다. 다른 플래그의 의존성으로 쓰인 상수이고, 이 상수는 Astra만 찾았습니다. 이런 차이를 알면 프롬프트를 고칠 수 있습니다. 새 모델이 나오면 이 보정은 필요 없어질 수 있어서, 프롬프트를 다시 살펴야 합니다.

Roim이 권하는 시작점은 작습니다.
