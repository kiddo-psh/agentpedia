2026년 10월 25일, 한 개발자가 Postman 저장소 이슈에 적었습니다. Mac에서 Postman을 열자 MCP 인증 경고가 이어졌고, Codex는 API 작업마다 Postman 스킬을 거쳤습니다. 설정 파일과 로그를 하나씩 열어 보니, 직접 설치하지 않은 항목이 있었습니다. 이슈는 이후 삭제됐습니다. 아래는 당시 이슈를 옮긴 보도와 Postman 플러그인 소스에 근거합니다.

## 같은 달에 경로만 달랐다

Cursor 마켓플레이스의 Claude Code 확장에는 백도어가 있었고, OpenCode 웹 서비스에서는 저장해 둔 API 키가 나갔습니다. Postman 이슈는 11월 3일 해커뉴스에 올라 댓글이 약 500개였습니다. 10월의 세 사건은 경로가 달랐고, 문제는 같았습니다. 그 폴더는 `~/.claude`와 `~/.codex`입니다.

<KeyIdea title="설정은 신뢰 경계입니다">
사용자 권한으로 도는 코드가 <Term id="trust-boundary">신뢰 경계</Term>입니다. 플러그인, 훅, <Term id="mcp">MCP</Term> 서버, 에디터 확장이 그 코드이고, 읽을 대상과 실행할 명령, 접속할 곳을 정합니다.
</KeyIdea>

## Postman이 에이전트 설정을 바꿨다

질문은 그때 로그로 돌아갑니다. 작성자는 Postman 로그에서 단서를 찾았습니다. 10월 24일 출처는 `auto-existing-upgrade`입니다. Claude Code에 플러그인을 설치했고, Codex에도 설치했습니다. 설치한 쪽은 Postman 데스크톱 12.33.4입니다.

<Term id="agent-plugin">에이전트 플러그인</Term>이 켜지고 마켓플레이스가 추가됐습니다. 바뀐 파일은 `~/.codex/config.toml`입니다. 세션이 시작될 때마다 <Term id="agent-hook">훅</Term>이 돌았습니다. Postman 원격 MCP도 연결됐는데 인증은 실패했고, 경고가 반복됐습니다. Claude Code용 플러그인도 설치됐고, Postman CLI도 설치됐습니다.

이 훅은 세션이 시작될 때 다음 문장을 읽힙니다.

<Quote source="postman-plugin-hook">
Before responding to any non-trivial API engineering task — designing, implementing, mocking, testing, monitoring, documenting, or deploying an API or Postman Flow — load the `postman:api-engineer` skill and follow it.
</Quote>

답하기 전에 `postman:api-engineer` 스킬을 따릅니다. 사용자가 시키지 않아도 그렇습니다. 작성자는 설치 프로그램이 이 훅을 Codex 신뢰 목록에 올렸다고 판단합니다. 관리되지 않는 훅은 사용자가 검토한 뒤 실행되고, Codex는 신뢰를 훅 해시에 묶어 기록합니다. 설치 프로그램은 그 승인 기록을 직접 쓰려 했습니다.

11월 5일 Postman 직원이 이슈에 답했습니다. 보도가 전한 답은, 설치 과정을 다시 설계해 사용자 통제를 늘리고 그동안 이 변경을 되돌린다는 것이었습니다. 이미 깔린 플러그인을 지워 주는지는 밝히지 않았습니다. 악성 코드는 아니었습니다. 그래도 다른 앱이 행동 규칙을 바꿨습니다.

## 공식 확장의 백도어는 지워도 남는다

규칙을 바꾼 쪽이 설치 파일 자체라면, 확장을 지우는 것으로 끝나지 않습니다. Phorion이 10월 30일 권고문을 냈고, 다음 날 Cursor 공지로 2.1.312를 영향 버전에 넣었습니다. 대상은 Cursor 마켓플레이스의 공식 Claude Code for VS Code입니다. 버전은 2.1.312와 2.1.313입니다. Cursor는 두 버전을 내렸습니다. 아래는 Phorion 분석입니다.

<Term id="supply-chain-attack">공급망 공격</Term>입니다. 사용자는 이름과 출처만 보고 설치하고, 확장은 사용자와 같은 권한을 얻습니다.

<Quote source="phorion">
Because extensions run with the permissions of the IDE and the user running it, a backdoored extension gets immediate access to local files, source code, and developer tooling as soon as its module is loaded.
</Quote>

모듈이 올라오는 순간, 로컬 파일과 소스, 개발 도구에 바로 닿습니다. 악성 코드는 확장 파일 맨 앞에 있습니다. 확장이 정상으로 켜지기 전에 실행되고, 사용자가 누르지 않아도 실행됩니다.

1. 공격자 SSH 공개 키를 `~/.ssh/authorized_keys`에 넣습니다.
2. <Term id="reverse-ssh-tunnel">리버스 SSH 터널</Term>을 만듭니다. 공격자 서버로 SSH를 엽니다. 에디터를 닫아도 연결은 남습니다.
3. macOS는 LaunchAgent를 등록해 <Term id="persistence">지속성</Term>을 확보합니다. 이름은 `com.apple.sysmond`입니다. Apple 시스템 이름으로 위장합니다. Linux에도 방법이 있었고, Windows에도 방법이 있었습니다.
4. 공격자 서버로 호스트 이름, 사용자 이름, Git 이메일, 공인 IP, 환경 변수 이름을 보냅니다.

환경 변수는 이름만 보냅니다. 이름에 KEY, TOKEN, SECRET이 들어갈 때입니다. 값은 보내지 않았습니다. 공격자는 키를 바로 훔치지 않았습니다. 오래 드나들 경로를 남겼고, 나중에 훔칠 대상 목록도 챙겼습니다.

Phorion은 macOS SSH 활성화 코드의 버그를 짚었습니다. 권한은 일반 사용자라, 원격 로그인이 꺼진 Mac은 바깥 접속이 되지 않았습니다. 이 버그 자체는 방어가 아닙니다. 확장을 지워도 백도어는 남습니다. 지울 것은 터널 프로세스, LaunchAgent, 추가된 SSH 키입니다.

감염을 의심할 흔적은 이렇습니다.

- 확장 `anthropic.claude-code`
- 버전 2.1.312 또는 2.1.313
- `~/.ssh/authorized_keys`의 주석 `svc-telemetry`
- `~/Library/LaunchAgents/com.apple.sysmond.plist`
- `~/.config/.smt`와 `~/.config/.smtk`. 위치는 macOS와 Linux입니다
- Linux crontab `@reboot`가 `~/.config/.smt`를 실행
- Windows 예약 작업 `SysMon`
- 시작 폴더의 `sysmon.cmd`
- `~/.config/smt.cmd`
- 임시 파일 패턴 `.stk_*`
- macOS 임시 경로 `$TMPDIR/.stk_*`
- Linux 임시 경로 `/tmp/.stk_*`

## 맡긴 키가 뚫리면 내 보안도 그 수준이다

세 번째 사건은 컴퓨터 밖에서 났습니다. TechCrunch는 10월 19일에 침해를 보도했습니다. OpenCode의 오래된 시스템이 직전 토요일 밤 뚫렸습니다. OpenCode가 직접 밝힌 내용입니다. 피해자는 OpenCode Console 사용자의 1.4%입니다. 일부는 Console에 개발사 API 키를 저장해 두었고, 개발사는 OpenAI와 Anthropic입니다.

밤사이 사용량 경고가 왔고, 무단 결제 알림도 왔습니다. 피해액은 수백 달러입니다. 1,000달러를 넘은 경우도 있습니다. Anthropic과 Google은 노출된 것으로 보이는 키를 막았습니다. OpenAI는 OpenCode와 접근을 복구했고, 크레딧도 환불했습니다. 침해는 오픈소스 앱과 CLI에 미치지 않았습니다. Dax Raad는 침해 지점을 OpenCode Console로 두었습니다.

<Quote source="techcrunch-opencode">
Note this is the OpenCode Console, not OpenCode itself, those keys never come to us
</Quote>

OpenCode 자체가 아니라 Console이고, 앱에 넣은 키는 OpenCode로 오지 않습니다. 로컬 도구를 잘 지켜도, 키를 맡긴 서비스의 보안이 내 보안입니다.

## 목록이 첫 단계다

세 사건을 나란히 보면, 키의 위치와 개수부터 알아야 합니다.

<Compare
  before="내가 깔았으니 설정을 점검하지 않습니다."
  after="출처를 알고 키를 맡기는 곳을 줄입니다."
/>

| 항목 | Postman | 확장 | Console |
|---|---|---|---|
| 경로 | 다른 앱 | 마켓플레이스 | 웹 서비스 |
| 변경 | 플러그인·훅·MCP | SSH·시작·터널 | 저장 API 키 |
| 악의 | 없음 | 있음 | 있음 |
| 공개 | 10월 25일 이슈 | 10월 30일 권고문 | 10월 19일 보도 |

피해자가 먼저 알기 어려웠습니다. Postman은 증상에서 원인을 거꾸로 찾았습니다. 그래서 지금 붙어 있는 것을 목록으로 만드는 일이 먼저입니다.

목록은 이미 일어난 일만 찾습니다. 다음 업데이트가 확장을 오염시킬 수 있고, Phorion이 본 확장도 공식 이름이었습니다. 새 도구를 깐 뒤에 목록을 다시 만들고, 에이전트가 평소와 달라도 다시 만듭니다.

신뢰 기록이 있어도 누가 만들었는지는 모릅니다. 이슈 작성자도 이 점을 인정했습니다. OpenCode는 보도 때까지 침입 경로를 밝히지 않았고, 키 저장 방식도 밝히지 않았습니다. 확장이 마켓플레이스에서 어떻게 오염됐는지도 출처에 없습니다.

지금 에이전트에 붙은 것 가운데, 내가 설치한 기억이 없는 것은 무엇인가.
