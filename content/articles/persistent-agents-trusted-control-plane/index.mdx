OpenAI는 OpenClaw 같은 <Term id="persistent-agent">지속 실행 에이전트</Term>를 "믿을 수 있는 자동화"로 두지 않습니다. Kevin S Lin이 2026년 11월 12일 OpenAI 개발자 블로그에 쓴 글의 요지입니다. OpenClaw는 넓은 범위에서 24시간 돌며, 입력이 없어도 먼저 행동할 수 있는 에이전트입니다.

Lin은 에이전트를 처음부터 믿지 않습니다. 에이전트가 만든 코드와 실행 환경도 마찬가지입니다. 대신 네트워크·신원·샌드박스를 맡는 <Term id="control-plane">제어면</Term>을 따로 돌리고, 이 제어면은 규칙대로만 움직이게 합니다. OpenAI는 사내 곳곳에 지속 실행 에이전트를 배포했고, 그중 OpenClaw 에이전트만 해도 수백 대입니다.

## 똑똑해질수록 권한을 넓히는 관행과 반대다

많은 팀은 에이전트가 잘할수록 도구, 네트워크, 파일 접근을 넓힙니다. 일을 맡기려면 손이 닿아야 한다고 보기 쉽습니다. Lin의 생각은 반대입니다. 전통 소프트웨어는 설정과 코드가 대체로 정해진 대로 움직이고, 위협은 주로 바깥에서 온다고 가정합니다. 지속 실행 에이전트는 다릅니다. 설정을 바꿀 수 있고, 목표를 이루려고 임의 코드를 쓸 수도 있습니다. 그래서 어긋난 행동이 안에서 나옵니다.

<Quote source="openai-persistent-agents">
Attacks come from the inside when agents take misaligned actions.
</Quote>

에이전트가 목표에서 어긋나면 위협은 바깥이 아니라 에이전트 쪽에서 생깁니다. 그래서 Lin은 에이전트를 더 믿게 만들기보다, 믿지 않아도 돌아가는 구조에 힘을 씁니다.

<KeyIdea title="실행은 믿지 않고, 경계는 규칙대로 둡니다">
믿는 것은 네트워크·신원·샌드박스처럼 설정대로 움직이는 로직뿐입니다. 에이전트, 실행 환경, 에이전트가 쓴 코드는 믿지 않습니다. 행동이 보장되지 않는 실행 공간으로 다룹니다.
</KeyIdea>

## 게이트웨이와 에이전트 하네스를 나눈다

OpenAI는 이 분리를 OpenClaw에 넣으려고 원격 하네스 실행을 오픈소스 쪽에 구현했습니다. 에이전트 설정은 OpenClaw 게이트웨이가 맡습니다. 게이트웨이는 에이전트 <Term id="agent-harness">하네스</Term>와 다른 컨테이너에서 돌고, OpenAI 사내에서는 아예 다른 클러스터에서 돕니다. 게이트웨이는 규칙대로 움직이는 신뢰 코드로 둡니다. 에이전트 워크로드만 믿지 않는 코드로 보고 샌드박스에 가둡니다.

게이트웨이를 에이전트와 같은 곳에 두면, 에이전트가 경계 설정까지 바꿀 여지가 커집니다. 제어면을 밖으로 빼면 그 길이 끊깁니다.

## 샌드박스는 네 가지 경계로 행동을 제한한다

경계를 강제하는 장치는 <Term id="sandbox">샌드박스</Term>입니다. Lin이 OpenAI의 OpenClaw 배포에 쓴 통제는 네 가지입니다.

- 네트워크: 조직이 관리하는 <Term id="network-allowlist">네트워크 허용 목록</Term>, 제한 대상은 명시적으로 거부
- 워크스페이스: 에이전트 작업 디렉터리에만 쓰기 허용
- 프로세스: Codex 리눅스 샌드박스로 프로세스 격리
- 비밀: <Term id="credential-broker">자격 증명 브로커</Term>가 중개해 에이전트가 비밀을 보지 못하게 함

예시 `requirements.toml`은 `allowed_sandbox_modes`에 `read-only`와 `workspace-write`만 남깁니다. 제한을 거의 다 푸는 <Term id="danger-full-access">danger-full-access</Term>는 뺍니다. 웹 검색은 라이브 검색 대신 OpenAI 인덱스를 거치는 cached 모드만 허용합니다. 관리형 네트워크 프록시를 켜고, 사용자가 허용 목록을 마음대로 늘리지 못하게 합니다. 거부 목록에는 pastebin·webhook 사이트와 클라우드 메타데이터 주소(`169.254.169.254` 등)가 들어 있습니다.

`config.toml`에서는 워크스페이스 경로에만 쓰기를 허용하고, `~/.ssh`는 deny로 막습니다. 셸 환경에서는 `GH_TOKEN`·`GITHUB_TOKEN` 같은 값을 뺍니다. 다만 이 exclude가 파일에 든 자격 증명까지 숨기지는 않는다고 Lin은 분명히 밝힙니다. OpenAI Agents 샌드박스 보안 문서도 비슷한 축을 짚습니다. 승인된 엔드포인트만 열고, 타사 자격 증명은 환경 밖에 두며, 자동 검토만으로 네트워크·자격 증명 통제를 대신하지 말라는 내용입니다.

## 규칙 기반 경계 위에 모델 검토를 얹는다

여기까지는 규칙대로 막는 정적 통제입니다. Lin은 모델이 똑똑해질수록 계산량과 함께 커지는 방어도 필요하다고 봅니다. 그 장치가 <Term id="auto-review">자동 검토</Term>(Auto-review)입니다. 두 번째 에이전트가 주 에이전트의 행동을 감시하고 승인합니다. 사람이 매번 승인하면 검토 피로가 쌓이고, 결국 모두 승인해 버리게 됩니다. LLM 검토기를 필터로 두면 사람은 값비싼 승인에만 주의를 쓰면 됩니다. OpenAI의 OpenClaw 배포는 모든 에이전트 행동에 자동 검토를 겁니다. 이 기능은 OpenClaw와 Codex에 모두 있습니다.

신원도 나눕니다. 에이전트마다 ChatGPT Service Account에 묶인 고유 신원이 있습니다. 그래서 사용자와 다른 추론 자격 증명을 쓰고, 행동을 감사하거나 추론을 끌 수 있습니다. 관찰 기록에는 제어면의 설정 변경과 에이전트 턴이 모두 남습니다. 턴 로그에는 민감 정보가 있을 수 있어, 보안팀 소수만 보게 잠가 둡니다.

## 사내 규모와 공개 제어면은 아직 초기 단계다

Lin에 따르면 사내 OpenClaw 파일럿 뒤 기술 팀과 비기술 팀 모두에서 생산성과 도입이 크게 늘었습니다. 글을 쓸 당시 백그라운드에서 먼저 움직이는 에이전트는 500대가 넘었습니다. 이 에이전트들은 제품 피드백을 받아 PR을 열고, 새 기능의 데이터 실험도 계속 돌립니다. OpenAI는 DevDay에서 OpenClaw Enterprise(OCE)를 발표했습니다. 특정 개발사에 묶이지 않는 오픈소스 에이전트 제어면입니다. 표준 Codex 프리셋을 쓰면 앞에서 말한 보호 장치 상당수를 켠 채 에이전트를 실행할 수 있습니다. 아직 파일럿 단계이고, 그해 말 1.0을 목표로 합니다.

Lin이 보여 주는 것은 통제 목록과 설정 예시입니다. 각 통제가 사고를 얼마나 줄였는지는 나오지 않습니다. 로컬 코딩 에이전트에는 조직 관리형 프록시, 브로커, 별도 클러스터가 없을 수 있습니다. 그래도 옮겨 올 축은 분명합니다. 에이전트를 더 믿기 전에 허용 목록, 쓰기 범위, 우회 모드를 확인하고, 에이전트가 비밀을 볼 수 있는지부터 점검합니다.
