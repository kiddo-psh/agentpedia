2026년 1월 2일, 보리스 체르니가 X에 게시물 15개짜리 스레드를 올렸습니다.
체르니는 Anthropic에서 일합니다. 첫 게시물에서 자신을 Claude Code를 만든 사람이라고 소개했습니다.
이어지는 말은 조금 뜻밖이었습니다. 자기 설정은 의외로 평범할 수 있다고 했습니다. Claude Code가 기본 상태로도 잘 동작해서 따로 많이 바꾸지 않는다는 이유였습니다.

도구를 만든 사람이라면 남들이 모르는 설정을 쓸 거라고 기대하기 쉽습니다.
숨은 플래그나 공들인 프롬프트, 복잡한 자동화 같은 것 말입니다.
체르니의 스레드에는 그런 내용이 거의 없습니다.
대신 매일 되풀이하는 습관이 나옵니다. 세션을 여러 개 동시에 돌리고, 실수를 적어 두고, 계획부터 세우고, 반복 작업은 명령으로 만듭니다.
스레드 마지막에는 아마 가장 중요할 거라며 한 가지를 따로 꼽습니다.

<KeyIdea title="가장 중요한 한 가지: Claude가 스스로 검증하게 하기">
체르니는 마지막 팁이자 아마 가장 중요한 팁으로, Claude에게 자기 작업을 검증할 방법을 주라고 말합니다. 이런 피드백 루프가 있으면 최종 결과의 품질이 2~3배 좋아진다고 합니다. 이 수치는 체르니 본인의 말이고, 스레드에 측정 근거는 없습니다.
</KeyIdea>

<Quote source="thread">
give Claude a way to verify its work. If Claude has that feedback loop, it will 2-3x the quality of the final result.
</Quote>

예도 하나 듭니다. claude.ai/code에 들어가는 변경은 모두 Claude가 Chrome 확장으로 브라우저에서 직접 테스트한다고 합니다.
이 글에서는 나머지 습관도 이 원칙을 뒷받침하는 장치로 보고 하나씩 살펴보겠습니다.

가장 먼저 눈에 띄는 습관은 세션을 여러 개 동시에 돌리는 것입니다.
스레드를 올릴 무렵 체르니는 터미널에서 Claude 세션 5개를 병렬로 돌렸습니다.
탭마다 번호를 붙이고, Claude가 입력을 기다리면 시스템 알림을 받습니다.

웹에서도 마찬가지입니다. 로컬 세션과 별도로 claude.ai/code에서 세션 5~10개를 동시에 돌립니다.
로컬 세션은 `&`로 웹에 넘기고, 가끔은 `--teleport`로 로컬과 웹을 오갑니다.

스레드에 달린 질문에 답하면서 두 가지를 덧붙이기도 했습니다.
로컬 세션 5개는 같은 레포를 따로 받은 git checkout 5개에서 각각 돕니다.
시작한 세션 중 중간에 버리는 비율을 묻자 "대략 10~20%쯤"이라고 어림했습니다.

모델 선택도 단순합니다. 당시 그는 모든 작업에 thinking을 켠 Opus 4.5를 썼습니다.
Sonnet보다 크고 느립니다. 하지만 덜 이끌어 줘도 되고 도구도 더 잘 써서, 결국 작은 모델보다 거의 항상 빨리 끝난다고 설명합니다.

---

세션을 많이 돌릴수록 Claude가 같은 실수를 되풀이하지 않게 하는 일이 중요해집니다.
당시 체르니의 팀은 git에 체크인한 `CLAUDE.md` 파일 하나를 함께 썼습니다.
규칙은 간단합니다. Claude가 뭔가 잘못하는 걸 보면 바로 적어 두고, 다음에는 그러지 않게 합니다.

<Quote source="thread">
Anytime we see Claude do something incorrectly we add it to the CLAUDE.md, so Claude knows not to do it next time.
</Quote>

코드 리뷰에서도 같은 일을 합니다. 동료 PR에 `@.claude`를 태그하면 Claude Code GitHub Action이 `CLAUDE.md`에 규칙을 추가합니다.
InfoQ에 따르면 2026년 1월 기준 팀의 `CLAUDE.md`는 약 2.5k 토큰이었습니다. 다만 이 수치는 스레드 본문에서는 확인하지 못했습니다.
실수를 한 번 적어 두면 팀원 모두의 다음 세션이 그만큼 덜 틀립니다.
검증 쪽에서 보면 `CLAUDE.md`는 Claude가 무엇을 틀렸는지 알려 주는 느린 피드백 루프입니다.

세션을 시작하는 방식도 정해져 있습니다. 체르니는 대부분의 세션을 Plan 모드로 시작한다고 썼습니다.
계획이 마음에 들 때까지 Claude와 주고받습니다. 그다음 auto-accept edits 모드로 바꾸면 Claude가 대개 한 번에 구현을 끝낸다고 합니다.

<Quote source="thread">
From there, I switch into auto-accept edits mode and Claude can usually 1-shot it.
</Quote>

'대개'라고 했다는 점은 기억해 둘 만합니다. 계획이 좋아도 매번 한 번에 끝나지는 않습니다.
계획을 먼저 맞춰 두면 덤으로 얻는 것도 있습니다. 구현이 끝난 뒤 무엇을 확인할지가 미리 정해집니다.

하루에도 몇 번씩 하는 작업은 `.claude/commands/`에 슬래시 명령으로 만들어 둡니다.
대표적인 예가 `/commit-push-pr`입니다. 체르니는 자신과 Claude가 이 명령을 하루에 수십 번 쓴다고 합니다.
이 명령은 inline bash로 `git status` 같은 정보를 미리 계산해 둡니다. 덕분에 모델과 주고받는 횟수가 줄어듭니다.
코드 단순화와 검증은 슬래시 명령 대신 서브에이전트(`code-simplifier`, `verify-app`)가 맡습니다. 검증만 하는 역할을 따로 둔 셈입니다.

훅도 씁니다. PostToolUse 훅으로 Claude가 쓴 코드를 포맷해서, CI에서 포맷 오류가 나지 않게 합니다. InfoQ는 이 명령이 `bun run format || true`라고 전합니다.
오래 걸리는 작업에는 Stop 훅과 백그라운드 검증 에이전트를 붙입니다. Slack, BigQuery, Sentry 같은 외부 도구도 Claude가 직접 다루게 합니다.

권한 설정도 같은 방향입니다. 빨리 일하고 싶으면 권한 확인을 아예 끄고 싶어집니다. 체르니는 평소에는 그렇게 하지 않는다고 밝힙니다.

<Compare
  before="--dangerously-skip-permissions로 권한 확인을 아예 끈다"
  after="/permissions로 자주 쓰는 안전한 bash 명령만 미리 허용하고, 이 설정을 .claude/settings.json에 넣어 팀과 공유한다"
/>

<Quote source="thread">
I don't use --dangerously-skip-permissions.
</Quote>

다만 오래 걸리는 작업을 다룬 게시물에서는, 샌드박스 안이라면 권한 확인을 건너뛰기도 한다고 덧붙입니다.
허용 목록이 팀 설정 파일에 들어 있으니, 한 사람이 정리해 두면 모두가 같이 씁니다.

---

이 방식을 그대로 따라 하기 전에 따져 볼 점이 몇 가지 있습니다.

첫째, 병렬 세션에도 비용이 듭니다. 체르니는 시작한 세션 중 대략 10~20%는 중간에 버린다고 어림했습니다. 여러 세션을 동시에 지켜보는 데에도 사람의 주의가 필요합니다.

둘째, 모델 선택에도 대가가 있습니다. 체르니도 Opus 4.5가 Sonnet보다 크고 느리다고 인정합니다. 결국 거의 항상 더 빠르다는 말은 자기 작업을 두고 한 판단입니다. 게다가 2026년 1월 기준 이야기라서, 모델 이름과 기능은 그 뒤에 바뀌었을 수 있습니다.

셋째, '2~3배'는 측정값이 아니라 체르니의 경험에서 나온 숫자입니다. 검증 루프가 얼마나 효과를 낼지는 레포에 믿을 만한 테스트나 실행 수단이 얼마나 있느냐에 달려 있습니다.

마지막으로, 체르니 본인도 스레드 첫머리에서 정해진 사용법은 없고 팀원마다 쓰는 방식이 다르다고 말합니다.

스레드에 단 답글에서 체르니는 요즘 일의 많은 부분이 코드 리뷰와 방향 잡기라고 했습니다. CI에서 Claude Agent SDK가 코드 리뷰를 대부분 먼저 끝내서, 사람이 볼 때쯤에는 코드가 이미 괜찮은 상태라고 합니다.
여기서도 핵심은 사람보다 먼저 확인하는 장치입니다. 가져갈 것은 그의 설정 파일이 아니라 습관입니다. 그중에서도 Claude가 자기 일을 스스로 확인하게 만드는 습관입니다.
